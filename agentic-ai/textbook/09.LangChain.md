## 1. LLM 애플리케이션 개발의 현실

### 1.1 LLM API 직접 호출의 한계

LLM 개발 시 가장 먼저 접하는 방법은 OpenAI, Anthropic, Google Gemini SDK 직접 호출  
프로젝트 규모가 커질수록 다음과 같은 문제에 직면

- **반복되는 보일러플레이트 코드**  
  각 API 호출마다 프롬프트 구성, 응답 파싱, 에러 처리 로직을 매번 작성 필요
- **모델별 API 차이 대응의 피로**  
  OpenAI는 `messages` 배열, Claude는 `system` 파라미터 분리,  
  Gemini는 `Content` 객체 요구  
  모델 교체 시 핵심 비즈니스 로직 수정 필요
- **복잡한 워크플로우 구현의 어려움**  
  "검색 → 요약 → 검증 → 답변" 같은 멀티스텝 체인을  
  순수 API만으로 구현하면 코드가 스파게티화됨

**[예제] Raw API 호출 vs LangChain 비교**     

**Raw OpenAI API 호출:**

```python
import openai

client = openai.OpenAI()

# 모델별로 파라미터 구조가 다름
response = client.chat.completions.create(
    model="gpt-4",
    messages=[{"role": "user", "content": "LangChain의 장점이 뭐야?"}]
)
print(response.choices[0].message.content)
```

**LangChain을 통한 추상화:**

```python
from langchain_openai import ChatOpenAI

# 모델 교체 시 ChatOpenAI 클래스만 교체하면 됨
llm = ChatOpenAI(model="gpt-4")
response = llm.invoke("LangChain의 장점이 뭐야?")
print(response.content)
```

### 1.2 개발자가 마주하는 핵심 문제들

실제 서비스 수준의 애플리케이션 구축 시 다음 4가지 장벽 존재

| 문제 | 설명 |
|------|------|
| **컨텍스트 윈도우 제한** | LLM이 한 번에 읽을 수 있는 텍스트 양이 제한됨 |
| **멀티턴 대화 상태 관리** | 이전 질문 기억 및 대화 이력의 효율적 저장/요약 필요 |
| **외부 데이터 연동 (RAG)** | 최신 데이터나 기업 내부 데이터 실시간 참조 필요 |
| **도구 사용 및 에이전트 구현** | LLM이 웹 검색, 코드 실행 등을 자율적으로 수행해야 함 |

## 2. LangChain의 존재 이유

### 2.1 LangChain이 해결하는 4가지 핵심 가치

LangChain은 단순 API 래퍼(Wrapper)가 아닌 LLM 개발의 **표준 인프라**를 지향

| 핵심 가치 | 설명 |
|-----------|------|
| **빠른 개발** | 150개+ 문서 로더, 60개+ 벡터 스토어 통합 제공. 개발 시간 3~5배 단축 |
| **벤더 독립성** | LCEL로 모델/도구/DB를 레고 블록처럼 교체 가능. 특정 모델 종속 없음 |

## 4. LangChain 생태계 전체 그림

LangChain은 단순 LLM 호출 라이브러리를 넘어  
복잡한 AI 애플리케이션 구축을 위한 거대한 생태계 형성

### 4.1 구성요소 개요

LangChain 생태계는 4가지 핵심 프로젝트로 구성

| 컴포넌트 | 역할 | 설명 |
|---------|-----|------|
| **LangChain** | 기본 프레임워크 | 체인/도구/컴포넌트 결합을 담당하는 뼈대 |
| **LangGraph** | 오케스트레이션 | Stateful 그래프 기반 워크플로우 제어 |
| **LangSmith** | 관측/통제/품질평가 | LLM 호출 트레이싱, 평가, 모니터링 |
| **LangServe** | REST API 배포 | FastAPI 기반 API 서버 배포 |

### 4.2 패키지 구조

최신 LangChain(v0.2+)은 모듈화/경량화를 위해 여러 패키지로 분리

| 패키지 | 역할 |
|--------|------|
| `langchain-core` | 기본 인터페이스 및 LCEL 핵심 로직 |
| `langchain` | 인지 아키텍처, 범용 체인, 에이전트 기능 |
| `langgraph` | 멀티 에이젼트 Workflow 구현 |
| `langchain-community` | 서드파티 통합(Vector DB, Loaders 등) |
| `langchain-openai` | OpenAI 전용 최적화 패키지 |
| `langchain-anthropic` | Anthropic(Claude) 전용 패키지 |
| `langchain-google-genai` | Google Gemini API 전용 패키지 |
| `langchain-google-vertexai` | Google Cloud Vertex AI 전용 패키지 (엔터프라이즈급) |

> **인지 아키텍처(Cognitive Architecture)란?**  
> AI 시스템이 인간의 인지 과정을 모방하여 추론, 기억, 계획, 학습 등을  
> 수행하는 구조. LangChain에서는 에이전트가 스스로 생각(Reasoning)하고  
> 행동(Action)하며 결과를 관찰(Observation)하는 ReAct 패턴 등을 제공

#### 설치 예시

```bash

# OpenAI 연동
pip install langchain-openai

# Google Gemini 연동

# 커뮤니티 통합 (벡터 DB, 문서 로더 등)
```

#### 왜 모델별 전용 패키지가 필요한가?

LangChain의 목적이 AI 모델 추상화인데 왜 전용 패키지가 분리되어 있는지 의문이 생길 수 있음

| 구분 | 설명 |
|------|------|
| **패키지 분리 이유** | 의존성 경량화. 필요한 모델의 SDK만 설치하여 불필요한 의존성 제거 |
| **전용 패키지 필수 여부** | 필수. 해당 모델 사용 시 전용 패키지 설치 필요 |
| **추상화가 작동하는 지점** | 코드 인터페이스. 패키지는 다르지만 사용법(API)은 동일 |

```python

from langchain_anthropic import ChatAnthropic
from langchain_google_genai import ChatGoogleGenerativeAI

openai_llm.invoke("안녕")   # 동일
```

### 4.3 핵심 개념 요약

LangChain의 핵심 개념을 AI 어플리케이션 **5대 핵심 구성요소**에 매핑하여 이해

```
AI 어플리케이션 5대 핵심 구성요소 → LangChain 매핑
├── ① Workflow 관리    → LangGraph (그래프 기반 워크플로우)
├── ② LLM 인터페이스   → Model I/O (프롬프트, 모델, 파서) + LCEL (파이프라인 연결)
├── ③ RAG             → Retrieval (문서 로드, 분할, 임베딩, 검색)
├── ④ Tools 연동       → Agents & Tools (도구 정의, 에이전트 실행)
└── ⑤ Harness          → LangSmith + Callbacks (관측, 통제, 품질평가)
```

| 구성요소 | LangChain 핵심 개념 | 설명 | Use Case | 핵심 클래스 |
|:---|:---|:---|:---|:---|
| **① Workflow 관리** | LangGraph | 복잡한 에이전트 흐름을 그래프로 제어. 순환/분기/상태 관리 | 승인 워크플로우, 멀티 에이전트 | `StateGraph`, `MemorySaver` |
| **② LLM 인터페이스** | Model I/O + LCEL | 프롬프트 구성 → 모델 호출 → 응답 파싱을 파이프라인으로 연결 | 번역기, 요약기, Q&A 봇 | `ChatPromptTemplate`, `StrOutputParser`, `RunnableSequence` |
| **③ RAG** | Retrieval | 내/외부 문서 검색으로 LLM 지식 보강 | 사내 문서 Q&A, 법률 검색 | `FAISS`, `Chroma`, `RecursiveCharacterTextSplitter` |
| **④ Tools 연동** | Agents & Tools | LLM이 스스로 도구를 선택하여 외부 API/함수 호출 | 웹 검색 봇, 코드 실행기 | `create_agent`, `@tool` |
| **⑤ Harness** | LangSmith + Callbacks | 관측, 통제, 품질평가 | 비용 모니터링, 품질 평가, 보안 필터링 | `CallbackHandler`, `LangSmithTracer`, `RateLimiter` |

## 5. 핵심 개념 ① - Workflow 관리 (LangGraph)

LangGraph는 순환(Cycle)이 포함된 복잡한 에이전트 로직 구현을 위한 최신 프레임워크

### 5.1 왜 LangGraph인가?

일반적인 LCEL 체인은 선형적으로 흐르기 때문에
"도구 사용 후 다시 판단하기" 같은 루프(반복) 구현이 어려움
LangGraph는 이를 그래프 구조로 해결

| 특징 | LCEL 체인 | LangGraph |
|------|-----------|-----------|
| 흐름 | 선형 (A → B → C) | 그래프 (순환, 분기 가능) |
| 상태 관리 | 제한적 | 풍부한 상태 관리 |
| 에이전트 루프 | 구현 어려움 | 자연스러운 구현 |

### 5.2 핵심 개념

| 개념 | 설명 |
|------|------|
| **State** | 그래프 내에서 공유되는 데이터 (메시지 리스트 등) |
| **Node** | 실제 작업 수행 함수 (LLM 호출, 도구 실행 등) |
| **Edge** | 노드 간 이동 경로 (조건부 분기 포함) |

### 5.3 실전 패턴 예제

```python
from typing import Annotated
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langchain_openai import ChatOpenAI

# 1. 상태 정의
class State(TypedDict):
    messages: Annotated[list, add_messages]

# 2. 모델 초기화
model = ChatOpenAI(model="gpt-4o-mini")

# 3. 노드 정의
def chatbot(state: State):
    """챗봇 노드: LLM 호출하여 응답 생성"""
    response = model.invoke(state["messages"])
    return {"messages": [response]}

# 4. 그래프 구성
builder = StateGraph(State)
builder.add_node("chatbot", chatbot)
builder.add_edge(START, "chatbot")
builder.add_edge("chatbot", END)

# 5. 컴파일
graph = builder.compile()

# 6. 실행
result = graph.invoke({
    "messages": [{"role": "user", "content": "안녕하세요!"}]
})
print(result["messages"][-1].content)
```

#### Human-in-the-loop 패턴

```python
from langgraph.graph import StateGraph, START, END

def should_continue(state: State) -> str:
    """조건부 분기: 사람 승인 필요 여부 판단"""
    last_message = state["messages"][-1]
    if "위험" in last_message.content:
        return "human_review"
    return "continue"

builder = StateGraph(State)
builder.add_node("agent", agent_node)
builder.add_node("human_review", human_review_node)

# 조건부 엣지 추가
builder.add_conditional_edges(
    "agent",
    should_continue,
    {
        "continue": END,
        "human_review": "human_review"
    }
)

graph = builder.compile()
```

### 5.4 State 관리
State 관리는 AI 어플리케이션에서 **두 가지 핵심 역할** 수행

#### State 관리의 두 가지 역할

| 역할 | 설명 | 예시 |
|:---|:---|:---|
| **① 대화 상태 관리** | 멀티턴 대화에서 이전 대화를 기억하여 컨텍스트 유지 | "토마토 요리 추천해줘" → "재료가 뭐야?" → 토마토 스파게티 재료 답변 |
| **② 워크플로우 상태 관리** | 그래프의 실행 상태(어떤 노드를 거쳤는지, 조건 분기 결과, 중간 데이터 등)를 저장하여 중단/재개, Human-in-the-loop 지원 | 승인 대기 중 상태 저장 → 승인 후 이어서 실행 |

LangGraph의 `MemorySaver`(Checkpointer)가 두 역할을 **모두 담당**하는 표준 방식

```
① 대화 상태 관리                      ② 워크플로우 상태 관리
─────────────                         ─────────────
Memory 없이:                          State 없이:
사용자: "토마토 요리 추천해줘"         [검색] → [승인 대기] → 서버 재시작
AI: "스파게티를 추천합니다"            → 처음부터 다시 시작 ✗
사용자: "재료가 뭐야?"
AI: "무슨 요리를 말씀하시나요?" ✗     State 사용:
                                      [검색] → [승인 대기] → 서버 재시작
Memory 사용:                          → 승인 대기 상태에서 이어서 실행 ✓
AI: "토마토 스파게티 재료는..." ✓
```

> **권장 방식 변화**
> LangChain 최신 버전에서는 기존 `ConversationBufferMemory` 등의 레거시 메모리 대신
> **LangGraph의 Checkpointer**를 사용한 상태 관리를 권장

#### 메모리 방식 비교

| 방식 | 상태 | 담당 역할 | 컨텍스트 유지 방법 | 권장 용도 |
|------|------|----------|-------------------|----------|
| `MemorySaver` (LangGraph) | **권장** | ①② 모두 | 그래프 상태를 체크포인트로 자동 저장 | 에이전트, 복잡한 워크플로우 |
| `InMemoryChatMessageHistory` | 권장 | ① 대화만 | 메시지 이력을 메모리에 저장 | 단순 체인의 대화 이력 |
| `ConversationBufferMemory` | 레거시 | ① 대화만 | 전체 대화를 버퍼에 저장 | 기존 코드 유지보수 시 참고 |

#### 권장: LangGraph Checkpointer

최신 LangChain에서 상태 관리의 **표준 방식**.
대화 상태와 워크플로우 상태를 자동으로 체크포인트에 저장하여,
**`thread_id`로 세션을 구분하고 이전 대화 및 워크플로우를 이어갈 수 있음**

##### ① 대화 상태 관리 예제

```python
from langgraph.checkpoint.memory import MemorySaver
from langgraph.graph import StateGraph, START, END

# 인메모리 체크포인터 (개발/테스트용)
checkpointer = MemorySaver()

# 그래프에 체크포인터 연결 → 대화 상태 자동 저장
graph = builder.compile(checkpointer=checkpointer)

# thread_id로 대화 세션 구분 → 같은 thread_id면 이전 대화 기억
config = {"configurable": {"thread_id": "user-123"}}
result = graph.invoke({"messages": [...]}, config)
```

##### ② 워크플로우 상태 관리 예제

승인이 필요한 워크플로우에서 중간 상태를 저장하고, 승인 후 이어서 실행하는 패턴

```python
from typing import Annotated
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langgraph.checkpoint.memory import MemorySaver

# 1. 워크플로우 상태 정의 (대화 + 승인 상태)
class WorkflowState(TypedDict):
    messages: Annotated[list, add_messages]
    approval_status: str  # "pending", "approved", "rejected"
    order_data: dict      # 주문 정보 등 중간 데이터

# 2. 노드 정의
def process_order(state: WorkflowState):
    """주문 처리 후 승인 대기 상태로 전환"""
    return {"approval_status": "pending", "order_data": {"item": "서버 증설", "cost": 5000000}}

def execute_order(state: WorkflowState):
    """승인된 주문 실행"""
    return {"messages": [{"role": "ai", "content": f"주문 실행 완료: {state['order_data']}"}]}

# 3. 조건부 분기: 승인 여부에 따라 다음 노드 결정
def check_approval(state: WorkflowState) -> str:
    if state["approval_status"] == "approved":
        return "execute"
    return "wait"  # 승인 대기 → 그래프 중단, 상태는 체크포인터에 저장됨

# 4. 그래프 구성
builder = StateGraph(WorkflowState)
builder.add_node("process", process_order)
builder.add_node("execute", execute_order)
builder.add_edge(START, "process")
builder.add_conditional_edges("process", check_approval, {"execute": "execute", "wait": END})
builder.add_edge("execute", END)

# 5. 체크포인터 연결 → 워크플로우 중간 상태 자동 저장
checkpointer = MemorySaver()
graph = builder.compile(checkpointer=checkpointer)

# 6. 첫 실행: 주문 처리 → 승인 대기 상태에서 중단
config = {"configurable": {"thread_id": "order-456"}}
result = graph.invoke({"messages": [], "approval_status": "", "order_data": {}}, config)
# → approval_status: "pending", 상태가 체크포인터에 저장됨

# 7. 승인 후 재실행: 저장된 상태에서 이어서 실행
graph.update_state(config, {"approval_status": "approved"})
result = graph.invoke(None, config)
# → "주문 실행 완료" 출력
```

> **핵심**: 같은 `thread_id`로 호출하면 체크포인터에 저장된 상태에서 이어서 실행.
> 서버가 재시작되더라도 DB 기반 체크포인터 사용 시 상태 복원 가능

##### 영속성이 필요한 경우 (프로덕션)

서버 재시작 후에도 대화 이력을 유지하려면 DB 기반 체크포인터 사용

```python
from langgraph.checkpoint.postgres import PostgresSaver

# PostgreSQL 기반 체크포인터 (프로덕션용)

    "postgresql://user:pass@localhost/db"

```

#### 단순 메시지 이력 관리

LangGraph 없이 간단한 대화 이력만 필요한 경우.
세션별로 메시지 이력을 저장하여 이전 대화를 컨텍스트에 포함

```python
from langchain_core.chat_history import InMemoryChatMessageHistory
from langchain_core.runnables.history import RunnableWithMessageHistory

# 세션별 메시지 이력 저장소
store = {}

def get_session_history(session_id: str):
    if session_id not in store:
        store[session_id] = InMemoryChatMessageHistory()
    return store[session_id]

# 체인에 메시지 이력 기능 추가 → 이전 대화를 자동으로 프롬프트에 포함
chain_with_history = RunnableWithMessageHistory(
    chain,
    get_session_history,
    input_messages_key="input",
    history_messages_key="history"
)

# 세션 ID로 대화 이력 유지
config = {"configurable": {"session_id": "user-123"}}
chain_with_history.invoke({"input": "안녕하세요"}, config)
```

```python
from langchain_openai import ChatOpenAI

    SystemMessage(content="당신은 한국어 번역 전문가입니다."),

# 멀티턴 대화 — AIMessage로 이전 응답을 포함하여 컨텍스트 유지
messages = [
    SystemMessage(content="당신은 한국어 번역 전문가입니다."),
    HumanMessage(content="I love developing AI agents with LangChain!"),
    AIMessage(content="나는 LangChain으로 AI 에이전트를 개발하는 것을 좋아합니다!"),

response = chat.invoke(messages)
print(response.content)
# 출력: "나는 LangChain으로 AI 에이전트 만드는 게 너무 좋아!"
```

### 6.3 Output Parsers

모델 출력을 원하는 형식으로 변환하는 파서

| OutputParser | 용도 |
|--------------|------|
| `StrOutputParser` | 모델 응답을 단순 문자열로 추출 |
| `SimpleJsonOutputParser` | 모델 응답에서 JSON 객체를 파싱 |
| `PydanticOutputParser` | Pydantic 모델 기반으로 구조화된 객체 파싱 |
| `CommaSeparatedListOutputParser` | 쉼표로 구분된 리스트를 파싱 |
| `DatetimeOutputParser` | 날짜/시간 문자열을 datetime 객체로 파싱 |
| `XMLOutputParser` | XML 형식의 응답을 딕셔너리로 파싱 |
| `MarkdownListOutputParser` | 마크다운 리스트 형식을 파싱 |

OutputParser는 LCEL의 파이프(`|`) 연산자로 체인에 연결하여 사용

```
chain = prompt | llm | parser
         ①        ②      ③
```

| 단계 | 역할 | 설명 |
|------|------|------|
| ① `prompt` | 입력 가공 | 템플릿에 변수를 삽입하여 프롬프트 생성 |
| ② `llm` | 모델 호출 | 프롬프트를 LLM에 전달하고 응답 수신 |
| ③ `parser` | 출력 변환 | 모델 응답을 원하는 형식(문자열, JSON, 객체 등)으로 파싱 |

`chain.invoke()`를 호출하면 ① → ② → ③ 순서로 데이터가 흘러
입력부터 최종 파싱 결과까지 한 번에 처리됨

#### ① StrOutputParser — 문자열 추출

```python
from langchain_core.output_parsers import StrOutputParser
from langchain_openai import ChatOpenAI

llm = ChatOpenAI(model="gpt-4o-mini")
parser = StrOutputParser()

chain = llm | parser
result = chain.invoke("토마토의 효능을 한 줄로 요약하세요")
print(result)  # "토마토는 항산화 성분이 풍부하여 심혈관 건강에 도움을 줍니다."
print(type(result))  # <class 'str'>
```

#### ② SimpleJsonOutputParser — JSON 파싱

```python
from langchain.output_parsers.json import SimpleJsonOutputParser
from langchain_core.prompts import PromptTemplate

parser = SimpleJsonOutputParser()

prompt = PromptTemplate.from_template(
    "다음 요리의 정보를 JSON으로 응답하세요.\n요리: {dish}\n{format_instructions}"
)

chain = prompt | llm | parser
result = chain.invoke({
    "dish": "토마토 스파게티",
    "format_instructions": parser.get_format_instructions(),
```

### 6.4 Structured Output

| 구분 | PydanticOutputParser (6.3 ③) | Structured Output (6.4) |
|------|------|------|
| **방식** | 프롬프트로 JSON 형식 출력을 텍스트로 요청 → 파서가 파싱 | 모델의 Function Calling API로 JSON Schema 강제 |
| **신뢰성** | 모델이 형식을 안 지키면 파싱 에러 발생 가능 | 모델 API가 구조를 보장하므로 안정적 |
| **코드** | `prompt \| llm \| parser` (3단계 체인) | `llm.with_structured_output(Model)` (모델에 직접 적용) |
| **사용 조건** | 모든 LLM에서 사용 가능 | Function Calling 지원 모델만 가능 (GPT-4, Claude 등) |
| **권장** | Function Calling 미지원 모델용 | **실무 권장** (안정성 우수) |

Pydantic 모델로 구조화된 데이터(JSON 등)를 정확하게 추출 가능

```python
from pydantic import BaseModel, Field
from langchain_openai import ChatOpenAI

class Recipe(BaseModel):
    """요리 레시피 정보"""
    name: str = Field(description="요리 이름")
    difficulty: str = Field(description="난이도 (상, 중, 하)")
    ingredients: list[str] = Field(description="필요한 재료 리스트")
    cooking_time: int = Field(description="조리 시간 (분)")

llm = ChatOpenAI(model="gpt-4o-mini")

# 구조화된 출력 적용
structured_llm = llm.with_structured_output(Recipe)

recipe = structured_llm.invoke("토마토 스파게티 레시피를 알려줘")
print(f"요리명: {recipe.name}")
print(f"난이도: {recipe.difficulty}")
print(f"재료: {recipe.ingredients}")
print(f"조리 시간: {recipe.cooking_time}분")
```

### 6.5 LCEL (LangChain Expression Language)

LCEL(엘셀, LangChain Expression Language)은
여러 컴포넌트를 선언적으로 결합하는 LangChain 고유 언어

#### 6.5.1 LCEL이란?

`|` (파이프) 연산자로 각 컴포넌트를 연결하여 **앞 컴포넌트의 결과가 뒤 컴포넌트의 입력이 되게 체인을 구성**하는 것임
가독성이 좋고 병렬 처리, 스트리밍 등 자동 지원

```python
from langchain_core.output_parsers import StrOutputParser
from langchain_core.prompts import ChatPromptTemplate
from langchain_openai import ChatOpenAI

# 컴포넌트 정의
prompt = ChatPromptTemplate.from_template(
    "다음 주제에 대해 짧게 설명해줘: {topic}"
)
model = ChatOpenAI(model="gpt-4o-mini")
parser = StrOutputParser()

# LCEL로 체인 구성 (파이프 연산자): model에 prompt가 input으로 들어와 수행한 결과를 parser가 문자열로 변환하여 리턴
chain = prompt | model | parser

# 실행
result = chain.invoke({"topic": "인공지능"})
print(result)
```

#### 6.5.2 Runnable 인터페이스

모든 LCEL 컴포넌트는 `Runnable` 인터페이스를 따르며 공통 메서드 제공

| 메서드 | 설명 |
|--------|------|
| `invoke()` | 단일 입력에 대해 동기 호출 |
| `ainvoke()` | 단일 입력에 대해 비동기 호출 |
| `batch()` | 여러 입력에 대해 병렬 호출 |
| `stream()` | 출력을 토큰 단위로 스트리밍 |
| `astream()` | 출력을 토큰 단위로 비동기 스트리밍 |

```python
# invoke() - 동기 호출
result = chain.invoke({"topic": "인공지능"})
print(result)

# ainvoke() - 비동기 호출
import asyncio

async def async_example():
    result = await chain.ainvoke({"topic": "인공지능"})
    print(result)

asyncio.run(async_example())

# batch() - 배치 처리
results = chain.batch([
    {"topic": "인공지능"},
    {"topic": "블록체인"},
    {"topic": "양자컴퓨팅"}
])

# stream() - 동기 스트리밍
for chunk in chain.stream({"topic": "우주"}):
    print(chunk, end="", flush=True)

# astream() - 비동기 스트리밍
async def async_stream_example():
    async for chunk in chain.astream({"topic": "우주"}):
        print(chunk, end="", flush=True)

asyncio.run(async_stream_example())

```

**예제 2: 여러 체인을 동시 실행**

```python

from langchain_core.output_parsers import StrOutputParser
from langchain_core.runnables import RunnableParallel

parallel_analysis = RunnableParallel(
    tech=tech_chain,

# 하나의 입력으로 3가지 분석 결과를 동시에 획득
```


##### 패스스루 (RunnablePassthrough)
입력을 그대로 통과시키는 역할을 하며 RAG 체인에서 질문을 변환 없이 전달할 때 사용

**예제 1: 입력 그대로 전달**

```python
from langchain_core.runnables import RunnablePassthrough

result = chain.invoke("안녕하세요")  # "안녕하세요"가 그대로 model로 전달
```

**예제 2: 질문은 그대로 두고, 관련 문서는 검색해서 추가 (RAG 패턴)**

```python
from langchain_core.runnables import RunnablePassthrough
from langchain_community.vectorstores import FAISS
from langchain_openai import OpenAIEmbeddings
from langchain_core.documents import Document

# 문서 및 retriever 생성
docs = [Document(page_content="토마토는 빨간색 과일입니다.")]
vectorstore = FAISS.from_documents(docs, OpenAIEmbeddings())
retriever = vectorstore.as_retriever()

# 체인 구성
chain = {
    "question": RunnablePassthrough(),  # 질문은 그대로
    "context": retriever  # 컨텍스트는 검색하여 추가
} | prompt | model
```

**예제 3: assign() - 기존 딕셔너리에 새 키 추가**

```python
from langchain_core.runnables import RunnablePassthrough

chain = (
    RunnablePassthrough.assign(uppercase=lambda x: x["text"].upper())
    | RunnablePassthrough.assign(length=lambda x: len(x["text"]))
)

result = chain.invoke({"text": "hello"})
# 결과: {"text": "hello", "uppercase": "HELLO", "length": 5}
```

**RunnablePassthrough 사용 시나리오:**
- RAG: 질문은 유지하면서 컨텍스트만 검색
- 데이터 보강: 원본 데이터는 유지하면서 추가 정보 생성
- 중간 결과 유지: 체인 중간의 데이터를 최종 출력에 포함

## 7. 핵심 개념 ③ - RAG (Retrieval)

RAG(Retrieval-Augmented Generation)는
내/외부 데이터를 검색하여 모델의 지식을 보강하는 기술

### 7.1 RAG 원리와 아키텍처

RAG는 두 단계로 분리

```
[Indexing]  Load → Split → Embed & Store   (사전 준비)
[Retrieval] Query → Retrieve → Generate    (런타임 질의)
```

#### Indexing (인덱싱)

문서를 검색 가능한 형태로 사전 준비하는 단계

1. **Load**: 문서 로드 (PDF, 웹페이지, DB 등)
2. **Split**: 문서를 청크로 분할
3. **Embed & Store**: 텍스트를 벡터로 변환하여 저장

> 암기 팁: **"불쪼임"** - 불러와서 쪼개서 임베딩 및 저장

#### Retrieval (검색)

사용자 질의 시 실시간으로 수행되는 단계

1. **Query**: 사용자 질문 입력
2. **Retrieve**: 질의와 유사한 문서 검색
3. **Generate**: 검색된 문서를 컨텍스트로 LLM 응답 생성

> 암기 팁: **"문탐생"** - 문의 관련 정보 검색하여 답변 생성

### 7.2 Document Loaders

150개 이상의 포맷(PDF, Word, HTML, CSV 등)을 지원하며,
각 Loader가 원본 데이터를 자동으로 텍스트로 변환하여 `Document` 객체로 반환

| 구성 요소 | 설명 |
|-----------|------|
| `page_content` | 원본에서 추출된 텍스트 (문자열) |
| `metadata` | 출처, 페이지 번호 등 부가 정보 (딕셔너리) |

이후 단계(Text Splitter → Embedding → Vector Store)에서 통일된 형식으로 처리 가능

**주요 지원 포맷:**

| Format | Document Loader |
|--------|-----------------|
| 텍스트 (.txt) | `TextLoader` |
| PDF (.pdf) | `PyPDFLoader` |
| Word (.docx) | `Docx2txtLoader` |
| Excel (.xlsx) | `UnstructuredExcelLoader` |
| PowerPoint (.pptx) | `UnstructuredPowerPointLoader` |
| CSV (.csv) | `CSVLoader` |
| HTML (.html) | `BSHTMLLoader` |
| JSON (.json) | `JSONLoader` |
| Markdown (.md) | `UnstructuredMarkdownLoader` |
| 웹 페이지 (URL) | `WebBaseLoader` |

> 전체 Document Loader 목록:
> [LangChain Document Loaders](https://docs.langchain.com/oss/python/integrations/document_loaders)

```python
from langchain_community.document_loaders import (
    TextLoader,
    PyPDFLoader,
    WebBaseLoader,
    CSVLoader
)

# 텍스트 파일 로드
text_loader = TextLoader("data.txt")
docs = text_loader.load()

# PDF 파일 로드
pdf_loader = PyPDFLoader("document.pdf")
pdf_docs = pdf_loader.load()

# 웹 페이지 로드
web_loader = WebBaseLoader("https://example.com")
web_docs = web_loader.load()
```

### 7.3 Text Splitters

문서를 LLM이 처리할 수 있는 적절한 크기로 분할

| 파라미터 | 용도 | 예시 |
|----------|------|------|
| `chunk_size` | 각 청크의 최대 문자 수. 너무 크면 정보 검색 정확도 저하, 너무 작으면 문맥 손실 | `500` |
| `chunk_overlap` | 인접 청크 간 겹치는 문자 수. 문맥이 끊기지 않도록 앞뒤 청크를 연결 | `50` |
| `separators` | 분할 기준 문자 목록. 앞 순서부터 우선 적용하여 의미 단위로 분할 | `["\n\n", "\n", " ", ""]` |

```python
from langchain_text_splitters import RecursiveCharacterTextSplitter

text_splitter = RecursiveCharacterTextSplitter(
    chunk_size=500,      # 청크 크기
    chunk_overlap=50,    # 청크 간 오버랩
    separators=["\n\n", "\n", " ", ""]  # 분할 기준
)

splits = text_splitter.split_documents(docs)
print(f"총 {len(splits)}개의 청크 생성")
```

### 7.4 Embeddings

텍스트를 숫자 벡터(고차원 좌표)로 변환하는 과정.
의미가 비슷한 텍스트는 벡터 공간에서 가까운 위치에 배치되므로,
벡터 간 거리를 비교하여 유사한 문서를 검색할 수 있음 (RAG의 핵심 원리)

```
"토마토 스파게티 만드는 법" → [0.12, -0.45, 0.78, ...] ─┐ 거리 가까움 = 유사
"파스타 요리 레시피"        → [0.11, -0.43, 0.80, ...] ─┘
"주식 투자 방법"            → [-0.67, 0.33, -0.12, ...] ← 거리 멀음 = 비유사
```

40개 이상의 임베딩 모델 지원

| 제공사 | 모델 | LangChain 클래스 | 특징 |
|--------|------|-----------------|------|
| OpenAI | `text-embedding-3-small` | `OpenAIEmbeddings` | 가성비 우수, 1536차원 |
| OpenAI | `text-embedding-3-large` | `OpenAIEmbeddings` | 고정밀, 3072차원 |
| Google | `text-embedding-004` | `GoogleGenerativeAIEmbeddings` | Gemini 기반, 768차원 |
| Anthropic | `voyage-3` | `VoyageAIEmbeddings` | Claude 연동 최적화 |
| HuggingFace | `BAAI/bge-m3` | `HuggingFaceEmbeddings` | 오픈소스, 다국어 지원 |
| Cohere | `embed-multilingual-v3.0` | `CohereEmbeddings` | 다국어 특화 |

> 임베딩 모델 성능 비교:
> [MTEB Leaderboard](https://huggingface.co/spaces/mteb/leaderboard) (Massive Text Embedding Benchmark)

```python
from langchain_openai import OpenAIEmbeddings

embeddings = OpenAIEmbeddings(model="text-embedding-3-small")

# 7.3에서 생성한 splits를 임베딩
# splits: 청크 분할된 Document 객체 리스트
vectors = embeddings.embed_documents([doc.page_content for doc in splits])

print(f"총 {len(vectors)}개 청크 임베딩 완료")
print(f"각 벡터 차원: {len(vectors[0])}")

# 임베딩 결과 확인
for i, vector in enumerate(vectors[:2]):  # 처음 2개만 확인
    print(f"청크 {i+1} 벡터: [{vector[0]:.4f}, {vector[1]:.4f}, ...]")
```

### 7.5 Vector Stores

임베딩된 벡터를 저장하고 유사도 검색 기능을 제공하는 저장소.
일반적으로 Retriever로 감싸서 RAG 파이프라인에서 사용

60개 이상의 벡터 저장소 통합

| Vector Store | 특징 |
|--------------|------|
| `FAISS` | Meta 개발, 로컬 실행, 설치 간편, 프로토타입에 적합 |
| `Chroma` | 오픈소스, 로컬/서버 모드 지원, 메타데이터 필터링 강력 |
| `Pinecone` | 클라우드 매니지드, 대규모 프로덕션 환경에 최적화 |
| `Weaviate` | 오픈소스, 하이브리드 검색(벡터+키워드) 지원 |
| `Qdrant` | 오픈소스, 고성능 필터링, Rust 기반 |
| `Milvus` | 오픈소스, 대규모 분산 처리, 10억+ 벡터 지원 |
| `pgvector` | PostgreSQL 확장, 기존 DB 인프라 활용 가능 |

> 전체 Vector Store 목록:
> [LangChain Vector Stores](https://docs.langchain.com/oss/python/integrations/vectorstores)

```python
    documents=splits,

    documents=splits,

    persist_directory="./chroma_db"

```

### 7.6 Retrievers

Vector Store에 저장된 문서 중 질문과 관련된 문서를 검색하여 LLM에 전달하는 역할.
Vector Store가 "저장소"라면, Retriever는 그 저장소에서 적절한 문서를 꺼내오는 "검색기"

```python
# 기본 검색기
retriever = vectorstore.as_retriever(
    search_type="similarity",  # 유사도 검색
    search_kwargs={"k": 4}     # 상위 4개 반환
)

# MMR (Maximal Marginal Relevance) 검색
mmr_retriever = vectorstore.as_retriever(
    search_type="mmr",
    search_kwargs={"k": 4, "fetch_k": 10}
)

# 검색 실행
docs = retriever.invoke("LangChain이란 무엇인가?")
```

**기본 검색 vs MMR 검색 비교:**

| 항목 | 기본 검색 (Similarity) | MMR 검색 (Maximal Marginal Relevance) |
|------|----------------------|-------------------------------------|
| **검색 방식** | 유사도만 고려 | 유사도 + 다양성 고려 |
| **결과 특징** | 가장 유사한 문서 반환 | 유사하면서도 서로 다른 관점의 문서 반환 |
| **장점** | 빠르고 간단 | 중복 제거, 다양한 관점 제공 |
| **단점** | 비슷한 문서 중복 가능 | 계산 비용이 높음 |
| **적합한 경우** | 명확한 질문, 빠른 응답 필요 | 다양한 정보 필요, 중복 최소화 |
| **파라미터** | `k`: 반환 개수 | `k`: 최종 반환 개수<br>`fetch_k`: 후보 개수 |
| **예시 시나리오** | "LangChain이란?" → 가장 유사한 4개 | "LangChain이란?" → 유사하면서 다양한 관점의 4개 |

**언제 MMR을 사용할까?**
- 비슷한 내용의 문서가 많을 때 (예: 같은 주제의 여러 블로그 글)
- 다양한 관점이나 측면을 원할 때 (예: 장단점 모두 파악)
- LLM에게 더 풍부한 컨텍스트를 제공하고 싶을 때

#### 완전한 RAG 체인 예제

```python
from langchain_core.runnables import RunnablePassthrough
from langchain_core.output_parsers import StrOutputParser
from langchain_community.vectorstores import FAISS
from langchain_openai import OpenAIEmbeddings
from langchain_core.documents import Document

# 1. 문서 준비
documents = [
    Document(page_content="LangChain은 LLM 애플리케이션 개발 프레임워크입니다."),
    Document(page_content="LangChain의 주요 기능은 Model I/O, RAG, Agents, LCEL입니다."),
    Document(page_content="RAG는 외부 문서를 검색하여 LLM의 응답을 보강합니다."),
]

# 2. 임베딩 모델 및 VectorStore 생성
embeddings = OpenAIEmbeddings()
vectorstore = FAISS.from_documents(documents, embeddings)

# 3. Retriever 생성
retriever = vectorstore.as_retriever(
    search_type="similarity",
    search_kwargs={"k": 2}
)

# 4. RAG 프롬프트
rag_prompt = ChatPromptTemplate.from_template("""
다음 컨텍스트를 기반으로 질문에 답하세요.

컨텍스트: {context}

질문: {question}

답변:
""")

# 5. RAG 체인 구성
rag_chain = (
    {"context": retriever, "question": RunnablePassthrough()}
    | rag_prompt
    | model
    | StrOutputParser()
)

# 6. 실행
answer = rag_chain.invoke("LangChain의 주요 기능은?")
print(answer)
```

## 8. 핵심 개념 ④ - Tools 연동 (Agents & Tools)

### 8.1 Tools 연동이란?

#### Agent와 Tools 개념

**Agent(에이전트)**는 LLM이 스스로 어떤 행동을 할지 결정하는 자율적인 주체.
**Tool(도구)**는 에이전트가 외부 세계와 상호작용하기 위한 실행 가능한 함수 (예: 날씨 조회, 계산기, 웹 검색 등)

에이전트는 사용자의 질문을 분석하여:
1. 도구가 필요한지 판단
2. 필요하다면 적절한 도구를 선택
3. 도구 실행 결과를 바탕으로 최종 답변 생성

**ReAct 패턴**: 추론(Reasoning) → 행동(Action) → 관찰(Observation) 사이클을 반복하며 문제 해결

#### Function Calling 5단계 프로세스

Tools 연동은 **Function Calling**을 통해 구현되며, 다음 5단계로 진행:

```
1️⃣ 도구 정의          2️⃣ 요청 전송          3️⃣ 모델 판단
   ↓                     ↓                     ↓
함수명·설명·        사용자 메시지 +      모델이 프롬프트
파라미터            도구 목록            분석 후 함수
JSON 스키마 정의     API 전송             호출 결정

4️⃣ 함수 실행          5️⃣ 결과 반환          🔄 ReAct 루프
   ↓                     ↓                     ↓
앱에서 실제          모델에 함수 결과     필요시 STEP 2~5
함수 호출 수행       전달하여              반복 실행
                     최종 응답 생성
```

#### 공통 예제: "날씨 조회 에이전트"

이 섹션에서는 동일한 예제를 **LangChain 없이 구현**과 **LangChain 사용** 두 가지 방식으로 비교

**목표**: 사용자가 "서울 날씨 알려줘"라고 요청하면, `get_weather` 도구를 호출하여 답변

```python
# 공통 도구 함수 (실제 구현)
def get_weather(city: str) -> str:
    """특정 도시의 날씨 정보를 조회"""
    # 실제로는 API 호출하지만, 여기서는 간단히 구현
    return f"{city}의 현재 날씨는 맑음, 기온 22도입니다."
```

이 함수를 LLM이 자동으로 호출하도록 만드는 과정을 5단계로 나누어 비교

### 8.2 Tools 연동 5단계 프로세스 비교

동일한 "날씨 조회 에이전트" 기능을 구현하는 과정을 5단계로 나누어,
각 단계마다 **LangChain 없이 구현**과 **LangChain 사용**을 비교

#### 8.2.1 STEP 1: 도구 정의

함수명, 설명, 파라미터 정의

##### LangChain 없이

```python
from openai import OpenAI

# 1. 실제 함수 정의
def get_weather(city: str) -> str:
    """특정 도시의 날씨 정보를 조회"""
    return f"{city}의 현재 날씨는 맑음, 기온 22도입니다."

# 2. OpenAI Function Calling용 JSON 스키마 수동 작성
tools = [{
    "type": "function",
    "function": {
        "name": "get_weather",
        "description": "특정 도시의 날씨 정보를 조회합니다",
        "parameters": {
            "type": "object",
            "properties": {
                "city": {
                    "type": "string",
                    "description": "도시 이름"
                }
            },
            "required": ["city"]
        }
    }
}]
```

**문제점**:
- JSON 스키마를 수동으로 작성해야 함 (~15줄)
- 함수와 스키마가 분리되어 관리 어려움
- 함수 시그니처 변경 시 스키마도 수동으로 동기화 필요

##### LangChain 사용

```python
from langchain.tools import tool

@tool
def get_weather(city: str) -> str:
    """특정 도시의 날씨 정보를 조회합니다"""
    return f"{city}의 현재 날씨는 맑음, 기온 22도입니다."
```

**장점**:
- `@tool` 데코레이터 하나로 자동 스키마 생성 (~5줄)
- 타입 힌트(`city: str`) + Docstring → JSON 스키마 자동 변환
- 함수와 스키마가 항상 동기화됨

##### 📊 비교

| 항목 | LangChain 없이 | LangChain 사용 |
|------|---------------|----------------|
| 코드량 | ~20줄 | ~5줄 |
| 스키마 작성 | JSON 수동 작성 | 자동 생성 |
| 유지보수 | 함수↔스키마 수동 동기화 | 자동 동기화 |
| 오류 가능성 | 높음 (스키마 오타) | 낮음 |
| 모델 호환성 | 모델마다 스키마 형식 다름 | 통일된 인터페이스 |

#### 8.2.2 STEP 2: 요청 전송

사용자 메시지 + 모델 + 도구 목록 API 전송

##### LangChain 없이

```python
from openai import OpenAI

client = OpenAI()

# 매번 API 호출 시 tools 파라미터 명시적으로 전달
response = client.chat.completions.create(
    model="gpt-4o",
    messages=[
        {"role": "user", "content": "서울 날씨 알려줘"}
    ],
    tools=tools  # ← 매번 전달해야 함
)
```

**문제점**:
- 매번 `tools` 파라미터를 명시적으로 전달
- 재사용성 낮음

##### LangChain 사용

```python
from langchain_openai import ChatOpenAI
from langchain_core.messages import HumanMessage

llm = ChatOpenAI(model="gpt-4o")
llm_with_tools = llm.bind_tools([get_weather])  # ← 한 번만 바인딩

# 이후 llm_with_tools는 항상 도구 포함
response = llm_with_tools.invoke([
    HumanMessage(content="서울 날씨 알려줘")
])
```

**장점**:
- `bind_tools()`로 한 번만 바인딩하면 재사용 가능
- 코드 간결화

##### 📊 비교

| 항목 | LangChain 없이 | LangChain 사용 |
|------|---------------|----------------|
| 바인딩 | 매 호출마다 tools 전달 | bind_tools() 한 번 |
| 재사용성 | 낮음 | 높음 |
| 코드 가독성 | 보통 | 높음 |
| 모델 호환성 | 모델마다 파라미터명 다름 | 통일된 인터페이스 |

#### 8.2.3 STEP 3: 모델 판단

모델이 도구 호출 분석 후 응답 호출 결정

##### LangChain 없이

```python
# 응답에서 tool_calls 확인
message = response.choices[0].message

if message.tool_calls:
    print("✅ 모델이 도구 호출을 결정함")
    for tool_call in message.tool_calls:
        print(f"  호출할 함수: {tool_call.function.name}")
        print(f"  전달할 인자: {tool_call.function.arguments}")  # ← JSON 문자열
else:
    print("❌ 도구 없이 직접 응답")
    print(message.content)
```

**문제점**:
- `tool_call.function.arguments`가 JSON 문자열 형태
- 다음 단계에서 `json.loads()` 필요

##### LangChain 사용

```python
# AIMessage에 tool_calls 자동 파싱
if response.tool_calls:
    print("✅ 모델이 도구 호출을 결정함")
    for tool_call in response.tool_calls:
        print(f"  호출할 함수: {tool_call['name']}")
        print(f"  전달할 인자: {tool_call['args']}")  # ← 파이썬 dict
else:
    print("❌ 도구 없이 직접 응답")
    print(response.content)
```

**장점**:
- `tool_call['args']`가 이미 파이썬 dict로 파싱됨
- 바로 사용 가능

##### 📊 비교

| 항목 | LangChain 없이 | LangChain 사용 |
|------|---------------|----------------|
| 응답 객체 | OpenAI ChatCompletion | AIMessage |
| 인자 형식 | JSON 문자열 | 파이썬 dict |
| 파싱 필요 | 예 (json.loads) | 아니오 (자동) |
| 모델 호환성 | 모델마다 응답 구조 다름 | 통일된 인터페이스 |

#### 8.2.4 STEP 4: 함수 실행

함수에 필요 인자 전달 및 호출

##### LangChain 없이

```python
import json

# 도구 호출 처리
for tool_call in message.tool_calls:
    function_name = tool_call.function.name
    # JSON 문자열을 dict로 변환
    function_args = json.loads(tool_call.function.arguments)

    # 함수 이름으로 수동 매핑
    if function_name == "get_weather":
        result = get_weather(**function_args)
    elif function_name == "calculator":
        result = calculator(**function_args)
    # ← 도구가 많아지면 elif 계속 추가...
```

**문제점**:
- `json.loads()` 수동 파싱 필요
- if-elif로 함수 수동 매핑
- 도구 추가 시마다 elif 추가 필요 (확장성 낮음)

##### LangChain 사용

```python
# 도구 딕셔너리 생성
tools = [get_weather, calculator]
tools_map = {tool.name: tool for tool in tools}

# 도구 호출 처리
for tool_call in response.tool_calls:
    # tool_call["name"]으로 도구 동적 선택
    tool = tools_map[tool_call["name"]]
    result = tool.invoke(tool_call["args"])
```

**장점**:
- 도구명으로 동적 매핑 (tools_map)
- 인자 자동 파싱 및 전달
- 도구 추가 시 코드 수정 불필요

##### 📊 비교

| 항목 | LangChain 없이 | LangChain 사용 |
|------|---------------|----------------|
| 인자 파싱 | json.loads() 수동 | 자동 파싱 |
| 함수 매핑 | if-elif 수동 분기 | .invoke() 자동 |
| 확장성 | 도구 추가마다 코드 수정 | 도구 추가만 하면 됨 |
| 모델 호환성 | 모델 변경 시 매핑 로직 수정 | 모델 변경 시 코드 수정 불필요 |

#### 8.2.5 STEP 5: 결과 반환

모델이 함수 결과 전달받아 최종 응답 생성

##### LangChain 없이

```python
# 1. 기존 메시지 히스토리에 assistant 응답 추가
messages = [
    {"role": "user", "content": "서울 날씨 알려줘"},
    message.model_dump()  # ← assistant의 tool_calls 포함
]

# 2. 도구 실행 결과를 tool 메시지로 추가
for tool_call in message.tool_calls:
    function_name = tool_call.function.name
    function_args = json.loads(tool_call.function.arguments)

    if function_name == "get_weather":
        result = get_weather(**function_args)

    # tool 메시지 수동 생성
    messages.append({
        "role": "tool",
        "tool_call_id": tool_call.id,
        "content": result
    })

# 3. 최종 응답 요청
final_response = client.chat.completions.create(
    model="gpt-4o",
    messages=messages
)

print(final_response.choices[0].message.content)
```

**문제점**:
- 메시지 히스토리 수동 관리
- dict 형태로 메시지 수동 생성
- 타입 안정성 낮음

##### LangChain 사용

```python
from langchain_core.messages import HumanMessage, ToolMessage

# 도구 딕셔너리 생성
tools = [get_weather, calculator]
tools_map = {tool.name: tool for tool in tools}

# 1. 메시지 히스토리
messages = [
    HumanMessage(content="서울 날씨 알려줘"),
    response  # ← AIMessage (tool_calls 포함)
]

# 2. 도구 실행 결과 추가
for tool_call in response.tool_calls:
    tool = tools_map[tool_call["name"]]
    result = tool.invoke(tool_call["args"])

    # ToolMessage 클래스로 타입 안전하게 생성
    messages.append(ToolMessage(
        content=result,
        tool_call_id=tool_call["id"]
    ))

# 3. 최종 응답 요청
final_response = llm_with_tools.invoke(messages)

print(final_response.content)
```

**장점**:
- Message 클래스로 타입 안전성 보장
- IDE 자동완성 지원
- 오류 방지

##### 📊 비교

| 항목 | LangChain 없이 | LangChain 사용 |
|------|---------------|----------------|
| 메시지 형식 | dict 수동 생성 | Message 클래스 |
| 타입 안정성 | 낮음 (dict) | 높음 (클래스) |
| IDE 지원 | 없음 | 자동완성 지원 |
| 모델 호환성 | 모델마다 메시지 형식 다름 | 통일된 인터페이스 |

### 8.3 ReAct 루프 구현

**ReAct 루프**는 **STEP 2~5를 종료 조건까지 반복**하는 것.
복잡한 질문(예: "서울과 부산 날씨 비교")은 여러 번 도구를 호출해야 답변 가능

```
사용자: "서울과 부산 날씨 비교해줘"

STEP 2~5 (1회차)
  → 모델: "서울 날씨 먼저 조회" → get_weather("서울") 호출
  → 결과: "서울 맑음, 22도"

STEP 2~5 (2회차)
  → 모델: "부산 날씨도 조회" → get_weather("부산") 호출
  → 결과: "부산 흐림, 20도"

STEP 2~5 (3회차)
  → 모델: 도구 불필요 → 최종 답변 생성
  → "서울은 맑고 22도, 부산은 흐리고 20도입니다. 서울이 조금 더 따뜻합니다."
```

#### LangChain 없이 (완전 수동)

```python
from openai import OpenAI
import json

client = OpenAI()

# STEP 1: 도구 정의 (생략 - 위 8.2.1 참고)
def get_weather(city: str) -> str:
    return f"{city}의 현재 날씨는 맑음, 기온 22도입니다."

tools = [...]  # JSON 스키마

# 메시지 히스토리 초기화
messages = [{"role": "user", "content": "서울과 부산 날씨 비교해줘"}]

# ReAct 루프 (수동 구현)
while True:
    # STEP 2: 요청 전송
    response = client.chat.completions.create(
        model="gpt-4o",
        messages=messages,
        tools=tools
    )

    message = response.choices[0].message
    messages.append(message.model_dump())

    # STEP 3: 모델 판단 - 종료 조건
    if not message.tool_calls:
        print(message.content)  # 최종 답변
        break

    # STEP 4: 함수 실행
    for tool_call in message.tool_calls:
        function_name = tool_call.function.name
        function_args = json.loads(tool_call.function.arguments)

        if function_name == "get_weather":
            result = get_weather(**function_args)

        # STEP 5: 결과 반환 준비
        messages.append({
            "role": "tool",
            "tool_call_id": tool_call.id,
            "content": result
        })
    # ← 다시 STEP 2로 돌아가서 반복...
```

**코드량**: ~40줄
**문제점**: 루프 로직, 히스토리 관리, 종료 조건 모두 수동 구현

```python
    # STEP 3: 모델 판단 - 종료 조건

        break

            tool_call_id=tool_call["id"]
        ))
```

### 8.5 커스텀 도구 & 빌트인 도구

#### 커스텀 도구 만들기

> **중요:** `@tool` 데코레이터 사용 시 **Docstring은 필수**.
> 에이전트는 Docstring을 description으로 읽고 도구 선택을 판단하므로,
> Docstring이 없거나 불명확하면 에이전트가 도구를 올바르게 선택하지 못함

```python
from langchain.tools import tool

@tool
def get_stock_price(symbol: str) -> str:
    """주식 심볼을 입력받아 실시간 주가를 반환합니다"""  # ← 에이전트가 이 설명을 보고 도구 선택
    prices = {"AAPL": 150.0, "GOOGL": 140.0, "MSFT": 380.0}
    return f"{symbol}: ${prices.get(symbol, 'N/A')}"

@tool
def calculate(expression: str) -> float:
    """수학 표현식을 계산합니다"""  # ← Docstring이 곧 description
    return eval(expression)

@tool
def search_web(query: str) -> str:
    """웹 검색을 수행하고 결과를 반환합니다"""
    # 실제로는 검색 API 호출
    return f"'{query}'에 대한 검색 결과..."

tools = [get_stock_price, calculate, search_web]
```

LangChain은 다양한 빌트인 도구 제공

| 도구 | 설명 | API 키 |
|------|------|--------|
| `DuckDuckGoSearchRun` | 웹 검색 결과를 텍스트로 반환 | 불필요 |
| `DuckDuckGoSearchResults` | 검색 결과 + 링크/메타데이터 반환 | 불필요 |
| `TavilySearchResults` | 고품질 검색 (AI 최적화) | 필요 |

### 8.6 Middleware 시스템

LangChain 1.0 신기능
미들웨어로 에이전트 동작을 세밀하게 제어 가능

| 미들웨어 | 기능 |
|----------|------|
| `HumanInTheLoopMiddleware` | 중요 액션 전 사람 승인 요청 |
| `SummarizationMiddleware` | 긴 대화 자동 요약 |
| `PIIMiddleware` | PII(Personally Identifiable Information) 개인정보 자동 마스킹 |

#### ① HumanInTheLoopMiddleware — 사람 승인

```python
from langchain.agents import create_agent
from langchain.agents.middleware import HumanInTheLoopMiddleware

agent = create_agent(
    model="gpt-4o",
    tools=[send_email],
    middleware=[
        HumanInTheLoopMiddleware(
            interrupt_on={
                "send_email": {  # send_email 도구 호출 시 승인 요청
                    "allowed_decisions": ["approve", "edit", "reject"]
                }
            }
        ),
    ]
)
```

#### ② SummarizationMiddleware — 대화 요약

```python
from langchain.agents.middleware import SummarizationMiddleware

agent = create_agent(
    model="gpt-4o",
    tools=tools,
    middleware=[
        SummarizationMiddleware(
            model="gpt-4o-mini",       # 요약에 사용할 모델
            trigger={"tokens": 500}    # 대화가 500 토큰 초과 시 자동 요약
        ),
    ]
)
```

#### ③ PIIMiddleware — 개인정보 마스킹

**내장 PII 타입**

| 타입 | 설명 | 검증 방식 |
|------|------|-----------|
| `email` | 이메일 주소 | 정규식 패턴 |
| `credit_card` | 신용카드 번호 | Luhn 알고리즘 |
| `ip` | IP 주소 | 표준 라이브러리 |
| `mac_address` | MAC 주소 | 정규식 패턴 |
| `url` | URL (http/https) | 정규식 패턴 |

**처리 전략 (strategy)**

| 전략 | 동작 | 출력 예시 |
|------|------|-----------|
| `block` | PII 감지 시 예외 발생 | `PIIBlockedError` 예외 |
| `redact` | 타입 표시 후 완전 대체 | `[REDACTED_EMAIL]` |
| `mask` | 부분 마스킹 | `****-****-****-1234` |
| `hash` | 해시값으로 대체 | `<email_hash:a1b2c3d4>` |

**예제 1: 내장 타입 사용**

```python
from langchain.agents.middleware import PIIMiddleware

agent = create_agent(
    model="gpt-4o",
    tools=tools,
    middleware=[
        PIIMiddleware("email", strategy="redact", apply_to_input=True),
        PIIMiddleware("credit_card", strategy="mask"),
    ]
)
```

**예제 2: 커스텀 detector (전화번호 등)**

내장 타입에 없는 PII는 `detector` 파라미터에 정규식을 지정하여 탐지

```python
from langchain.agents.middleware import PIIMiddleware

agent = create_agent(
    model="gpt-4o",
    tools=tools,
    middleware=[
        # 한국 전화번호 패턴 (010-1234-5678)
        PIIMiddleware(
            "phone",
            detector=r"\b01[0-9]-\d{3,4}-\d{4}\b",
            strategy="mask"
        ),
        # 주민등록번호 패턴 (123456-1234567)
        PIIMiddleware(
            "rrn",
            detector=r"\b\d{6}-[1-4]\d{6}\b",
            strategy="redact"
        ),
    ]
)
```

#### Middleware 적용 레벨

Middleware는 에이전트 루프(`create_agent`) 수준에서만 사용 가능하며,
단순 도구 바인딩(`bind_tools`)에서는 사용할 수 없음

| 구분 | 대상 | Middleware 사용 |
|------|------|-----------------|
| `bind_tools` | 모델 레벨 | ❌ 불가 |
| `create_agent` | 에이전트 레벨 | ✅ 가능 |

```python
# bind_tools: 모델에 도구 스키마만 연결 (루프 없음)
model_with_tools = model.bind_tools([tool1, tool2])

# create_agent: 에이전트 루프 생성 (model → tool → model 반복)
# Middleware는 이 루프의 before_model / after_model 시점에 개입
agent = create_agent(
    model=model,
    tools=[tool1, tool2],
    middleware=[PIIMiddleware("email", strategy="redact")]
)
```

`bind_tools` 체인에서 PII 처리가 필요한 경우, `RunnableLambda`로 직접 구현

```python
from langchain_core.runnables import RunnableLambda
import re

def mask_pii(text):
    return re.sub(r'\b[\w.-]+@[\w.-]+\.\w+\b', '[REDACTED]', text)

chain = RunnableLambda(mask_pii) | model.bind_tools(tools) | parser
```

### 9.1 왜 Harness인가?

**Harness Engineering**은 자율적으로 동작하는 AI 에이전트에 "고삐(harness)"를 씌워
안전하고 예측 가능하게 제어하는 엔지니어링 분야임.  
에이전트의 자율성은 허용하되, 비용·성능·보안 측면의 가드레일을 설계하여
의도된 범위 안에서만 동작하도록 보장하는 것이 핵심임.

#### 운영 리스크 3축

| 축 | 리스크 | 암기법 |
|----|--------|--------|
| **💰 비용** | 무한 루프 / 토큰 누수 / Agent 폭주 | 돌·토·폭 |
| **⚡ 성능** | 시스템 마비 / 응답 지연 / 할루시네이션 전파 | 멈·느·할 |
| **🔒 보안** | Prompt Injection / 데이터 유출 / 권한 오남용 | 침·유·권 |

#### LangChain Harness 구성요소 매핑

| 구성요소 | LangChain 도구 | 담당 리스크 |
|---------|--------------|------------|
| **Observability** | LangSmith | 관측, 통제, 품질평가 |
| **비용 관리** | Callbacks (`get_openai_callback`, `BaseCallbackHandler`) | 돌·토·폭 |
| **성능 관리** | `InMemoryRateLimiter`, `timeout`, `recursion_limit` | 멈·느·할 |
| **보안 관리** | Guardrails (`RunnableLambda`, Pydantic) | 침·유·권 |

> **Middleware vs Harness**: 섹션 8.6의 Middleware(에이전트 레벨 실행 제어)와  
> Harness(관측 + 운영 제어)는 상호 보완적 관계임

### 9.2 Observability (LangSmith)

LangSmith는 LangChain 체인·에이전트의 전 실행 과정을 추적하는 공식 Observability 플랫폼.  
비용·성능·보안 문제를 식별하려면 먼저 관측이 가능해야 함.

#### 설치 및 환경 설정

```bash
pip install langsmith
```

```bash
# .env 또는 환경 변수 설정
LANGCHAIN_TRACING_V2=true
LANGCHAIN_API_KEY=your_langsmith_api_key
LANGCHAIN_PROJECT=my-project   # 선택사항 (기본값: default)
```

#### 자동 트레이싱

환경 변수 설정만으로 모든 LangChain 체인/에이전트 실행이 자동으로 LangSmith에 기록됨

```python
from langchain_openai import ChatOpenAI
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser

# 환경변수 설정 후 일반 체인 실행 → LangSmith에 자동 트레이싱
llm = ChatOpenAI(model="gpt-4o-mini")
prompt = ChatPromptTemplate.from_template("다음을 한국어로 번역해줘: {text}")
chain = prompt | llm | StrOutputParser()

result = chain.invoke({"text": "Hello, world!"})
# LangSmith 대시보드에서 입력/출력/토큰/지연시간 확인 가능
```

#### 커스텀 트레이싱 (`@traceable`)

일반 함수도 `@traceable` 데코레이터로 LangSmith 트레이싱에 포함 가능

```python
from langsmith import traceable

@traceable(name="문서_전처리")
def preprocess_document(text: str) -> str:
    """LangChain 체인 외부 로직도 트레이스에 포함"""
    return text.strip().lower()

@traceable(name="RAG_파이프라인")
def rag_pipeline(query: str) -> str:
    docs = preprocess_document(query)  # 중첩 트레이스 자동 생성
    result = chain.invoke({"text": docs})
    return result
```

#### LangSmith 트레이스 확인 정보

| 항목 | 내용 |
|------|------|
| 입력/출력 | 각 단계별 프롬프트 및 응답 |
| 토큰 사용량 | 입력 토큰 / 출력 토큰 / 비용 |
| 지연 시간 | 단계별 latency (ms) |
| 에러 | 예외 발생 위치 및 스택 트레이스 |
| 평가 | 수동/자동 품질 평가 결과 |

### 9.3 비용 관리 (Callbacks)

LangChain Callbacks는 실행 파이프라인의 각 단계에서 이벤트를 가로채는 훅(Hook) 시스템.  
`on_llm_start`, `on_llm_end` 등의 이벤트를 활용하여 비용을 추적하고 제어함.

#### 주요 Callback 이벤트

| 이벤트 | 발생 시점 |
|--------|----------|
| `on_llm_start` | LLM 호출 직전 |
| `on_llm_end` | LLM 응답 수신 후 |
| `on_llm_error` | LLM 오류 발생 시 |
| `on_chain_start/end` | 체인 시작/종료 |
| `on_tool_start/end` | 도구 실행 시작/종료 |

#### ① 토큰/비용 추적 (`get_openai_callback`)

```python
from langchain_community.callbacks import get_openai_callback
from langchain_openai import ChatOpenAI

llm = ChatOpenAI(model="gpt-4o-mini")

with get_openai_callback() as cb:
    result = llm.invoke("LangChain이란?")
    print(f"입력 토큰: {cb.prompt_tokens}")
    print(f"출력 토큰: {cb.completion_tokens}")
    print(f"총 비용: ${cb.total_cost:.4f}")
    print(f"총 토큰: {cb.total_tokens}")
```

#### ② 비용 한도 초과 시 중단 (커스텀 Callback 구현)

`CostLimitCallbackHandler`는 LangChain 빌트인 클래스가 아님. `BaseCallbackHandler`를 상속하여 직접 구현하는 커스텀 핸들러임

```python
from langchain_core.callbacks import BaseCallbackHandler
from langchain_core.outputs import LLMResult

class CostLimitCallbackHandler(BaseCallbackHandler):
    """누적 비용이 임계값 초과 시 예외 발생 — MAS.md '돌·토·폭' 리스크 대응"""

    def __init__(self, max_cost: float = 1.0):
        self.max_cost = max_cost
        self.total_cost = 0.0

    def on_llm_end(self, response: LLMResult, **kwargs) -> None:
        # OpenAI 응답에서 토큰 정보 추출
        usage = response.llm_output.get("token_usage", {})
        # 비용 추정 (gpt-4o-mini 기준: 입력 $0.15/1M, 출력 $0.60/1M)
        cost = (usage.get("prompt_tokens", 0) * 0.00000015 +
                usage.get("completion_tokens", 0) * 0.0000006)
        self.total_cost += cost

        if self.total_cost > self.max_cost:
            raise RuntimeError(f"비용 한도 초과: ${self.total_cost:.4f} > ${self.max_cost}")

# 사용 예시
handler = CostLimitCallbackHandler(max_cost=0.50)
llm = ChatOpenAI(model="gpt-4o-mini", callbacks=[handler])
```

### 9.4 성능 관리 (RateLimiter)

응답 지연, 시스템 마비, 할루시네이션 전파 등 **멈·느·할** 리스크에 대응하는 LangChain 성능 제어 도구.

#### 성능 제어 도구 비교

| 도구 | 제어 대상 | 적용 방법 |
|------|----------|----------|
| `InMemoryRateLimiter` | API 호출 속도 (초당 요청 수) | 모델에 바인딩 |
| `timeout` | 단일 LLM 호출 최대 대기 시간 | 모델 파라미터 |
| `recursion_limit` | LangGraph 그래프 순환 횟수 | 컴파일 옵션 |

#### ① API 호출 속도 제한 (`InMemoryRateLimiter`)

**토큰 버킷(Token Bucket) 개념**

물이 채워지는 양동이(버킷)에 비유:
- 시간이 지나면 토큰(API호출 허가증)이 버킷에 자동으로 채워짐
- API를 호출할 때마다 토큰 1개를 꺼내 씀
- 토큰이 없으면 채워질 때까지 자동으로 대기

```
설정: requests_per_second=1, max_bucket_size=10
버킷에 채워진 횟수만큼 초당 허용 API 호출 횟수(requests_per_second)의 제약 없이, 대기하지 않고 즉각 실행됨. 마치, 비상 사용권같은 것.     

[10초 쉰 뒤]  버킷: ■■■■■■■■■■ (10개 가득) → 연속 10회 즉시 호출 가능 (burst)
[매초 호출]   버킷: □□□□□□□□□□ (항상 비어 있음) → 초당 1회만 허용
```

**코드 설명**

```python
from langchain_core.rate_limiters import InMemoryRateLimiter
from langchain_openai import ChatOpenAI

rate_limiter = InMemoryRateLimiter(
    requests_per_second=1,       # 초당 허용 API 호출 횟수
    check_every_n_seconds=0.1,   # 토큰 보충 여부를 확인하는 주기 (초). 값이 작을수록 정밀하나 CPU 사용 증가
    max_bucket_size=10,          # 버킷 최대 누적 토큰 수. 오래 쉰 후 연속 호출 가능한 최대 횟수 (burst 허용량)
)

# rate_limiter를 llm에 연결 → 이후 llm.invoke() 호출 시마다
# LangChain이 내부적으로 토큰 여부를 확인하고, 없으면 자동으로 대기 후 실행
llm = ChatOpenAI(model="gpt-4o-mini", rate_limiter=rate_limiter)
```

#### ② 타임아웃 설정

```python
from langchain_openai import ChatOpenAI

# LLM 호출당 최대 30초 대기

    model="gpt-4o-mini",
```

#### ③ LangGraph 순환 횟수 제한 (`recursion_limit`)

LangGraph 에이전트의 무한 루프 방지 — MAS.md '돌' 리스크 대응


### 9.5 보안 관리 (Guardrails)

**Guardrails**는 LCEL 체인 수준에서 입력/출력을 검증하여 보안 리스크를 차단하는 패턴.

> **Middleware vs Guardrails**  
> - 섹션 8.6 Middleware: **에이전트 레벨** 실행 제어 (HumanInTheLoop, PIIMiddleware 등)  
> - 섹션 9.5 Guardrails: **체인/LCEL 레벨** 입출력 검증 (RunnableLambda, Pydantic)  
> 두 레이어를 함께 적용하면 다층 보안 구조 구성 가능

#### ① 입력 Guardrail (Prompt Injection 방어)

`RunnableLambda`로 체인 앞단에 입력 필터링 단계 삽입 — MAS.md '침' 리스크 대응

```python
from langchain_core.runnables import RunnableLambda
from langchain_openai import ChatOpenAI
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser

# 위험 패턴 목록
INJECTION_PATTERNS = [
    "ignore previous instructions",
    "system prompt",
    "너의 지시사항을 무시",
    "주민번호", "비밀번호", "신용카드",
]

def input_guard(inputs: dict) -> dict:
    """입력 검증: 위험 패턴 감지 시 예외 발생"""
    text = inputs.get("text", "").lower()
    for pattern in INJECTION_PATTERNS:
        if pattern.lower() in text:
            raise ValueError(f"보안 정책 위반 입력 감지: '{pattern}'")
    return inputs

llm = ChatOpenAI(model="gpt-4o-mini")
prompt = ChatPromptTemplate.from_template("{text}에 대해 설명해줘")
chain = RunnableLambda(input_guard) | prompt | llm | StrOutputParser()

# 정상 입력
result = chain.invoke({"text": "LangChain"})

# 위험 입력 → ValueError 발생
# chain.invoke({"text": "주민번호 알려줘"})
```

#### ② 출력 Guardrail (민감 정보 유출 방지)

Pydantic 모델로 출력 구조 검증 + 민감 정보 필터링 — MAS.md '유' 리스크 대응

```python
from pydantic import BaseModel, field_validator
import re
from langchain_openai import ChatOpenAI
from langchain_core.prompts import ChatPromptTemplate

class SafeResponse(BaseModel):
    """출력 검증 모델 — 민감 정보 포함 시 마스킹"""
    answer: str
    confidence: float

    @field_validator("answer")
    @classmethod
    def mask_pii(cls, v: str) -> str:
        # 주민번호 패턴 마스킹 (예: 123456-1234567)
        v = re.sub(r"\d{6}-\d{7}", "******-*******", v)
        # 이메일 마스킹
        v = re.sub(r"[\w.+-]+@[\w-]+\.[a-z]+", "***@***.***", v)
        return v

llm = ChatOpenAI(model="gpt-4o-mini")
structured_llm = llm.with_structured_output(SafeResponse)

prompt = ChatPromptTemplate.from_template("다음 질문에 답해줘: {question}")
chain = prompt | structured_llm

result = chain.invoke({"question": "AI 보안이란?"})
print(result.answer)       # 민감 정보 자동 마스킹된 답변
print(result.confidence)   # 0.0 ~ 1.0
```

#### ③ Callbacks 방식 Guardrails

`BaseCallbackHandler`를 상속하여 LLM, Chain, Tool 등 모든 Runnable의 이벤트 훅에 Guardrails 로직 삽입 가능

**Callbacks vs Middleware 비교**

| 구분 | Callbacks | Middleware |
|------|-----------|------------|
| 적용 범위 | 모든 Runnable (LLM, Chain, Tool 등) | 에이전트 루프 전용 |
| 도입 시기 | LangChain 초기부터 | LangChain 1.0 |
| 사용 방식 | 이벤트 핸들러 상속 | 선언적 설정 |
| 적합 상황 | 세밀한 커스텀 로직, 범용 체인/LLM 훅 | 에이전트 루프 제어, 간단한 선언적 설정 |

```python
from langchain_core.callbacks import BaseCallbackHandler
from langchain_openai import ChatOpenAI

class GuardrailCallback(BaseCallbackHandler):
    """Callbacks 기반 다층 Guardrails"""

    def on_llm_start(self, serialized, prompts, **kwargs):
        """LLM 호출 전 - 입력 검증"""
        blocked_words = ["비밀번호", "주민번호", "ignore previous"]
        for prompt in prompts:
            for word in blocked_words:
                if word.lower() in prompt.lower():
                    raise ValueError(f"입력 차단: '{word}' 포함")

    def on_llm_end(self, response, **kwargs):
        """LLM 호출 후 - 출력 검증"""
        text = response.generations[0][0].text
        if len(text) > 5000:
            raise ValueError("응답 길이 초과 (5000자 제한)")

    def on_tool_start(self, serialized, input_str, **kwargs):
        """도구 호출 전 - 위험 명령 차단"""
        dangerous_commands = ["rm -rf", "DROP TABLE", "DELETE FROM"]
        for cmd in dangerous_commands:
            if cmd in input_str:
                raise ValueError(f"위험 명령 차단: '{cmd}'")

# 사용
llm = ChatOpenAI(model="gpt-4o-mini")
result = llm.invoke(
    "LangChain이란?",
    config={"callbacks": [GuardrailCallback()]}
)

# 체인에도 동일하게 적용 가능
chain = prompt | llm | parser
result = chain.invoke(
    {"text": "AI 보안"},
    config={"callbacks": [GuardrailCallback()]}
)
```
