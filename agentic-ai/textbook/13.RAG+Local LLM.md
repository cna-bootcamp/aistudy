# 1. WHY - 왜 Local LLM인가?

## 1.1 클라우드 API의 한계

GPT-4, Claude 등 클라우드 기반 LLM API는 강력하지만 실전 적용 시 핵심 문제가 발생함

| 한계점 | 설명 |
|--------|------|
| **데이터 보안** | 민감한 기업 데이터가 외부 서버로 전송됨. 의료/금융/법률 분야에서 규정 위반 가능 |
| **비용 증가** | 사용량에 비례하여 과금. 대규모 서비스에서 월 수천만원 비용 발생 가능 |
| **네트워크 의존** | 인터넷 연결 필수. 오프라인 환경이나 저지연이 필요한 상황에서 제약 |
| **서비스 종속** | API 정책 변경, 가격 인상, 서비스 중단 리스크 존재 |
| **커스터마이징 제한** | 파인튜닝, 모델 수정 등 자유로운 커스터마이징 불가 |

## 1.2 Local LLM이 제공하는 가치

Local LLM은 모델을 직접 보유하고 로컬 환경에서 실행하여 클라우드 API의 한계를 극복함

| 가치 | 설명 |
|------|------|
| **완전한 데이터 통제** | 모든 데이터가 로컬에서만 처리됨. 외부 전송 없이 프라이버시 보장 |
| **비용 예측 가능** | 초기 하드웨어 투자 후 추가 비용 없음. 대규모 사용 시 ROI 우수 |
| **오프라인 운영** | 인터넷 없이도 완전한 AI 기능 제공. 공장, 선박, 군사 환경 등 |
| **지연시간 최소화** | 네트워크 왕복 없이 즉각 응답. 실시간 애플리케이션에 적합 |
| **완전한 커스터마이징** | 파인튜닝, 프롬프트 최적화, 모델 수정 자유로움 |

## 1.4 클라우드 vs 로컬 선택 기준

| 기준 | 클라우드 API 선택 | Local LLM 선택 |
|------|------------------|----------------|
| **데이터 민감도** | 공개 가능한 데이터 | 기밀/개인정보 포함 |
| **사용량** | 소량/간헐적 사용 | 대량/지속적 사용 |
| **지연시간** | 수백ms 허용 | 수십ms 이하 필요 |
| **네트워크** | 안정적 인터넷 | 오프라인/불안정 환경 |
| **모델 성능** | 최고 성능 필요 | 적정 성능으로 충분 |
| **운영 역량** | 인프라 관리 어려움 | 자체 인프라 운영 가능 |

> **실무 팁**: 대부분의 경우 **하이브리드 접근**이 최적임.  
> 복잡한 추론은 클라우드 API, 반복적인 작업은 Local LLM으로 분리하여 비용과 성능을 최적화함.

## 2.1 런타임 비교

Local LLM을 실행하기 위한 주요 런타임(실행 환경)을 비교함

### Ollama

가장 쉽게 시작할 수 있는 로컬 LLM 런타임임

```bash
# 설치 (macOS/Linux)
curl -fsSL https://ollama.com/install.sh | sh

# 설치 (Windows)
# https://ollama.com/download 에서 설치 파일 다운로드

# 모델 실행
ollama run gemma3:4b
```

| 장점 | 단점 |
|------|------|
| 원클릭 설치 | 세밀한 설정 제한적 |
| 모델 자동 다운로드 | 지원 모델에 한정 |
| REST API 기본 제공 | 커스텀 모델 추가 복잡 |
| GPU 자동 감지 | |

> **실습 예제**
> - `hands-on/13.local-llm/agentic-rag` — Ollama + gemma3:12b 기반 Agentic RAG

### LlamaCpp

llama.cpp 기반으로 GGUF 모델을 직접 실행하는 방식임

> **GGUF (GPT-Generated Unified Format)**  
> llama.cpp 프로젝트에서 개발한 로컬 LLM 전용 모델 포맷임.  
> 양자화된 가중치와 메타데이터를 단일 파일로 저장하여 CPU/GPU에서 효율적으로 실행됨.  
> HuggingFace에서 원본 모델을 다운로드 후 변환하거나, 이미 변환된 GGUF 파일을 직접 사용함.  
> Ollama에서 제공하는 모델도 내부적으로 GGUF 포맷을 사용함.

```bash
# 설치
pip install llama-cpp-python

# GPU 지원 설치 (CUDA)
CMAKE_ARGS="-DGGML_CUDA=on" pip install llama-cpp-python --force-reinstall
```

| 장점 | 단점 |
|------|------|
| GGUF 모델 직접 실행 | 설치 복잡 (특히 GPU) |
| 세밀한 파라미터 제어 | 모델 직접 다운로드 필요 |
| 경량/저사양 최적화 | API 서버 별도 구성 |
| 다양한 양자화 지원 | |

### HuggingFace Transformers

PyTorch 기반의 가장 유연한 방식임

```bash
# 설치
pip install transformers torch accelerate
```

| 장점 | 단점 |
|------|------|
| 최신 모델 즉시 사용 | VRAM 사용량 높음 |
| 파인튜닝 용이 | 설정 복잡 |
| 풍부한 생태계 | 양자화 별도 설정 필요 |
| 연구/실험에 최적 | |

> **실습 예제**
> - `hands-on/05.stt/whisper` — Whisper Large V3 Turbo (STT)
> - `hands-on/06.tts/bark` — Suno Bark (TTS)
> - `hands-on/07.vlm/qwen3-vl` — Qwen3 Vision-Language (VLM)

OpenAI API와 호환되는 로컬 서버임

```bash
# Docker로 실행
docker run -p 8080:8080 localai/localai:latest
```

| 장점 | 단점 |
|------|------|
| OpenAI API 100% 호환 | Docker 필요 |
| 기존 코드 재사용 | 설정 복잡 |

## 2.3 양자화(Quantization) 기법

### 양자화란?

모델의 가중치(weights)를 더 적은 비트로 표현하여 메모리 사용량을 줄이는 기법임

```
원본 (FP16): 16비트 부동소수점
  → 7B 모델 = 약 14GB VRAM 필요
  
양자화 (Q4): 4비트 정수
  → 7B 모델 = 약 4GB VRAM 필요 (70% 절감)
```
  
> **비유**: 사진 압축과 유사함.  
> JPEG 품질을 100% → 80%로 낮추면 용량은 크게 줄지만 눈으로 보기엔 거의 차이 없음.

### GGUF 양자화 레벨

| 양자화 | 비트 | VRAM 절감 | 품질 손실 | 용도 |
|--------|------|-----------|-----------|------|
| **Q8_0** | 8bit | ~20% | 거의 없음 | 품질 우선, 서버 환경 |
| **Q6_K** | 6bit | ~35% | 매우 적음 | 품질-효율 균형 |
| **Q5_K_M** | 5bit | ~45% | 적음 | 권장 (품질 중시) |
| **Q4_K_M** | 4bit | ~50% | 소폭 | **실무 표준** (Ollama 기본) |
| **Q4_K_S** | 4bit | ~55% | 소폭 | 메모리 절약 |
| **Q3_K_M** | 3bit | ~60% | 체감됨 | 저사양 환경 |
| **Q2_K** | 2bit | ~70% | 상당함 | 극한 경량화, 테스트용 |

> **K, M, S 의미**  
> - **K**: K-quant 방식 (레이어별 최적화)
> - **M**: Medium (중간 품질)
> - **S**: Small (작은 크기 우선)

### 양자화 선택 가이드

| VRAM | 추천 양자화 |
|------|-------------|
| 24GB+ | Q8_0 또는 Q6_K |
| 12~16GB | Q5_K_M |
| 8~12GB | Q4_K_M (표준) |
| 6~8GB | Q4_K_S 또는 Q3_K_M |
| 4~6GB | Q3_K_S 또는 Q2_K |

# 4. LangChain 통합
  
## 4.1 Ollama 통합

가장 간단한 Local LLM 연동 방식임

**설치**:

```bash
pip install langchain-ollama
```

**사용 예시**:

```python
from langchain_ollama import ChatOllama

# 모델 초기화
model = ChatOllama(
    model="qwen3:8b",
    temperature=0.7,
)

# 단일 호출
response = model.invoke("Python에서 리스트 정렬하는 방법을 알려줘")
print(response.content)

# 스트리밍
for chunk in model.stream("RAG 시스템의 장점은?"):
    print(chunk.content, end="", flush=True)
```

**대화 이력 관리**:

```python
from langchain_core.messages import HumanMessage, AIMessage, SystemMessage

messages = [
    SystemMessage(content="당신은 친절한 AI 어시스턴트입니다."),
    HumanMessage(content="안녕하세요!"),
    AIMessage(content="안녕하세요! 무엇을 도와드릴까요?"),
    HumanMessage(content="오늘 날씨가 어때요?"),
]

response = model.invoke(messages)
```

**Cloud LLM 비교** (OpenAI, Anthropic):

동일한 코드 구조로 Cloud LLM 사용 가능

```python
# OpenAI (GPT-4)
from langchain_openai import ChatOpenAI

model = ChatOpenAI(
    model="gpt-4o",
    temperature=0.7,
    api_key="YOUR_OPENAI_API_KEY"  # 환경변수 OPENAI_API_KEY로 설정 가능
)

# Anthropic (Claude)
from langchain_anthropic import ChatAnthropic

model = ChatAnthropic(
    model="claude-3-5-sonnet-20241022",
    temperature=0.7,
    api_key="YOUR_ANTHROPIC_API_KEY"  # 환경변수 ANTHROPIC_API_KEY로 설정 가능
)

# 사용법은 Ollama와 동일
response = model.invoke("Python에서 리스트 정렬하는 방법을 알려줘")
```

**Local vs Cloud 비교**:

| 항목 | Local LLM (Ollama) | Cloud LLM (OpenAI/Claude) |
|------|-------------------|---------------------------|
| **비용** | 무료 (하드웨어 비용만) | 사용량 기반 과금 |
| **속도** | GPU 성능에 따라 다름 | 빠름 (최적화된 인프라) |
| **품질** | 모델 크기에 따라 다름 | 최상 (70B+ 모델) |
| **프라이버시** | 완전한 로컬 처리 | 데이터 외부 전송 |
| **인터넷** | 불필요 | 필수 |
| **설정** | 복잡 (GPU, VRAM 관리) | 간단 (API 키만) |
| **적합 용도** | 민감 데이터, 오프라인 | 프로토타이핑, 고품질 필요 시 |

| 파라미터 규모 | 대표 모델 | 적합 용도 | VRAM (Q4) |

## 5.2 양자화 (Quantization)

양자화 수준에 따라 메모리 사용량과 추론 속도가 극적으로 변화  
품질 대비 자원 효율의 핵심 레버

**양자화 포맷 비교**:

| 포맷 | 비트 | 메모리 | 속도 | 품질 손실 | 권장 용도 |
|------|------|--------|------|----------|----------|
| **FP16** | 16bit | 기준 | 기준 | 없음 | VRAM 충분시 |
| **Q8_0** | 8bit | 50% | +20% | 극미 | 고품질 필요 |
| **Q5_K_M** | 5bit | 35% | +40% | 미미 | 균형 |
| **Q4_K_M** | 4bit | 25% | +50% | 작음 | **권장** (일반) |
| **Q3_K_M** | 3bit | 20% | +60% | 중간 | VRAM 부족시 |
| **Q2_K** | 2bit | 15% | +70% | 큼 | 비권장 |

**실무 가이드**:
- **기본**: Q4_K_M (품질 90~95% 유지, 메모리 75% 절감)
- **고품질**: Q5_K_M 이상
- **극한 절약**: Q3_K_M (단, 품질 테스트 필수)

```bash
# Ollama에서 양자화 모델 다운로드

ollama pull qwen2.5:7b-instruct-q5_K_M
```

## 5.3 GPU 레이어 오프로딩

GPU 활용도에 따른 추론 속도 차이  
모델의 일부 레이어만 GPU에 올려 VRAM 부족 문제 해결

**LlamaCpp**:

```python
model = LlamaCpp(
    model_path="./model.gguf",
    n_gpu_layers=20,  # 20개 레이어만 GPU에
    # n_gpu_layers=-1  # 전체 레이어 GPU에 (VRAM 충분시)
)
```

**HuggingFace**:

```python
from transformers import AutoModelForCausalLM

model = AutoModelForCausalLM.from_pretrained(
    "Qwen/Qwen2.5-7B-Instruct",
    device_map="auto",  # 자동으로 GPU/CPU 분배
    torch_dtype=torch.float16,
)
```

**GPU 레이어 수 결정**:

| VRAM | 8B 모델 (Q4) | 14B 모델 (Q4) |

## 5.4 컨텍스트 윈도우 크기 설정

RAG에서 검색된 문서를 얼마나 넣을 수 있는지 직접 결정  
너무 크면 속도 저하, 너무 작으면 정보 부족

```python
# 컨텍스트 윈도우 설정
model = LlamaCpp(
    model_path="./model.gguf",
    n_ctx=4096,  # 4K 컨텍스트 (기본)
    # n_ctx=8192,  # 8K (더 긴 대화/문서)
    # n_ctx=32768, # 32K (VRAM 많이 필요)
)
```

| 컨텍스트 크기 | 용도 | VRAM 증가 | RAG Top-K |
|--------------|------|-----------|-----------|
| 2048 | 짧은 대화 | 기본 | 2~3개 |
| 4096 | 일반 RAG | +0.5~1GB | 3~5개 |
| 8192 | 문서 분석 | +1~2GB | 5~8개 |
| 32768 | 긴 문서 | +4~8GB | 10개+ |

**RAG 컨텍스트 계산**:
```
필요 컨텍스트 = (청크 크기 × Top-K) + 시스템 프롬프트 + 질문 + 응답 여유
예: (500 토큰 × 5개) + 300 + 100 + 500 = 3400 토큰 → n_ctx=4096
```

**청크 크기 전략**:

| 청크 크기 | 장점 | 단점 | 적합 용도 |
|----------|------|------|----------|
| **작음** (300~500) | 정확한 검색, 관련성 높음 | 컨텍스트 부족 가능 | FAQ, 짧은 문서 |

```python
# 검색 전략
retriever = vectorstore.as_retriever(
```

## 5.8 생성 파라미터 조정

```python
model = ChatOllama(
    model="qwen2.5:7b",
```

## B. 용어 정리

| 용어 | 설명 |
|------|------|
| **컨텍스트 윈도우** | LLM이 한 번에 처리할 수 있는 텍스트 길이. 128K = 약 A4 200~300페이지 |

| **토큰** | LLM이 처리하는 텍스트의 기본 단위. 한글 1자 ≈ 1~2토큰 |

## C. 트러블슈팅 가이드

| 문제 | 원인 | 해결 |
|------|------|------|
| CUDA out of memory | VRAM 부족 | 양자화 레벨 낮춤, n_gpu_layers 감소 |
| 모델 로딩 느림 | 디스크 I/O | SSD 사용, 모델 캐싱 |
| 응답 품질 저하 | 과도한 양자화 | Q4_K_M 이상 사용 |
| Ollama 연결 실패 | 서버 미실행 | `ollama serve` 실행 확인 |
| HF 모델 다운로드 실패 | 네트워크/인증 | HF_TOKEN 설정, 프록시 확인 |
