# 1. WHY - 왜 자연어 기반 Agent 개발인가?

기획자가 실제 개발에 앞서 프로토타이핑을 통해 검증하여 기획-개발 간 갭을 줄이고 재작업 비용을 최소화하기 위함

## 1.1 기존 개발 방식의 한계

기존 AI 에이전트 개발은 코드 중심으로 진행되어 다음과 같은 문제가 있음.

| 문제 | 설명 |
|------|------|
| 높은 진입 장벽 | 프레임워크(LangChain 등) 학습이 선행되어야 함 |
| 느린 프로토타이핑 | 코드 작성 → 테스트 → 수정 사이클이 길어 검증 지연 |
| 기획-개발 간 갭 | 기획자의 의도가 코드로 전환되는 과정에서 정보 손실 발생 |
| 반복 비용 | 워크플로우 변경 시마다 코드 수정 필요 |

```
[기존 방식 vs 자연어 기반 방식]

  기존 방식:
  기획서 작성 → 개발자 해석 → 코드 개발 → 테스트 → 수정
     ↑                                              │
     └──────────── 피드백 (느림, 정보 손실) ──────────┘

  자연어 기반 방식:
  자연어 입력 → DSL 자동 생성 → 시각적 프로토타이핑 → 검증 → 개발
     ↑                                                    │
     └──────────── 피드백 (빠름, 시각적 확인) ─────────────┘
```

## 1.2 자연어 → 프로토타입 → 프로덕션 패러다임

본 교재의 핵심 워크플로우는 **점진적 구체화** 방식임.
자연어로 시작하여 단계적으로 구체화하며, 각 단계에서 검증과 피드백을 반복함.

```
[점진적 구체화 워크플로우]

  자연어          DSL           프로토타입        코드
  (추상)    →   (구조화)   →   (시각화/검증)  →  (구체화)
  ──────────────────────────────────────────────────────→
                    점진적 구체화 방향
```
※ DSL(Domain Specific Language): 개발코드를 **도메인 전문가가 이해할 수 있도록 표현할 때 사용하는 언어**로 보통 YAML을 사용
  
**3가지 핵심 원리:**

| 원리 | 설명 |
|------|------|
| 자연어 입력 | 비즈니스 시나리오를 자연어로 입력하여 AI가 워크플로우 DSL을 자동 생성 |
| 도구 연계 | Dify Visual Builder에서 시각적 프로토타이핑 후 DSL Export하여 개발에 활용 |
| 반복 검증 | 프로토타입 검증 → 피드백 반영 → 코드 개발의 Iterative 사이클 |

## 1.3 왜 Dify인가?

Dify는 에이전틱 워크플로우를 구축하기 위한 오픈소스 플랫폼임.
"Do It For You"에서 유래한 이름처럼, 복잡한 에이전트 개발을 쉽게 만들어 줌.

| 특징 | 설명 |
|------|------|
| **직관적 UI** | 문서 없이도 바로 사용 가능한 낮은 학습 곡선 |
| **올인원 플랫폼** | 에이전트 + RAG + LLMOps를 하나의 도구에서 통합 관리 |
| **내장 모니터링** | 프롬프트 실험, 모델 비교, 성능 추적 대시보드 |
| **간결한 DSL** | YAML 기반으로 Claude Code와 원활한 연계 가능 |

```
[Dify 플랫폼 구성]

  ┌─────────────────────────────────────────────────┐
  │                  Dify Platform                   │
  │                                                  │
  │  ┌──────────┐  ┌──────────┐  ┌──────────────┐  │
  │  │  Studio   │  │ Knowledge│  │   LLMOps     │  │
  │  │(워크플로우│  │  (지식    │  │ (모니터링/   │  │
  │  │  편집기)  │  │  베이스)  │  │  프롬프트)   │  │
  │  └──────────┘  └──────────┘  └──────────────┘  │
  │                                                  │
  │  ┌──────────┐  ┌──────────┐  ┌──────────────┐  │
  │  │  Agent   │  │  Plugins  │  │  DSL Import  │  │
  │  │  (에이전 │  │ (플러그인)│  │  / Export    │  │
  │  │   트)    │  │           │  │  (YAML)      │  │
  │  └──────────┘  └──────────┘  └──────────────┘  │
  │                                                  │
  │  배포: API / 웹앱 / MCP 서버                     │
  └─────────────────────────────────────────────────┘
```

> Dify DSL은 YAML 기반으로 가독성이 높고,
> Claude Code가 전체 구조를 빠르게 이해하기에 최적임.

## 2.1 전체 워크플로우 개요

전체 개발 과정은 6단계로 구성되며, 각 단계에서 Human과 AI가 협업함.

```
[전체 Workflow]

  STEP 1       STEP 2       STEP 3       STEP 4       STEP 5       STEP 6
  비즈니스     Dify DSL     Dify         Knowledge    개발계획서    AI Agent
  시나리오 ───→ 자동생성 ───→ 프로토타입 ──→ Graph ────→ 작성 ─────→ 개발
  (Human+AI)  (AI)         (AI)         구축(AI)     (AI)         (AI)

  입력물:
  비즈니스 →  요구사항 →   DSL YAML →   FAQ 데이터 → 검증된 DSL → 개발
  문제         문서                                 + KG 인덱스   계획서

  산출물:
  요구사항 →  Dify    →   검증된   →   MS GraphRAG  → 개발     →  AI Agent
  문서        YAML DSL   DSL         KG 인덱스    계획서       코드

  ←── 피드백 루프: 프로토타입 결과에 따라 시나리오 수정 또는 DSL 재생성 ──→
```

| 단계 | 주체 | 입력 | 산출물 |
|------|------|------|--------|
| STEP 1 | Human | 비즈니스 문제 | 요구사항 문서 (자연어) |
| STEP 2 | Claude Code | 요구사항 문서 | Dify YAML DSL |
| STEP 3 | Human + Dify | DSL 파일 | 검증된 프로토타입 + 수정된 DSL |
| STEP 4 | Claude Code | FAQ 데이터 | MS GraphRAG Knowledge Graph 인덱스 |
| STEP 5 | Claude Code | 검증된 DSL + KG 인덱스 | 개발 계획서 |
| STEP 6 | Claude Code | 개발 계획서 + DSL + KG | AI Agent 코드 |

## 2.2 STEP 1: 비즈니스 시나리오 & 요구사항 정의

**주체:** Human → Claude Code

### 요구사항 프롬프트 템플릿

아래 8개 섹션을 순서대로 작성하여 Claude Code에 입력하면,
구조화된 Dify Workflow DSL이 자동 생성됨.

| 섹션 | 작성 내용 | 필수 |
|------|-----------|:----:|
| **1. 서비스 개요** | 서비스명, 유형(Workflow/Chatflow/Agent), 목적, 대상 사용자 | O |
| **2. 사용자 시나리오** | As-Is(현재) → To-Be(목표), 기대 효과 | O |
| **3. 에이전트 역할 및 행동** | 역할 정의, 단계별 기대 행동, 예외 처리 | O |
| **4. 워크플로우 설계** | 입력/출력 정의, 분기 조건, 반복 처리 | △ |
| **5. 외부 도구 및 데이터 소스** | 도구/API 목록, Knowledge Base, 외부 API 연동 | O |
| **6. 프롬프트 가이드** | 시스템 프롬프트, 출력 형식(언어, 형식, 길이) | △ |
| **7. 비기능 요구사항** | 성능, 정확도, 보안, 모니터링 | △ |
| **8. 테스트 시나리오** | 정상/예외/성능 시나리오 | △ |

> O = 필수, △ = 권장 (작성할수록 DSL 품질 향상)

#### 핵심 섹션 작성 가이드

**섹션 1. 서비스 개요** - 에이전트의 정체성을 정의

```
서비스명: {서비스 이름}
서비스 유형: {Workflow / Chatflow / Agent}
서비스 목적: {이 에이전트가 해결하려는 핵심 문제}
대상 사용자: {주요 사용자 그룹}
```

**섹션 3. 에이전트 역할 및 행동** - DSL 노드 구조를 결정하는 가장 중요한 섹션

```
사용자가 {트리거 조건}하면:

1) {첫 번째 동작}
   - 입력: {필요한 데이터}
   - 처리: {수행할 작업}
   - 출력: {결과물}

2) {두 번째 동작}
   - 조건: {이 단계로 진행하는 조건}
   - 처리: {수행할 작업}
   - 출력: {결과물}

예외 처리:
- {예외 상황}: {대응 방법}
- 기본 폴백: {모든 예외 시 기본 동작}
```

**섹션 5. 외부 도구 및 데이터 소스** - 워크플로우의 실행 능력을 결정

```
도구 목록:
- {도구명}: {용도} (예: Knowledge Base - FAQ 검색)
- {도구명}: {용도} (예: HTTP Request - 외부 API 호출)

지식 베이스 (해당 시):
- 데이터 소스: {문서 유형}
- 검색 방식: {키워드 / 시맨틱 / 하이브리드}
```


### 예시) 고객 상담 에이전트

아래는 템플릿의 핵심 섹션만 작성한 최소 예시임.

```
[서비스 개요]
서비스명: 스마트 고객 상담 에이전트
서비스 유형: Chatflow
서비스 목적: 고객 문의에 대해 FAQ 기반 자동 응답 및 상담원 에스컬레이션
대상 사용자: 제품 구매 고객, CS 상담원

[에이전트 역할 및 행동]
고객이 제품에 대해 질문하면:
1) FAQ 지식베이스에서 검색하고
2) 관련 답변이 없으면 상담원 연결
3) 상담 내역을 자동 요약하여 저장

예외 처리:
- API 호출 실패: 재시도 후 상담원 연결
- 지식베이스 비어있음: 상담원 직접 연결

[외부 도구]
- Knowledge Base: FAQ 문서 시맨틱 검색
- Slack API: 상담원 채널 알림 전송

[비기능 요구사항]
- 정확도 목표: 90% 이상
- 응답 시간: 3초 이내
```

> **Tip:** 구체적인 시나리오와 기대 행동을 명시할수록
> Claude Code가 생성하는 DSL의 품질이 높아짐.

> 노드 구조, 분기 조건, 에러 핸들링이 정확하게 생성됨.

## 2.3 STEP 2: Dify Workflow DSL 자동 생성

**주체:** Claude Code → Dify YAML DSL

Claude Code가 자연어 요구사항을 분석하여 Dify DSL을 자동으로 생성함.

### DSL 생성 프로세스

```
[DSL 자동 생성 흐름]

  ┌───────────────────────────────────────────────┐
  │              Claude Code 처리 과정              │
  │                                                │
  │  ┌──────────┐    ┌──────────┐    ┌──────────┐ │
  │  │ 입력 분석 │───→│ DSL 구성 │───→│  출력물  │ │
  │  └──────────┘    └──────────┘    └──────────┘ │
  │                                                │
  │  · 자연어 요구   · 노드(Node)    · YAML DSL   │
  │    사항 파싱       정의            파일        │
  │  · 에이전트 역할 · 엣지(Edge)    · 워크플로우  │
  │    식별            연결            구조 설명서 │
  │  · 필요 도구     · 변수/파라미터 · 프롬프트    │
  │    매핑            설정            초안        │
  │  · 데이터 흐름   · 프롬프트      · 테스트      │
  │    추론            템플릿 생성     시나리오    │
  └───────────────────────────────────────────────┘
```

### Dify DSL 구조

Dify DSL은 YAML 기반의 도메인 특화 언어로,
모든 Dify 앱을 코드로 표현 가능함.

```yaml
# Dify DSL 기본 구조 예시
app:
  name: "고객 상담 에이전트"
  mode: "workflow"

workflow:
  nodes:
    - id: "start"
      type: "user-input"
      data:
        variables:
          - name: "query"
            type: "string"
            required: true

    - id: "knowledge_search"
      type: "knowledge-retrieval"
      data:
        dataset_ids: ["faq_dataset"]
        query: "{{#start.query#}}"

    - id: "classifier"
      type: "question-classifier"
      data:
        model:
          provider: "openai"
          name: "gpt-4o-mini"
        classes:
          - name: "FAQ 답변 가능"
          - name: "상담원 연결 필요"

    - id: "llm_answer"
      type: "llm"
      data:
        model:
          provider: "openai"
          name: "gpt-4o"
        prompt: "검색 결과를 바탕으로 답변하세요..."

    - id: "output"
      type: "output"
      data:
        outputs:
          - name: "answer"
            value: "{{#llm_answer.text#}}"

  edges:
    - source: "start"
      target: "knowledge_search"
    - source: "knowledge_search"
      target: "classifier"
    - source: "classifier"
      target: "llm_answer"
      condition: "FAQ 답변 가능"
    - source: "llm_answer"
      target: "output"
```

> Dify DSL 파일에서 직접 앱을 생성할 수 있어,
> 다른 Dify 인스턴스로의 이식 및 공유가 용이함.

**DSL Import/Export 상세:**

| 항목 | 설명 |
|------|------|
| 내보내기 위치 | Studio 페이지 또는 Orchestration 인터페이스에서 Export |
| 포함 항목 | 설정, 워크플로우 설정, 모델 매개변수, 지식 베이스 연결 |
| 제외 항목 | API 키, 지식 베이스 콘텐츠, 분석 데이터 |
| 보안 | 비밀 환경 변수 포함 여부를 사용자에게 확인 프롬프트 표시 |
| 가져오기 | YAML 파일 업로드 시 시스템이 버전 호환성을 자동 검증 |

**Dify 버전 관리:**

Dify는 워크플로우의 변경 이력을 체계적으로 관리함.

| 버전 상태 | 설명 |
|-----------|------|
| **Current Draft** | 사용자가 수정하는 활성 작업 버전 |
| **Latest Version** | 최종 사용자가 현재 액세스하는 게시된 버전 |
| **Previous Versions** | 참조용으로 사용 가능한 이전 게시 버전 |

게시(Publish) 시 드래프트가 새로운 Latest Version으로 변환되며,
지속적인 작업을 위한 새로운 드래프트가 자동 생성됨.
버전 히스토리에서 "all versions" 또는 "only yours"로 필터링 가능함.

[Dify 프로토타이핑 사이클]

### 주요 편집 항목

Dify Visual Builder에서 조정 가능한 주요 항목:

| 영역 | 편집 항목 |
|------|-----------|
| 워크플로우 구조 | 노드 추가/삭제, 연결(Edge) 수정, 분기 조건 변경 |
| 프롬프트 | LLM 노드의 시스템/사용자 프롬프트 튜닝 |
| 변수 | 입출력 변수, 환경 변수, 대화 변수 설정 |
| 도구 연동 | 외부 API, Knowledge Base, 플러그인 연결 |
| 모델 설정 | LLM 제공자, 모델명, 온도(temperature) 등 파라미터 |

**Dify 내장 디버그 도구:**

Dify는 프로토타이핑과 검증을 위한 강력한 디버그 도구를 내장하고 있음.

| 도구 | 설명 |
|------|------|
| **단일 노드 실행** | 전체 워크플로우를 실행하지 않고 개별 노드를 격리된 환경에서 테스트 |
| **변수 인스펙터** | 워크플로우를 통해 이동하는 모든 데이터를 실시간으로 표시 |
| **실행 이력** | 애플리케이션/노드 레벨의 실행 로그를 Result, Detail, Tracing 섹션으로 확인 |

```
[디버그 워크플로우]

  ┌──────────────────────────────────────────────────────────┐
  │                    Dify 디버그 도구                       │
  │                                                          │
  │  ┌────────────────┐  ┌──────────────┐  ┌─────────────┐ │
  │  │  단일 노드 실행  │  │ 변수 인스펙터 │  │  실행 이력   │ │
  │  │                │  │              │  │             │ │
  │  │ · 노드 선택     │  │ · 입출력 표시 │  │ · Result    │ │
  │  │ · 테스트 데이터  │  │ · 값 편집     │  │ · Detail    │ │
  │  │   입력          │  │ · 초기화      │  │ · Tracing   │ │
  │  │ · 독립 실행     │  │              │  │             │ │
  │  │ · 결과 즉시확인  │  │              │  │             │ │
  │  └────────────────┘  └──────────────┘  └─────────────┘ │
  └──────────────────────────────────────────────────────────┘
```

**단일 노드 실행** 절차:
1. 워크플로우 캔버스에서 테스트할 노드를 선택
2. 설정 패널을 통해 테스트 데이터를 입력
3. 노드를 독립적으로 실행하여 결과를 즉시 확인
4. "Last run"을 클릭하여 입력값, 출력값, 실행 시간, 오류 메시지 등 상세 확인

**변수 인스펙터** 기능:
- 노드 실행 완료 후 출력 변수가 하단 인스펙터 패널에 표시됨
- 변수 값을 클릭하여 수정 가능하며, 다운스트림 노드에서 편집된 값을 사용함
- 되돌리기 아이콘으로 개별 변수 초기화, "Reset all"로 전체 초기화 가능

## 3.4 Knowledge Base와 RAG

Dify의 지식 베이스는 RAG(Retrieval-Augmented Generation)를 활용하여
LLM의 응답 품질을 향상시킴.

**RAG 프로세스:**

```
[RAG 3단계 프로세스]

  ┌──────────┐    ┌──────────────┐    ┌──────────────┐
  │ 1. 검색   │───→│ 2. 컨텍스트  │───→│ 3. 응답 생성  │
  │           │    │    결합       │    │              │
  │ 지식 베이 │    │ 검색 결과 +  │    │ LLM이 컨텍스 │
  │ 스에서 관 │    │ 사용자 쿼리  │    │ 트를 사용하여 │
  │ 련 정보   │    │ 를 결합하여  │    │ 최적화된     │
  │ 검색      │    │ 보조 컨텍스  │    │ 응답 생성    │
  │           │    │ 트 생성      │    │              │
  └──────────┘    └──────────────┘    └──────────────┘
```

**RAG의 장점:**

| 장점 | 설명 |
|------|------|
| 응답 정확도 향상 | 관련성 높은 정보에 접근하여 더 정확한 응답 생성 |
| 도메인 지식 통합 | 특정 도메인의 지식을 LLM에 통합하여 전문적 응답 가능 |
| 사전 학습 의존도 감소 | 최신 정보나 사내 데이터 등 사전 학습에 없는 정보 활용 가능 |

**워크플로우에서 Knowledge Base 활용:**

1. Dify 워크스페이스에서 지식 베이스를 생성하고 문서를 업로드
2. 워크플로우에 **Knowledge Retrieval** 노드를 추가
3. 검색 결과를 **LLM** 노드의 컨텍스트로 전달
4. LLM이 검색된 정보를 기반으로 답변을 생성

> **참고:** 본 실습에서는 Dify 내장 Knowledge Base 외에
> MS GraphRAG를 활용한 Knowledge Graph 검색도 활용함.

## 3.5 배포 옵션 상세

Dify에서 완성된 워크플로우를 프로덕션으로 배포하는 4가지 방식.

[Dify 배포 옵션]

  │              검증된 Dify 워크플로우                    │
  └──┬──────────┬──────────┬──────────┬─────────────────┘
     │          │          │          │
     ▼          ▼          ▼          ▼
  ┌──────┐  ┌──────┐  ┌──────┐  ┌──────────┐
  │ 웹앱  │  │ API  │  │ 임베딩│  │MCP 서버  │
  │      │  │      │  │      │  │          │
  │즉시   │  │백엔드│  │채팅   │  │Claude    │
  │공유   │  │통합  │  │위젯  │  │Desktop   │
  │링크   │  │      │  │      │  │Cursor 등 │
  └──────┘  └──────┘  └──────┘  └──────────┘
```

| 배포 방식 | 장점 | 적합 케이스 |
|-----------|------|-------------|
| **웹 애플리케이션** | 설치 없이 즉시 공유, 가장 빠른 배포 | 내부 도구, 데모, MVP |
| **API** | 완전한 UX/데이터 제어, 기존 제품에 AI 임베드 | SaaS 통합, 커스텀 프론트엔드 |
| **웹사이트 임베딩** | 모든 웹 플랫폼 호환, 채팅 위젯 또는 iframe | 고객 지원, 랜딩 페이지 |
| **MCP 서버** | 개발 도구 연결, 전문 환경 내 접근성 확장 | 개발자 도구, AI 어시스턴트 연동 |

**API 배포 워크플로우:**
1. Dify Studio에서 앱 구축
2. 보안 자격증명(API 키) 생성
3. 애플리케이션에서 API 호출
4. 사용자가 커스텀 인터페이스를 통해 상호작용하는 동안 Dify가 AI 처리 담당

| **Average User Interactions** | 평균 사용자 상호작용 횟수 |

**로그 기능:**

| 기능 | 설명 |
|------|------|

| 사용자 평가 | 사용자가 제공한 평가 또는 코멘트 수집 |
| 패턴 식별 | 불량 응답, 느린 성능, 과도한 토큰 사용 감지 |

**실행 이력:**

각 워크플로우 실행은 3가지 섹션으로 상세 로그가 기록됨:

| 섹션 | 내용 |
|------|------|
| **Result** | 최종 실행 결과 |
| **Detail** | 입출력, 실행 시간, 파라미터 등 상세 정보 |
| **Tracing** | 각 노드별 실행 추적, 디버깅용 상세 흐름 |

> 모니터링 데이터를 활용하여 프롬프트 최적화, 모델 비교,

## 3.2 실습: 고객 상담 에이전트 구축

실습 전체 흐름:

```
STEP 1: 시나리오 작성 (/abra:scenario)
  ↓
STEP 2: DSL 생성 (/abra:dsl-generate)
  ↓

  ↓

  ↓

### STEP 1 실습: 시나리오 작성

abra 플러그인으로 비즈니스 시나리오를 자동 생성함.

```bash
/abra:scenario
```

실행 시 abra가 대화형으로 서비스 목적, 시나리오 갯수 등을 질문함.

```
실행 예시:

→ 서비스 목적 입력: "고객이 제품에 대해 질문하면 FAQ 지식베이스에서
  자동으로 답변을 찾아 응답하고, 답변이 없는 경우 상담원에게 연결하는 에이전트"
→ 시나리오 후보 3개 자동 생성
→ 각 시나리오의 관점·서비스명·핵심가치 비교표 제시
→ 사용자가 하나를 선택
```

| 항목 | 내용 |
|------|------|
| 입력 | 서비스 목적 키워드 또는 도메인 |
| 출력 | 구조화된 시나리오 문서 (`output/scenario.md`) |
| 확인 포인트 | 에이전트 역할, 외부 도구, 비기능 요구사항 항목 검토 |

### STEP 2 실습: DSL 생성

STEP 1에서 확정된 시나리오를 기반으로 Dify Workflow DSL을 자동 생성함.

```bash
/abra:dsl-generate
```

| 항목 | 내용 |
|------|------|
| 입력 | 확정된 시나리오 (자동 연계) |
| 출력 | Dify Workflow DSL YAML 파일 (`output/{app-name}.dsl.yaml`) |
| 확인 포인트 | 노드 구조, 엣지 연결, 변수 참조 정확성 |

### STEP 3 실습: Dify 프로토타이핑
#### 초기 프로토타이핑 생성  
생성된 DSL을 Dify에 자동 Import → Publish → Run 하여 프로토타이핑 수행함.

```bash
/abra:prototype
```

프로세스:
1. DSL 사전 검증 (`validate_dsl`)
2. Dify에 Import → Publish → Run (테스트 실행)
3. 에러 발생 시 자동 수정 루프 (에러 분석 → DSL 수정 → 재배포 → 재실행)
4. 성공 시 Export로 검증된 DSL 확보

| 항목 | 내용 |
|------|------|
| 입력 | 생성된 DSL YAML (자동 연계) |
| 출력 | Dify에 배포된 워크플로우 + 테스트 실행 결과 |
| 확인 포인트 | Dify Studio에서 워크플로우 시각적 확인, 테스트 결과 검증 |

> 자동 수정 루프가 해결하지 못하는 경우
> Dify Studio에서 수동 편집 후 `/abra:prototype` 재실행

#### 프로토타이핑 수정 
프롬프팅을 통해 DSL을 수정함.   
AI가 자동으로 DSL 수정 -> Dify에 Import -> 테스트를 수행함.   
수정된 프로토타입을 확인하여 완료할 때까지 수정 작업 수행  

예시)  
```
/abra:prototype 
검색된 결과와 질문과의 관련도와 정확도를 평가하여 90점 이하면  
질문 프롬프트를 수정하여 재검색 하도록 합니다.  
최대 3번까지 반복하도록 합니다.   
```

## 3.3 Dify 주요 노드 참조

워크플로우 설계 시 자주 사용하는 Dify 노드:

| 노드 | 설명 | 용도 |
|------|------|------|
| **User Input** | 사용자 입력 변수를 정의하는 시작 노드 | 워크플로우 시작점 |
| **LLM** | 대규모 언어 모델을 호출하여 텍스트 생성 | 답변 생성, 요약, 분류 |
| **Knowledge Retrieval** | 지식 베이스에서 관련 정보 검색 | RAG 패턴 구현 |
| **Agent** | 자율적으로 도구를 선택하고 실행하는 에이전트 | 복잡한 의사결정 |
| **Question Classifier** | 사용자 질문을 카테고리별로 분류 | 분기 처리 |
| **If-Else** | 조건에 따라 워크플로우 분기 | 조건부 로직 |
| **Code** | Python/JavaScript 코드 실행 | 데이터 변환, API 호출 |
| **HTTP Request** | 외부 API 호출 | 외부 서비스 연동 |
| **Iteration** | 배열 데이터에 대해 동일 작업 반복 | 대량 데이터 처리 |
| **Template** | Jinja2 템플릿으로 텍스트 변환 | 출력 포맷팅 |
| **Answer** | Chatflow에서 스트리밍 응답 출력 | 대화형 응답 |
| **Output** | Workflow의 최종 결과 출력 | 결과 반환 |

### Agent 노드 상세

Agent 노드는 LLM이 도구를 자율적으로 선택하고 실행하는 핵심 노드임.

**에이전트 전략:**

| 전략 | 설명 |
|------|------|
| **Function Calling** | LLM의 네이티브 기능 호출 방식, 강력한 모델에서 최적 |
| **ReAct** | Reason + Act 패턴으로 명시적 추론을 통해 모델을 안내 |

**Agent 노드 구성 요소:**

| 구성 요소 | 설명 |
|-----------|------|
| 도구 설정 | 에이전트가 사용할 도구의 인증 자격증명, 기능, 사용 사례 설명 |
| 지시사항 | 에이전트의 역할을 자연어와 업스트림 변수 참조로 정의 |
| 실행 제어 | 최대 반복 횟수 설정으로 무한 루프 방지 |
| 메모리 관리 | TokenBufferMemory로 과거 메시지 보존과 토큰 소비 균형 |

```
[Agent 노드 동작 흐름]

  사용자 입력 ──→ Agent 노드 ──→ 도구 선택 ──→ 도구 실행
                    │                              │
                    │    ← 결과 반환 ← ─────────────┘
                    │
                    ├──→ 추가 도구 필요? ──→ 반복
                    │
                    └──→ 최종 응답 생성
```

## Dify 앱 유형 비교

| 유형 | 설명 | 시작 방식 | 배포 옵션 |
|------|------|-----------|-----------|
| **Workflow** | 단일 턴 작업 처리, 일괄 실행 가능 | User Input 또는 Trigger | API, 웹앱, MCP 서버 |
| **Chatflow** | 대화의 매 턴마다 트리거되는 워크플로우 | User Input만 가능 | API, 웹앱 |
| **Chatbot** | 간단한 대화형 앱 (레거시) | - | API, 웹앱 |
| **Agent** | 자율적 도구 활용 앱 (레거시) | - | API, 웹앱 |
| **Text Generator** | 텍스트 생성 앱 (레거시) | - | API, 웹앱 |

> Workflow는 Dify의 모든 앱 유형의 기반이 됨.
> 본 교재에서는 주로 Workflow 유형을 사용함.
