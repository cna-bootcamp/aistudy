# 1. WHY - 왜 GraphRAG인가?

---

## 1.1 기존 RAG의 한계

기존 Vector RAG는 청크 기반 유사도 검색으로 동작하며,  
복잡한 질문에서 구조적 한계가 발생함

### 청크 기반 검색의 문맥 단절 (멀티홉 추론 실패)

```
[원본 문서]
"이병철은 삼성그룹을 창업했다. 이건희는 이병철의 아들이다.
 이재용은 이건희의 아들이다."

[청크 분할 후]
청크 1: "이병철은 삼성그룹을 창업했다."
청크 2: "이건희는 이병철의 아들이다."
청크 3: "이재용은 이건희의 아들이다."

[문제] 질문: "이재용의 조부는 누구인가?"
→ "이재용"이 있는 청크 3만 검색됨
→ 청크 3: "이재용은 이건희의 아들" (아버지 정보만 획득)
→ 청크 2: "이건희는 이병철의 아들" (검색 안 됨 - "이재용" 없음)
→ 2단계 관계(조부) 추론 실패
```

### 멀티홉 질문 처리 실패

| 질문 유형 | 예시 | Vector RAG |
|----------|------|------------|
| **단일 팩트** | "삼성전자 설립연도는?" | 처리 가능 |
| **관계 추론** | "이재용의 조부는 누구인가?" | 처리 곤란 |
| **집계/요약** | "문서에 등장하는 모든 기업은?" | 처리 불가 |
| **비교 분석** | "삼성과 SK의 경영 스타일 차이는?" | 처리 불가 |

### Vector RAG vs GraphRAG

```
Vector RAG:  "이 청크가 질문과 얼마나 유사한가?" (유사도 기반)
GraphRAG:    "이 엔티티가 다른 엔티티와 어떤 관계인가?" (관계 기반)
```

# 2. HOW - 어떻게 동작하는가?

---

## 2.1 핵심 아키텍처

GraphRAG는 **Knowledge Graph 구축**과 **그래프 기반 검색**의 두 단계로 구성됨.

### 인덱싱 단계

| 단계 | 작업 | 설명 | 
|------|------|------|
| Load(불) | **문서로드** | 원본 문서를 변환하고 전처리 수행 |
| Split(쪼) | **텍스트 분할** | 원본 문서를 분석 단위(청크)로 분할 |
| Embedding(임) | **엔티티 추출** | 사람, 조직, 장소, 개념 등 핵심 개체 식별 |
|  | **관계 추출** | 엔티티 간 관계(소속, 협력, 소유 등) 식별 |
|  | **그래프 구축** | 엔티티(노드) + 관계(엣지)로 Knowledge Graph 구성 |
|  | **사전요약** | 엔티티를 커뮤니티로 그룹화하고 요약 생성 (커뮤니티 계층 요약은 MS GraphRAG 고유) |
|  | **임베딩** | 엔티티, 청크, 커뮤니티 요약을 벡터로 변환 (관계는 선택적) |
|  | **저장** | KG 저장소와 벡터 저장소에 저장 |

> 사전요약 수행  
> - MS GraphRAG는 필수 수행
> - LlamaIndex는 설정에 따라 스킵 가능   
  
> KG저장소와 벡터 저장소는 보통 분리(Neo4J는 통합)
  
### 검색 단계

질문 유형에 따라 세 가지 검색 방식 활용:  
- **Local Search**: 특정 엔티티 중심의 미시적 질문 (예: "스티브 잡스가 창업한 회사는?")
- **Global Search**: 문서 전체를 조망하는 거시적 질문 (예: "주요 테마는 무엇인가?")
- **Hybrid Search**: 미시적·거시적 요소를 결합한 복합 질문

#### Local Search 단계

| 단계 | 작업 | 설명 |
|------|------|------|
| Query(문) | **질문 분석** | 사용자 질문에서 핵심 엔티티/키워드 식별 |
| Retrieve(탐) | **진입점 탐색** | 벡터 검색으로 질문과 관련된 엔티티 또는 텍스트를 찾아 그래프 탐색의 시작점 확보 |
|  | **그래프 탐색** | 진입점에서 관련 엔티티와 관계를 그래프로 확장 탐색 |
|  | **컨텍스트 수집** | 탐색 결과에서 관련 텍스트/요약 수집 |
| Generate(생) | **답변 생성** | 수집된 컨텍스트를 기반으로 LLM이 답변 생성 |

#### Global Search 단계

프레임워크별로 Global Search를 구현하는 방식이 다름:

##### 방식 1: 커뮤니티 요약 (MS GraphRAG, LlamaIndex)

| 단계 | 작업 | 설명 |
|------|------|------|
| Query(문) | **질문 분석** | 광범위한 주제/테마 식별 |
| Retrieve(탐) | **커뮤니티 선택** | 사전 생성된 커뮤니티 요약에서 질문 관련 커뮤니티 탐색 |
| Retrieve(탐) | **요약 종합** | 선택된 커뮤니티의 요약 리포트 수집 및 통합 |
| Generate(생) | **답변 생성** | 통합된 요약 기반으로 전체 조망 답변 생성 |

> 인덱싱 시 커뮤니티 탐지(Leiden) + LLM 요약 생성. 벡터 검색 없이 사전 생성된 요약 활용.

##### 방식 2: 키워드 확장 (LightRAG)

| 단계 | 작업 | 설명 |
|------|------|------|
| Query(문) | **질문 분석** | 광범위한 주제/테마 식별 |
| Retrieve(탐) | **키워드 확장** | High-level 키워드로 확장하여 넓은 범위 커버 |
| Retrieve(탐) | **관계 탐색** | 관계 유사도 검색으로 넓은 범위의 엔티티·관계 탐색 |
| Retrieve(탐) | **컨텍스트 수집** | 탐색된 관계와 엔티티에서 정보 수집 |
| Generate(생) | **답변 생성** | 수집된 컨텍스트 기반 답변 생성 |

> 커뮤니티 탐지 없이 쿼리 시점에 키워드 확장으로 동적 탐색. 비용 효율적.

##### 방식 3: 쿼리 집계 (LangChain + Neo4j, Neo4j GraphRAG)

| 단계 | 작업 | 설명 |
|------|------|------|
| Query(문) | **질문 분석** | 광범위한 주제/테마 식별 |
| Retrieve(탐) | **Cypher 쿼리 생성** | 그래프 전체 집계/패턴 매칭을 위한 Cypher 쿼리 작성 |
| Retrieve(탐) | **그래프 집계** | Cypher 쿼리 실행으로 그래프 전체 정보 수집 |
| Generate(생) | **답변 생성** | 집계 결과 기반 답변 생성 |

> Cypher 쿼리로 그래프 전체를 직접 집계. Global Search 품질은 제한적이나 유연한 쿼리 가능.

#### Hybrid Search 단계

| 단계 | 작업 | 설명 |
|------|------|------|
| Query(문) | **질문 분석** | 미시적 요소(특정 엔티티)와 거시적 요소(전체 테마) 모두 식별 |
| Retrieve(탐) | **Local 검색** | 진입점 탐색 → 그래프 탐색으로 구체적 정보 수집 |
| Retrieve(탐) | **Global 검색** | 제품에 따라 커뮤니티 요약/High-level 키워드/Cypher 쿼리로 검색하여 광범위한 맥락 정보 수집 |
| Retrieve(탐) | **결과 통합** | Local 컨텍스트(세부 정보) + Global 컨텍스트(전체 맥락) 결합 |
| Generate(생) | **답변 생성** | 통합된 컨텍스트로 구체성과 포괄성을 갖춘 답변 생성 |

### 프레임워크 비교

| 구분 | 항목 | MS GraphRAG | LlamaIndex | LangChain + Neo4j | Neo4j GraphRAG | LightRAG |
|------|------|-------------|------------|-------------------|----------------|----------|
| 인덱싱 | **인덱싱 단계** | 청킹 → 추출 → KG 저장 → **사전요약** → 벡터 임베딩 | 청킹 → 추출 → KG 저장 → **(선택)사전요약** → 벡터 임베딩 | 청킹 → 추출 → KG 저장 → 벡터 임베딩 | 청킹 → 추출 → KG 저장 → 벡터 임베딩 | 청킹 → 추출 → KG 저장 → 벡터 임베딩 |
| | **증분 업데이트** | 지원 (전체 재인덱싱 권장) | 지원 (Neo4j 활용) | 지원 (Neo4j MERGE) | 지원 (MERGE 연산) | 지원 (문서 삭제 후 재삽입) |
| | **Graph/Vector 저장소** | 분리 (Parquet + Vector DB) | 분리 또는 통합 선택 | 통합(Neo4j)이 기본<br>Vector DB분리 가능 | **통합** (Neo4j 내장) | 분리 (Graph + Vector DB) |
| 검색 | **Local Search**<br>- 벡터 검색 | 엔티티 벡터 검색 | 벡터 유사도 검색 | 벡터 유사도 검색 | 벡터 유사도 검색 | 키워드 추출 →<br>엔티티 벡터 검색 |
| | **Local Search**<br>- 그래프 탐색 | 주변 엔티티/관계<br>자동 탐색 | 그래프 API 탐색 | Cypher 쿼리 탐색 | Cypher 쿼리 탐색 | 관계 기반<br>자동 탐색 |
| | **Global Search** | 커뮤니티 요약 종합 (벡터 미사용) | 커뮤니티 요약 (Leiden + LLM) | Cypher 집계 쿼리 (제한적) | Cypher 집계 쿼리 (제한적) | 추상화/일반화된 키워드 → 관계 유사도 검색 |
| | **Hybrid Search** | DRIFT<br>Local + Global 결합 | Local + Global 결합 | Local + Global 결합 | Local + Global 결합 | Mix 모드<br>Local + Global 통합 |

> **참고**: 비교 정보는 각 프레임워크 공식 문서 기준 (2025~2026년)

> **Local Search**: 특정 엔티티나 개념을 중심으로 주변 정보를 검색. "X란 무엇인가?" 같은 구체적 질문에 적합  
> **Global Search**: 문서 전체를 조망하는 검색. "주요 테마는?" 같은 광범위한 질문에 적합  
> **Hybrid Search**: Local + Global을 결합하여 구체성과 포괄성을 동시에 확보  
  
> **글로벌 질문 답변**: "전체 문서의 주요 테마는?",  
> "이 분야의 핵심 개념 간 관계는?" 등  
> 특정 엔티티가 아닌 **전체를 조망하는 질문**에 답변하는 능력.  
> MS GraphRAG의 Global Search에 국한되지 않으며,  
> 각 프레임워크가 고유 방식으로 달성함.  
>
> | 방식 | 프레임워크 | 메커니즘 |  
> |------|-----------|----------|  
> | **사전 요약** | MS GraphRAG, LlamaIndex | 인덱싱 시 커뮤니티 탐지(Leiden) + LLM 요약 생성 |  
> | **키워드 확장** | LightRAG | 쿼리 시 High-level 키워드로 넓은 범위 탐색 |  
> | **쿼리 집계** | Neo4j 계열 | Cypher 쿼리로 그래프 전체 집계/패턴 매칭 |

> - **커뮤니티 탐지**: 그래프에서 밀접하게 연결된 엔티티들을
>   자동으로 그룹화하는 알고리즘 (예: Leiden Algorithm).  
>   "삼성전자-이재용-반도체"처럼 관련 엔티티가  
>   하나의 커뮤니티로 묶임.  
> - **요약 생성**: 탐지된 커뮤니티마다 LLM이 소속
>   엔티티/관계를 종합하여 텍스트 요약(리포트)을 생성.  
>   전체 문서에 대한 종합 질문 응답에 활용됨.

> **Cypher**: Neo4j 그래프 DB 전용 쿼리 언어.  
> SQL이 관계형 DB의 쿼리 언어이듯, Cypher는 그래프 DB의  
> 쿼리 언어임. 노드는 `()`, 관계는 `-->` 로 표현.  
> 예: `MATCH (p:Person)-[:LEADS]->(c:Company) RETURN c.name`

> **2024년 대비 주요 변경 사항**:  
> - **MS GraphRAG**: 증분 업데이트 지원 (v0.5.0+),
>   LazyGraphRAG 출시로 인덱싱 비용 99% 절감 (쿼리 시점 요약).  
>   LazyGraphRAG는 인덱싱 시 LLM 사전 요약을 수행하지 않고,  
>   NLP 명사구 추출 + 동시출현 그래프만 구성한 뒤  
>   쿼리 시점에 LLM을 호출하는 방식.  
>   2026.1 현재 오픈소스 미공개 (Azure 서비스로만 제공)  
> - **LightRAG**: 커뮤니티 탐지를 의도적으로 회피하는 설계.
>   Dual-level 검색으로 커뮤니티 없이 광범위한 테마 처리.  
>   Citation, MongoDB/PostgreSQL/Neo4j 스토리지 지원 추가  
> - **Neo4j GraphRAG**: Cypher AI 프로시저(2025.12)로
>   Python 없이 순수 Cypher에서 KG 구축(엔티티 추출, 임베딩) 가능.  
>   단, Neo4j Enterprise (유료) 라이선스 필요  
> - **LlamaIndex**: PropertyGraph에 hierarchical_leiden
>   커뮤니티 탐지 및 LLM 요약 내장 지원 추가

### 문서 업데이트 시 처리

인덱싱된 문서의 내용이 변경된 경우, 각 프레임워크의 처리 방식이 다름.    
**모든 프레임워크가 변경된 문서를 자동 감지하지 않으며**,   
개발자가 직접 변경 추적 로직을 구현해야 함.

| 항목 | MS GraphRAG | LangChain+Neo4j | LightRAG |
|------|-------------|-----------------|----------|
| **변경 자동 감지** | X | X | X |
| **Upsert (자동 병합)** | X | X | X |
| **삭제 API** | X (미제공) | Cypher 수동 삭제 | `delete_by_doc_id()` |
| **권장 업데이트 방법** | 전체 재인덱싱 | Cypher 삭제 → 재삽입 | 삭제 → `ainsert()` |
| **커뮤니티 재계산** | 필요 | 해당 없음 | 해당 없음 |

- **MS GraphRAG**: 삭제 API가 없어 수정된 문서 반영이 가장 불편.  
  커뮤니티 탐지/요약 구조상 부분 업데이트 시 커뮤니티 재계산이 필요하므로  
  **전체 재인덱싱이 가장 안전한 방법**.  
- **LangChain + Neo4j**: Neo4j Cypher 쿼리로 기존 노드/관계를 직접 삭제 후 재삽입.  
  그래프 DB에 직접 접근 가능하여 유연하지만 개발자가 직접 구현 필요.  
  별도 삭제 과정 불필요. 동시성 제어(locking + checkpointing) 내장.  
  **문서 변경이 빈번한 환경에 가장 적합.**  
- **LightRAG**: MD5 해시 기반 문서 ID를 사용하므로,  
  내용 변경 시 다른 문서로 인식되어 구/신 버전이 공존.  
  `delete_by_doc_id()` → `ainsert()` 워크플로우로 처리.  

> **동일 내용 재삽입 시**: 모든 프레임워크가 중복 삽입을 방지함.  
> LightRAG는 MD5 해시,  
> LangChain+Neo4j는 Neo4j MERGE로 각각 처리.

### 선택 가이드

| 우선 고려 | 권장 프레임워크 | 근거 |
|-----------|----------------|------|
| 글로벌 질문 품질 최우선 | MS GraphRAG | 사전 요약으로 최고 품질, 인덱싱 비용 감수 |
| 비용 효율 + 빠른 처리 | LightRAG | 인덱싱 비용 낮음, 실시간 키워드 확장 |
| LangChain 생태계 활용 필요 | LangChain + Neo4j | 체인/에이전트/메모리 조합, 레퍼런스 풍부 |
| Neo4j 공식 솔루션 선호 | Neo4j GraphRAG | 경량 통합, 별도 프레임워크 불필요 |
| LlamaIndex 기반 프로젝트 | LlamaIndex PropertyGraph | 사전 요약 내장 + 다양한 스토어 지원 |
| 오픈소스 필수 | MS GraphRAG, LightRAG, Neo4j 계열 | 모두 오픈소스. 단, Neo4j GDS 사전 요약은 유료 |

> **Neo4j GraphRAG vs LangChain + Neo4j**  
>
> 사용 빈도: LangChain + Neo4j가 더 많이 사용됨.  
> - LangChain 생태계의 압도적 규모와 유연성
> - 체인, 에이전트, 메모리 등과 자유로운 조합
> - 튜토리얼, 예제, 커뮤니티 답변이 풍부
>
> 실무 권장:  
> - 처음 시작 또는 LangChain 사용 중 → LangChain + Neo4j
> - Neo4j 인프라가 이미 있고 경량 통합 → Neo4j GraphRAG

| IT/빠른 산업 | 분기~월간 |

분기/반기 주기라면 전체 재인덱싱도 충분히 감당 가능

| 상황 | 최적 프레임워크 | 근거 |
|------|----------------|------|
| 글로벌 질문 품질 최우선 | MS GraphRAG | 커뮤니티 요약으로 70~80% 우위, 검증된 기업 사례 |
| 생태계 안정성/레퍼런스 중시 | LangChain + Neo4j | 시장 65% 점유, 풍부한 커뮤니티 |
| 비용 대비 효과 최우선 | LightRAG | 65~80% 비용 절감, 간결한 아키텍처 |


### GraphRAG와 Vector RAG의 관계

GraphRAG는 Vector RAG를 **대체가 아닌 보완**

**Vector 임베딩의 역할**: 그래프 탐색의 **진입점**

```
질문 → 벡터 유사도 검색 → 관련 엔티티 찾기 → 그래프 탐색 → 답변
                ↑                                    ↑
          Vector DB 사용                    Knowledge Graph 사용
```

- **진입점 탐색**: Knowledge Graph만으로는 질문과 관련된
  시작 엔티티를 특정할 수 없음.  
  Vector 유사도로 질문과 가장 관련된 엔티티를 먼저 찾고,  
  그 엔티티를 기점으로 그래프를 확장 탐색  
- **원문 검색**: 그래프 탐색 후 원문 텍스트 추출 시
  임베딩 기반 유사도 검색 활용

| 프레임워크 | Vector 임베딩 활용 |
|---|---|
| MS GraphRAG | Local/DRIFT Search의 진입점 |
| LightRAG | Low-level 검색의 진입점 |
| Neo4j 계열 | Vector/Hybrid 검색 모드 |
| LlamaIndex | Vector/Hybrid 검색 모드 |

> **결론**: GraphRAG = Knowledge Graph(관계 추론)  
> \+ Vector Embeddings(유사도 검색).  
> 대부분의 GraphRAG 프레임워크가 Vector 임베딩을  
> 그래프 탐색의 진입점으로 활용함.

## 2.4 MS GraphRAG

Microsoft GraphRAG의 상세 아키텍처와 구축 방법.

### 2.4.1 인덱싱 프로세스

| 단계 | 작업 | 설명 |
|------|------|------|
| 1 | **TextUnit 분할** | 원본 문서를 분석 단위로 분할 |
| 2 | **엔티티 추출** | 사람, 조직, 장소, 개념 등 엔티티 식별 |
| 3 | **관계 추출** | 엔티티 간 관계(소속, 협력, 소유 등) 식별 |
| 4 | **그래프 구축** | 엔티티(노드) + 관계(엣지)로 Knowledge Graph 구성 |
| 5 | **커뮤니티 탐지** | Leiden 알고리즘으로 밀접 연결 그룹 탐지 |
| 6 | **요약 생성** | 각 커뮤니티에 대한 계층적 요약문 생성 |
| 7 | **텍스트 임베딩** | 엔티티/텍스트를 벡터로 변환 (유사도 검색용) |

> `graphrag index --root ./project` 명령 하나로  
> 1~7단계 전체 파이프라인이 자동 실행됨.

**검색 모드별 Vector 임베딩 필요 여부**:

| 검색 모드 | Vector 임베딩 | 이유 |
|----------|--------------|------|
| Global Search | ❌ 불필요 | 사전 생성된 커뮤니티 요약만 사용 |
| **Local Search** | ✅ **필수** | 질문-엔티티 유사도 검색 (진입점) |
| **DRIFT Search** | ✅ **필수** | Global + Local 결합 |

#### 단계별 상세

**1단계: TextUnit 분할**
```
원본: "삼성전자는 1969년 이병철 회장이 설립했다. 현재 이재용 회장이..."

TextUnit 1: "삼성전자는 1969년 이병철 회장이 설립했다."
TextUnit 2: "현재 이재용 회장이 경영을 이끌고 있다."
```

**2~3단계: 엔티티/관계 추출 (LLM 활용)**
```json
{
  "entities": [
    {"name": "삼성전자", "type": "ORGANIZATION"},
    {"name": "이병철", "type": "PERSON"},
    {"name": "이재용", "type": "PERSON"}
  ],
  "relationships": [
    {"source": "이병철", "target": "삼성전자", "type": "FOUNDED"},
    {"source": "이재용", "target": "삼성전자", "type": "LEADS"}
  ]
}
```

**4단계: 그래프 구축**
```
이병철 ──FOUNDED──▶ 삼성전자 ◀──LEADS── 이재용
```

**5단계: 커뮤니티 탐지 (Leiden Algorithm)**

커뮤니티 = 엔티티들의 그룹 + 그들 사이의 관계.  
Leiden 알고리즘이 밀접하게 연결된 엔티티들을 자동으로 그룹화.  
재귀적으로 반복하여 **계층적 커뮤니티 구조**를 생성.

```
[커뮤니티 구조 예시]

Level 1: 커뮤니티 A
         ┌─────────────────────────────────┐
         │  엔티티: 삼성전자, 이재용, 반도체  │
         │  관계:                           │
         │    - 이재용 ─[경영]→ 삼성전자     │
         │    - 삼성전자 ─[생산]→ 반도체     │
         └─────────────────────────────────┘

Level 0: 커뮤니티 B          커뮤니티 C
         ┌──────────────┐   ┌──────────────┐
         │ 엔티티: A, B  │   │ 엔티티: C, D  │
         │ 관계: A→B    │   │ 관계: C→D    │
         └──────────────┘   └──────────────┘
```

| 레벨 | 설명 | 용도 |
|------|------|------|
| **Level 0** | 가장 세부적인 커뮤니티 | Local Search, 상세 질문 |
| **Level 1, 2, ...** | 상위 커뮤니티 (하위 커뮤니티들을 묶음) | 중간 수준 요약 |
| **최상위 Level** | 전체 그래프를 아우르는 커뮤니티 | Global Search, 전체 요약 |

**6단계: 커뮤니티 요약 생성 (LLM)**

각 커뮤니티마다 LLM을 호출하여 개별 리포트 생성.  
커뮤니티 내 엔티티/관계 정보를 입력받아 요약 리포트를 출력.

```
커뮤니티 A → LLM → 리포트 A
커뮤니티 B → LLM → 리포트 B
커뮤니티 C → LLM → 리포트 C
(커뮤니티 10개 → LLM 호출 10회 → 리포트 10개)
```

> 커뮤니티 A 리포트 예시:  
> "삼성전자는 이병철 회장이 1969년 설립한 기업으로,  
>  현재 이재용 회장이 경영을 이끌고 있음..."

**7단계: 텍스트 임베딩 (Embedding 모델)**

엔티티 설명, 텍스트 청크 등을 벡터로 변환하여  
Local/DRIFT Search 시 유사도 검색의 진입점으로 활용.

```
엔티티 "삼성전자" 설명 → Embedding 모델 → [0.12, -0.34, 0.56, ...]
엔티티 "이재용" 설명   → Embedding 모델 → [0.08, -0.21, 0.43, ...]
TextUnit 1            → Embedding 모델 → [0.15, -0.28, 0.61, ...]
```

> 결과는 `embeddings.entity_description.parquet`와  
> `lancedb/` 벡터 인덱스로 저장됨.

#### 결과 파일

인덱싱 완료 시 `output/` 디렉토리에 **Parquet** 형식의  
결과 파일이 생성됨.

**디렉토리 구조**:
```
data/output/
├── entities.parquet                           # 엔티티 목록
│     (name, type, description, source_id)
├── relationships.parquet                      # 관계 목록
│     (source, target, description, weight)
├── documents.parquet                          # 원본 문서 메타데이터
├── text_units.parquet                         # 청크 분할 결과
├── communities.parquet                        # 커뮤니티 구성 정보
├── community_reports.parquet                  # 커뮤니티 요약 리포트
├── embeddings.entity_description.parquet      # 엔티티 임베딩 벡터
│     (id, embedding[4096])
└── lancedb/                                   # 벡터 검색 인덱스
    └── *.lance                                # Lance 포맷 인덱스
```

**워크플로우 단계별 생성 파일**:

| 워크플로우 | 생성 파일 |
|-----------|----------|
| load_input_documents | documents.parquet |
| create_base_text_units | text_units.parquet |
| extract_graph | entities.parquet, relationships.parquet |
| create_communities | communities.parquet |
| finalize_graph | community_reports.parquet |
| generate_text_embeddings | embeddings.*.parquet, lancedb/ |

**Parquet 포맷이란?**

Apache Parquet는 **열 기반(columnar) 바이너리 저장 포맷**.  
이름은 프랑스어로 **쪽마루(나무 조각을 패턴으로 깐 바닥재)**를  
뜻하며, 데이터를 행 단위가 아닌 열 단위로 조각내어 배치하는  
구조가 쪽마루의 나무 조각 배열과 유사한 데서 착안한 이름임.

GraphRAG에서 Parquet를 사용하는 이유:  
- **대용량 벡터 저장**: 4096차원 임베딩을 CSV로 저장하면
  파일이 수십 배 커짐  
- **열 선택 읽기**: 쿼리 시 필요한 열만 로드하여 메모리 절약
- **타입 보존**: 정수, 실수, 리스트 등 Python 타입 그대로 유지
- **생태계 호환**: pandas, Spark, Arrow, DuckDB 등
  데이터 도구의 공통 포맷

```python
# Parquet 파일 읽기 예시
import pandas as pd

entities = pd.read_parquet("output/entities.parquet")
print(entities.columns)
# Index(['id', 'name', 'type', 'description', 'source_id'])

print(len(entities))  # 엔티티 수 확인
```

### 2.4.2 쿼리 처리 방식

#### Local Search

**특정 엔티티 중심**의 상세 질문에 적합

```
질문: "이재용 회장의 경영 철학은?"

[처리 과정]
1. "이재용" 엔티티 검색
2. 연결된 엔티티/관계 탐색 (삼성전자, 반도체, 경영전략 등)
3. 관련 TextUnit 수집
4. 컨텍스트 구성 → LLM 답변 생성
```

#### Global Search

**전체 데이터셋 대상** 요약/집계 질문에 적합

```
질문: "문서에 등장하는 주요 기업들의 공통점은?"

[처리 과정]
1. 모든 커뮤니티 요약 수집
2. Map 단계: 각 요약에서 부분 답변 생성
3. Reduce 단계: 부분 답변 통합
4. 최종 답변 생성
```

**Map-Reduce 패턴**:
```
[Map 단계]
커뮤니티 1 요약 → 부분 답변 1: "삼성, LG는 전자 분야..."
커뮤니티 2 요약 → 부분 답변 2: "현대, 기아는 자동차 분야..."
커뮤니티 3 요약 → 부분 답변 3: "네이버, 카카오는 IT 분야..."

[Reduce 단계]
부분 답변 통합 → "주요 기업들의 공통점: 1) 대기업 그룹 계열..."
```

#### DRIFT Search

**Global + Local 검색 결합** (Dynamic Reasoning and Inference with Flexible Traversal)

```
질문: "반도체 시장에서 삼성전자의 위치는?"

[처리 과정 - 3단계]
1. Primer (Global): 커뮤니티 리포트와 쿼리 비교 → 초기 답변 + follow-up 질문 생성
2. Follow-Up (Local): follow-up 질문을 Local 검색으로 탐색 → 상세 답변 생성
3. Output: 질문-답변의 계층적 구조로 최종 결과 생성

[결과]
→ Global의 broad insight + Local의 상세 정보 결합
→ 비용과 품질의 균형
```

#### 쿼리 모드 선택 가이드

| 질문 유형 | 추천 모드 | 예시 |
|----------|----------|------|
| 특정 엔티티 상세 | **Local** | "이재용의 학력은?" |
| 전체 요약/집계 | **Global** | "모든 기업의 공통 과제는?" |
| Global + Local 결합 | **DRIFT** | "AI 산업에서 네이버의 역할은?" |
| 단순 팩트 검색 | **Basic** | "삼성전자 설립연도는?" |

## 2.5 LangChain+Neo4j

LangChain의 `LLMGraphTransformer`와 Neo4j Graph DB를 조합한 GraphRAG 구현.  
MS GraphRAG와 달리 커뮤니티 탐지/사전 요약 없이,  
LLM 기반 엔티티/관계 추출 → Neo4j 저장 → 벡터+그래프 하이브리드 검색 구조.

### 2.5.1 인덱싱 프로세스

LangChain+Neo4j의 인덱싱은 **KG 구축**과 **벡터 인덱스 생성** 2단계로 구성.

#### 전체 파이프라인

```
[Phase 1: KG 구축]
문서 로드 → 텍스트 청킹 → LLMGraphTransformer → Neo4j KG 저장

[Phase 2: 벡터 인덱스]
엔티티 벡터 인덱스 생성 (KG 노드 임베딩)
(선택) 추가 벡터 인덱스 생성 (도메인별 문서 임베딩)
```

#### 단계별 상세

| 단계 | 작업 | 설명 |
|------|------|------|
| 1 | 문서 로드 | 대상 문서를 읽어 LangChain `Document` 객체로 변환 |
| 2 | 텍스트 청킹 | `RecursiveCharacterTextSplitter`로 분할 (권장: chunk_size 600~1000) |
| 3 | **엔티티/관계 추출** | `LLMGraphTransformer`가 각 청크를 LLM에 전달하여 엔티티와 관계 추출 |
| 4 | Neo4j 저장 | `add_graph_documents(baseEntityLabel=True)`로 KG 저장 |
| 5 | 엔티티 벡터 인덱스 | KG 노드의 description을 임베딩하여 Neo4j 벡터 인덱스 생성 |
| 6 | (선택) 추가 벡터 인덱스 | 도메인 특화 문서(코드, FAQ 등)를 별도 벡터 인덱스로 생성 |

#### MS GraphRAG와의 차이

| 항목 | MS GraphRAG | LangChain+Neo4j |
|------|-------------|-----------------|
| 그래프 저장소 | 파일 기반 (Parquet) | **Neo4j Graph DB** |
| 커뮤니티 탐지 | Leiden Algorithm으로 수행 | 없음 |
| 커뮤니티 리포트 | LLM으로 사전 요약 생성 | 없음 |
| 엔티티 추출 | 자체 추출 파이프라인 | **LLMGraphTransformer** |
| 벡터 인덱스 | LanceDB | **Neo4j Vector Index** |
| 인덱싱 비용 | 커뮤니티 리포트 생성으로 높음 | 엔티티 추출만으로 상대적으로 낮음 |

#### LLMGraphTransformer 동작 방식

```
입력: "Kubernetes는 컨테이너 오케스트레이션 플랫폼으로, Docker 컨테이너를 관리한다."

[LLM 추출 결과]
노드: (Kubernetes:기술), (컨테이너 오케스트레이션:개념), (Docker:기술)
관계: (Kubernetes)-[구현]->(컨테이너 오케스트레이션), (Kubernetes)-[사용]->(Docker)

[Neo4j 저장]
(:__Entity__:기술 {id: "Kubernetes", description: "컨테이너 오케스트레이션 플랫폼"})
(:__Entity__:개념 {id: "컨테이너 오케스트레이션"})
(:__Entity__:기술 {id: "Docker"})
(Kubernetes)-[:구현]->(컨테이너 오케스트레이션)
(Kubernetes)-[:사용]->(Docker)
```

**주요 설정 파라미터**:

- `__Entity__`: 모든 노드에 공통 부여되는 라벨 (`baseEntityLabel=True` 시 자동 생성)
- `allowed_nodes`: 허용 노드 타입 목록 (예: Person, Organization, Technology 등)
- `allowed_relationships`: 허용 관계 타입 목록 (예: WORKS_FOR, USES, DEPENDS_ON 등)
- `strict_mode=True`: 허용 목록에 매칭되는 엔티티/관계만 저장, 나머지 폐기
- `strict_mode=False`: 허용 목록은 힌트일 뿐, 모든 추출 결과 저장

#### 결과 저장소

| 저장소 | 내용 | 용도 |
|--------|------|------|
| Neo4j KG | 엔티티 노드 + 관계 엣지 | 그래프 탐색, Cypher 쿼리 |
| Neo4j Vector Index | 엔티티 description 임베딩 | 벡터 유사도 검색 |
| (선택) 추가 Vector Index | 도메인 문서 임베딩 | 특화 검색 (코드, FAQ 등) |

### 2.5.2 쿼리 처리 방식

LangChain+Neo4j는 Neo4j의 그래프 탐색과 벡터 검색을 조합하여  
다양한 검색 모드를 구성할 수 있음.  
대표적인 검색 모드 4가지와 쿼리 라우팅 방식을 소개.

#### Vector Search

**벡터 유사도 기반** 검색. Neo4j Vector Index에서 임베딩 유사도로 관련 엔티티 탐색.

```
질문: "마이크로서비스 아키텍처란?"

[처리 과정]
1. 질문을 임베딩 벡터로 변환
2. Neo4j 벡터 인덱스에서 유사도 상위 K개 검색
3. 검색 결과를 컨텍스트로 구성 → LLM 답변 생성
```

- LangChain의 `Neo4jVector.from_existing_index()`로 벡터 스토어 연결
- `RetrievalQA` 체인으로 검색 → 답변 파이프라인 구성

#### Graph QA

**Cypher 쿼리 자동 생성**으로 그래프를 직접 탐색.  
`GraphCypherQAChain`이 질문에서 Cypher를 생성하고 Neo4j에서 실행.

```
질문: "Kubernetes와 관련된 기술은?"

[처리 과정]
1. LLM이 질문에서 Cypher 쿼리 자동 생성
   → MATCH (n {id: "Kubernetes"})-[r]-(m) RETURN m.id, type(r)
2. Neo4j에서 Cypher 실행
3. 결과를 자연어로 변환
```

- LangChain의 `GraphCypherQAChain.from_llm()`으로 구성
- `validate_cypher=True`로 생성된 Cypher의 문법 검증 가능

#### Hybrid Search

**Vector + Graph 결합** 검색. 벡터 검색으로 관련 엔티티를 찾고,  
그래프 탐색으로 이웃 노드까지 확장하여 풍부한 컨텍스트 구성.

```
질문: "클라우드 네이티브 기술 스택의 전체 구조는?"

[처리 과정]
1. 벡터 검색으로 관련 엔티티 상위 K개 탐색
2. 탐색된 엔티티의 1-hop 이웃 관계 그래프 확장
   → MATCH (n)-[r]-(m) WHERE n.id IN $names RETURN ...
3. 벡터 결과(개념 설명) + 그래프 결과(관계 구조) 통합
4. 통합 컨텍스트 → LLM 답변 생성
```

- Vector Search 단독 대비 관계 정보가 추가되어 멀티홉 질문에 강점
- 그래프 확장 깊이(hop 수)와 반환 수(LIMIT)로 컨텍스트 크기 조절

#### Cypher Direct

**사용자가 Cypher 쿼리를 직접 입력**하여 Neo4j에서 실행.  
그래프 구조 확인, 디버깅, 고급 탐색에 활용.

```
입력: MATCH (n)-[r]->(m) RETURN n.id, type(r), m.id LIMIT 10

[처리 과정]
1. 입력된 Cypher 쿼리를 Neo4j에 직접 실행
2. 결과를 그대로 반환 (LLM 변환 없음)
```

- 개발/디버깅 시 그래프 상태를 직접 확인하는 용도
- 운영 환경에서는 Cypher Injection 방지를 위해 입력 검증 필요

#### 쿼리 라우팅

질문 유형에 따라 적절한 검색 모드를 자동 선택하는 라우터 구성 가능.  
일반적인 라우팅 전략:

```
[1단계: 규칙 기반 매칭]
Cypher 키워드 포함 ("MATCH", "RETURN") → cypher 모드
패턴 매칭으로 질문 유형 분류 (키워드 점수 기반)

[2단계: LLM fallback]
규칙 기반으로 분류 확신도가 낮은 경우 → LLM이 모드 분류
```

> 예시) 본 프로젝트에서는 패턴 매칭(점수 2점 이상 시 확정) +  
> LLM Few-shot fallback 2단계 라우터를 구현.  
> "설명", "개념", "정의" → vector / "관계", "연결", "비교" → graph_qa /  
> "전체", "요약", "종합" → hybrid 로 분류.

#### 쿼리 모드 선택 가이드

| 질문 유형 | 추천 모드 | 예시 |
|----------|----------|------|
| 개념 설명, 정의 | **Vector** | "마이크로서비스란 무엇인가?" |
| 엔티티 간 관계 | **Graph QA** | "Kubernetes와 관련된 기술은?" |
| 종합 요약, 전체 파악 | **Hybrid** | "주요 프레임워크의 관계 구조는?" |
| 그래프 직접 탐색 | **Cypher** | "MATCH (n) RETURN n LIMIT 10" |

### 2.5.3 주의사항

**allowed_nodes/relationships는 영어로 설정**

LLMGraphTransformer는 내부적으로 영어 프롬프트를 사용하여 엔티티를 추출함.  
LLM 모델(qwen3 등)이 영어 엔티티 타입을 반환하므로,  
`strict_mode=True` 사용 시 **allowed_nodes/relationships를 영어로 설정**해야 함.

한국어로 설정할 경우 LLM 출력과 허용 목록이 불일치하여  
모든 엔티티가 필터링되는 **Silent Failure** 발생 가능.

```python
# 올바른 설정 (영어)
allowed_nodes = ["Concept", "Technology", "Library", "Framework",
                 "Tool", "Pattern", "Methodology"]
allowed_relationships = ["USES", "DEPENDS_ON", "IMPLEMENTS",
                         "CONTAINS", "COMPARES", "EXTENDS"]

# 잘못된 설정 (한국어) - LLM 출력과 매칭 실패
allowed_nodes = ["개념", "기술", "라이브러리", "프레임워크",
                 "도구", "패턴", "방법론"]
```

> **참고**: 엔티티의 `id`, `text`, `description` 속성은 문서 내용에서 추출되므로  
> 한국어 문서의 경우 한국어로 저장됨. **검색 시 영향 없음**.

## 2.6 LightRAG

LightRAG는 **듀얼 레벨(Low-level/High-level) 검색**과 **증분 업데이트**가 핵심인  
경량 GraphRAG 프레임워크 (EMNLP 2025 논문 기반).  
MS GraphRAG와 달리 커뮤니티 탐지/사전 요약 없이,  
LLM 기반 엔티티/관계 추출 → 자체 JSON/NetworkX 저장 →  
키워드 기반 그래프+벡터 검색 구조.

**주요 특징:**

| 항목 | 내용 |
|------|------|
| **검색 방식** | 듀얼 레벨 키워드 (High-level + Low-level) |
| **그래프 저장** | NetworkX (.graphml) 또는 Neo4j 선택 가능 |
| **벡터 저장** | NanoVectorDB (내장 JSON) 또는 외부 벡터 DB |
| **증분 업데이트** | 설계 초기부터 핵심 기능으로 구현 |
| **외부 의존성** | 없음 (별도 DB 서버 불필요) |
| **LLM 연동** | OpenAI, Ollama, Gemini 등 다양한 백엔드 지원 |

### 2.6.1 인덱싱 프로세스

LightRAG의 인덱싱은 **청킹 → KG 구축 → 벡터 인덱스 생성** 3단계로 구성.

#### 전체 파이프라인

```
[문서 입력]
문서 로드 (str 또는 list[str])

[Phase 1: 청킹]
문서 → 토큰 기반 분할 (chunk_token_size / chunk_overlap_token_size)

[Phase 2: KG 구축]
각 청크 → LLM 엔티티/관계 추출 → 그래프 저장

[Phase 3: 벡터 인덱스]
엔티티/관계/청크 각각 벡터 임베딩 → 벡터 DB 저장
```

#### 단계별 상세

| 단계 | 작업 | 설명 |
|------|------|------|
| 1 | **문서 큐 등록** | `ainsert(str \| list[str])`로 문서를 파이프라인 큐에 등록 |
| 2 | **토큰 기반 청킹** | `chunk_token_size`(기본 1200) 단위로 분할, `chunk_overlap_token_size`(기본 100) 오버랩 |
| 3 | **엔티티/관계 추출** | 각 청크를 LLM에 전달하여 엔티티(노드)와 관계(엣지) 추출 |
| 4 | **Gleaning (재추출)** | `entity_extract_max_gleaning`(기본 1)회 추가 검사로 누락 엔티티 보완 |
| 5 | **엔티티 병합** | 동일 엔티티를 하나로 병합, description을 LLM으로 요약 통합 |
| 6 | **그래프 저장** | NetworkX 그래프(.graphml) 또는 Neo4j에 노드/엣지 저장 |
| 7 | **벡터 인덱스 생성** | 엔티티/관계/청크 각각의 description을 임베딩하여 벡터 DB에 저장 |

> `await rag.ainsert(documents)`로 전체 파이프라인이 자동 실행됨.  
> `list[str]`로 전달하면 내부 배치 처리로 건별 호출 대비 효율적.

**Gleaning(재추출)이란?**  
LLM이 한 번에 모든 엔티티를 추출하지 못할 수 있으므로,  
"혹시 빠뜨린 엔티티가 있나?"라고 같은 청크를 다시 보내 추가 추출하는 과정.  
`entity_extract_max_gleaning=0`으로 비활성화하면 속도가 약 2배 향상되지만  
추출 누락 가능성이 있음. MS GraphRAG에도 동일 개념 존재 (`max_gleanings`).

#### 저장소 구조 (기본 설정 기준)

| 저장소 | 파일 | 용도 |
|--------|------|------|
| **그래프** | `graph_chunk_entity_relation.graphml` | 엔티티(노드) + 관계(엣지) Knowledge Graph |
| **엔티티 벡터** | `vdb_entities.json` | 엔티티 description 임베딩 (벡터 검색용) |
| **관계 벡터** | `vdb_relationships.json` | 관계 description 임베딩 (벡터 검색용) |
| **청크 벡터** | `vdb_chunks.json` | 원본 텍스트 청크 임베딩 (벡터 검색용) |
| **문서 상태** | `kv_store_doc_status.json` | 문서별 인덱싱 상태 추적 (증분 업데이트용) |
| **LLM 캐시** | `kv_store_llm_response_cache.json` | LLM 응답 캐시 (재인덱싱 시 비용 절감) |

> MS GraphRAG는 Parquet+LanceDB, LangChain+Neo4j는 Neo4j Graph DB를 사용하는 반면,  
> LightRAG는 기본적으로 **JSON 파일 기반** 저장으로 외부 DB 의존성 없이 동작.  
> Neo4j, Milvus 등 외부 스토리지도 설정으로 전환 가능.

#### 증분 업데이트

LightRAG의 핵심 강점. 기존 인덱스를 유지하면서 새 문서만 추가 가능.

```
[기존 인덱스]
문서 A, B, C → KG + 벡터 인덱스

[증분 추가]
rag.ainsert(["문서 D 내용", "문서 E 내용"])
→ 기존 A, B, C 인덱스 유지
→ D, E에서 추출된 엔티티/관계가 기존 그래프에 병합
→ 동일 엔티티 발견 시 description 자동 통합
```

- 문서별 처리 상태를 추적하여 이미 인덱싱된 문서는 자동 스킵 (MD5 해시 기반)
- MS GraphRAG v0.5.0+에서도 증분 업데이트를 지원하지만,
  LightRAG는 설계 초기부터 증분 업데이트를 핵심 기능으로 구현  
- 실시간에 가까운 문서 추가가 필요한 서비스에 적합

### 2.6.2 쿼리 처리 방식

LightRAG는 **6가지 검색 모드**를 지원하며,  
쿼리에서 LLM이 추출한 **High-level/Low-level 키워드**로 그래프와 벡터를 탐색.

#### 공통 전처리: 키워드 추출

모든 검색 모드(naive, bypass 제외)에서 쿼리 전처리로 키워드를 추출.

```
질문: "전자상거래에서 결제 시스템의 보안 이슈는?"

[LLM 키워드 추출]
High-level: ["전자상거래", "보안 아키텍처"]
Low-level:  ["결제 시스템", "PCI DSS", "토큰화"]

→ High-level: 넓은 개념/테마 (글로벌 탐색용)
→ Low-level: 구체적 엔티티/용어 (로컬 탐색용)
```

이 듀얼 레벨 키워드가 LightRAG의 핵심 차별점.  
같은 질문에서 **추상적 개념**과 **구체적 용어**를 동시에 추출하여  
검색 범위와 정밀도를 균형 있게 조절.

#### Local Search

**Low-level 키워드 중심**의 구체적 엔티티 탐색.

```
질문: "Kubernetes의 Pod 스케줄링 방식은?"

[처리 과정]
1. Low-level 키워드 추출: ["Kubernetes", "Pod", "스케줄링"]
2. 키워드로 엔티티 벡터 검색 → 관련 엔티티 상위 K개
3. 매칭된 엔티티의 관계/이웃 노드 탐색
4. 관련 텍스트 청크 수집
5. 컨텍스트 구성 → LLM 답변 생성
```

#### Global Search

**High-level 키워드 중심**의 넓은 범위 탐색.

```
질문: "소프트웨어 개발 방법론의 발전 흐름은?"

[처리 과정]
1. High-level 키워드 추출: ["소프트웨어 개발 방법론", "프로세스 혁신"]
2. 키워드로 관계 벡터 검색 → 관련 관계 상위 K개
3. 관계에 연결된 엔티티 쌍과 description 수집
4. 관련 텍스트 청크 수집
5. 컨텍스트 구성 → LLM 답변 생성
```

> MS GraphRAG의 Global Search가 사전 생성된 커뮤니티 요약을 사용하는 반면,  
> LightRAG의 Global Search는 **쿼리 시점에 키워드로 관계를 탐색**하여  
> 사전 요약 없이도 글로벌 질문에 답변.  
> 인덱싱 비용이 낮은 대신, 쿼리 시점에 더 많은 탐색이 필요.

#### Hybrid Search

**Local + Global 결합**. 엔티티(Local)와 관계(Global) 탐색 결과를 통합.

```
질문: "REST API와 gRPC의 차이점과 적용 시나리오는?"

[처리 과정]
1. Low-level 키워드 → 엔티티 벡터 검색 (REST API, gRPC 등)
2. High-level 키워드 → 관계 벡터 검색 (API 통신, 마이크로서비스 등)
3. 두 결과 통합 + 관련 텍스트 청크 수집
4. 통합 컨텍스트 → LLM 답변 생성
```

#### Mix Search (기본 모드)

**KG 그래프 탐색 + 벡터 검색 통합**. Hybrid와 유사하나 그래프 구조를 더 적극 활용.

```
질문: "디자인 패턴에서 Observer와 Mediator의 관계는?"

[처리 과정]
1. 키워드 추출 → 엔티티/관계 벡터 검색
2. KG에서 매칭된 노드의 이웃 관계까지 그래프 순회
3. 텍스트 청크 벡터 검색 결과 추가
4. KG 구조 정보 + 벡터 검색 결과 통합 → LLM 답변 생성
```

#### Naive Search

**단순 벡터 검색**. KG를 사용하지 않고 텍스트 청크만 벡터 검색.  
일반 Vector RAG와 동일한 방식. 비교 실험이나 KG 효과 측정에 활용.

#### Bypass

LLM에 직접 질문 전달. 검색 없이 LLM 자체 지식으로 답변.  
RAG 효과 측정을 위한 베이스라인 비교용.

#### 쿼리 모드 선택 가이드

| 질문 유형 | 추천 모드 | 예시 |
|----------|----------|------|
| 구체적 엔티티 상세 | **local** | "Kubernetes의 주요 컴포넌트는?" |
| 넓은 개념/테마 탐색 | **global** | "전체 문서의 핵심 주제는?" |
| Local + Global 결합 | **hybrid** | "REST와 gRPC의 차이점은?" |
| KG + 벡터 통합 (기본) | **mix** | "Observer 패턴과 관련 패턴은?" |
| 단순 벡터 검색 (비교용) | **naive** | KG 효과 측정용 베이스라인 |
| LLM 직접 답변 (비교용) | **bypass** | RAG 효과 측정용 베이스라인 |

> LightRAG 기본 모드는 `mix`이며, 대부분의 질문에 가장 균형 잡힌 결과 제공.

### 2.6.3 주의사항

**EmbeddingFunc 이중 래핑 문제**

LightRAG의 `ollama_embed` 함수는 `@wrap_embedding_func_with_attrs(embedding_dim=1024)` 데코레이터가  
기본 적용되어 있음. 이를 `EmbeddingFunc`으로 다시 래핑하면 내부 데코레이터가 자체 `embedding_dim=1024`로  
벡터 수를 검증하여 실제 차원(예: 4096)과 충돌 발생.

에러 예시:
```
ValueError: Vector count mismatch: expected 3 vectors but got 12 vectors
```

원인: 3텍스트 × 4096차원 = 12,288 요소 → 내부 검증이 12,288 / 1024 = 12벡터로 계산하여 불일치 발생.

해결: `ollama_embed.func`으로 내부 데코레이터를 우회하여 원본 함수에 직접 접근.

```python
# 잘못된 방법: 이중 데코레이터 충돌
embedding_func=EmbeddingFunc(
    embedding_dim=4096,
    func=lambda texts: ollama_embed(texts, embed_model="qwen3-embedding"),
)

# 올바른 방법: .func으로 원본 함수 접근
embedding_func=EmbeddingFunc(
    embedding_dim=4096,
    func=lambda texts, **kwargs: ollama_embed.func(
        texts, embed_model="qwen3-embedding", **kwargs,
    ),
)
```

## 2.7 인덱싱 비용 최적화

GraphRAG 인덱싱의 핵심 비용은 **엔티티/관계 추출** 단계에서 발생.  
모든 텍스트가 LLM을 통과해야 하므로 문서 규모에 비례하여 비용 증가.  
LLM 기반 추출을 사용하는 모든 프레임워크에 공통으로 적용되는 문제.

### 비용 발생 구조

| 단계 | 비용 | 설명 |
|------|------|------|
| 텍스트 분할 | 없음 | 단순 청킹 |
| **엔티티/관계 추출** | **높음** | 모든 텍스트 → LLM |
| **엔티티/관계 요약** | **높음** | 추출 결과 → LLM |
| 그래프 구조화 | 없음 | 알고리즘 기반 (비-LLM) |
| **글로벌 요약 생성** | **중간** | 프레임워크별 상이 (LLM 사용 시) |
| 텍스트 임베딩 | 낮음 | Embedding 모델 |

> Cloud LLM(GPT-4o, Claude 등) 사용 시  
> 100만 문서 기준 **\$3,000 ~ \$50,000** 비용 발생 가능

### 전략 1: Local LLM 활용

로컬 환경에서 오픈소스 LLM을 실행하여 API 비용을 제거.

**구성 방법**:  
- Ollama, vLLM, llama.cpp 등으로 로컬 LLM 서버 구동
- 프레임워크 설정에서 API 엔드포인트를 로컬 서버로 변경

**예시** (Ollama 로컬 서버):

```bash
# Ollama 서버 실행 후
# 프레임워크 설정에서 llm.api_base를 localhost로 변경
# MS GraphRAG: settings.yaml
# LightRAG/LlamaIndex: 초기화 시 base_url 파라미터
```

| 항목 | 설명 |
|------|------|
| **장점** | API 비용 $0, 데이터 외부 유출 없음 |
| **단점** | GPU 장비 필요, Cloud LLM 대비 품질 하락 가능 |
| **권장 모델** | Llama 3, Mistral, Qwen 등 (8B~70B) |

### 전략 2: Local LLM + Cloud LLM 검증 (하이브리드)

대량 추출은 Local LLM으로 처리하고,  
저신뢰도 결과만 Cloud LLM으로 검증하여 API 비용 대폭 감소.  
동일한 LLM 인터페이스를 사용하므로 별도 파이프라인 구축 불필요.

#### 공통 단계 (모든 프레임워크)

엔티티/관계 추출은 인덱싱 비용의 대부분을 차지하는 단계.

| 단계 | 작업 | 수행 주체 |
|------|------|----------|
| 1 | 텍스트 분할 | 단순 청킹 |
| 2 | 엔티티/관계 추출 (1차) | **Local LLM** (Ollama 등) |
| 3 | 신뢰도 판단 | 추출 결과의 confidence 기반 |
| 4 | 저신뢰도 결과 검증/보완 | **Cloud LLM** (GPT-4o 등) |
| 5 | 그래프 구축 | 비-LLM |
| 6 | 텍스트 임베딩 | Embedding 모델 (비용 낮음) |

> Local LLM이 대부분 처리 →  
> Cloud LLM은 전체의 10~20%만 검증  
> 엔드포인트 전환만으로 구현 가능 (코드 변경 최소)

#### 사전 요약 프레임워크 추가 단계 (MS GraphRAG, LlamaIndex)

MS GraphRAG와 LlamaIndex는 커뮤니티 탐지 후  
**커뮤니티 리포트(사전 요약)** 생성에 LLM을 추가 사용.  
이 단계도 하이브리드 전략 적용 가능.

| 단계 | 작업 | 하이브리드 전략 |
|------|------|----------------|
| 7 | 커뮤니티 탐지 | Leiden Algorithm (비-LLM, 비용 없음) |
| 8 | 커뮤니티 리포트 생성 | **Local LLM**으로 초안 생성 |
| 9 | 상위 레벨 리포트 검증 | **Cloud LLM**으로 품질 보완 |

> **하이브리드 적용 포인트**:  
> - 하위 레벨 커뮤니티(소규모, 다수):
>   Local LLM으로 리포트 생성 (비용 절감)  
> - 상위 레벨 커뮤니티(대규모, 소수):
>   Cloud LLM으로 리포트 생성 (품질 확보)  
> - 상위 레벨일수록 글로벌 질문 답변 품질에 직접 영향 →
>   소수이므로 Cloud LLM 비용 부담 적음

**프레임워크별 적용 방법**:

| 프레임워크 | 설정 방법 |
|-----------|----------|
| **MS GraphRAG** | `settings.yaml`에서 LLM 엔드포인트를<br>단계별로 분리 설정 (현재 미지원,<br>커스텀 워크플로우로 구현 가능) |
| **LlamaIndex** | `PropertyGraphIndex` 생성 시<br>`llm` 파라미터를 단계별로 교체하여 구현 |

> LightRAG 등 사전 요약을 수행하지 않는  
> 프레임워크는 공통 단계(1~5)만 적용하면 됨

### 비용 비교

| 항목 | Cloud LLM | Local LLM | 하이브리드 |
|------|-----------|-----------|-----------|
| **추출 주체** | Cloud LLM 전체 | Local LLM 전체 | Local + Cloud 검증 |
| **100만 문서 비용** | \$3,000~\$50,000 | ~\$100 (전기세) | \$300~\$5,000 |
| **처리 속도** | 느림 (API) | 중간 (GPU) | 중간 |
| **품질** | 높음 | 중간~높음 | 높음 |
| **구현 난이도** | 낮음 | 낮음 | 중간 (신뢰도 판단 로직) |

### 선택 가이드

| 상황 | 추천 전략 |
|------|----------|
| 소규모 (~1만 문서), 최고 품질 | Cloud LLM |
| 대규모, 비용 절감 우선 | Local LLM |
| 데이터 보안 필수 (온프레미스) | Local LLM |
| 대규모 + 높은 품질 | 하이브리드 (Local + Cloud 검증) |

## 2.9 인덱싱 성능 최적화

GraphRAG 인덱싱은 문서를 청킹하고 각 청크마다 LLM을 여러 번  
호출하여 엔티티와 관계를 추출하므로 소요 시간이 김.  
Local LLM 사용 시 적용 가능한 범용적 최적화 가이드.

### 1) Ollama 병렬 처리 (Parallelization)
로컬 LLM 사용 시 가장 효과적인 방법. GPU 메모리(VRAM)가 허용하는 한 동시에 여러 요청을 처리하도록 설정.

**주요 환경변수**

| 환경변수 | 기본값 | 설명 |
|---|---|---|
| `OLLAMA_NUM_PARALLEL` | 4 | 하나의 모델이 동시에 처리할 수 있는 요청 수.  값을 높이면 처리량 증가하지만, 요청마다 KV 캐시용 VRAM을 추가 소비 |
| `OLLAMA_MAX_LOADED_MODELS` | 3 | GPU 메모리에 동시에 올릴 수 있는 모델 수.  단일 모델만 사용하는 경우 1로 설정하여 VRAM을 병렬 처리에 집중 |
| `OLLAMA_FLASH_ATTENTION` | auto | FlashAttention 알고리즘 사용 여부.  1로 설정 시 어텐션 계산의 메모리 사용량 감소 및 속도 30~35% 향상 |
| `OLLAMA_MAX_QUEUE` | 512 | `NUM_PARALLEL` 초과 요청을 대기시키는 큐 크기.  큐가 가득 차면 503 에러 반환. 대규모 인덱싱 시 기본값 유지 권장 |

**GPU VRAM별 권장 설정** (qwen3:8b-q4_K_M 기준, 모델 로드 ~5GB)

| GPU VRAM | `NUM_PARALLEL` | 비고 |
|---|---|---|
| 8GB (RTX 3060 등) | **2** | KV 캐시 여유 ~3GB, 보수적 설정 |
| 12GB (RTX 3060 12G 등) | **3~4** | 안정적 병렬 처리 가능 |
| 16GB (RTX 4060 Ti 등) | **4~6** | 충분한 여유, 권장 설정 |
| 24GB (RTX 4090 등) | **8** | 최대 병렬 처리 |

- 병렬 요청마다 KV 캐시 메모리를 추가 사용 (요청당 ~0.5~1GB)
- VRAM 초과 시 OOM 에러 또는 CPU 오프로딩으로 급격한 속도 저하 발생
- `nvidia-smi`로 VRAM 사용량 모니터링 권장
- 환경변수 셋팅
```bash
export OLLAMA_NUM_PARALLEL=4
export OLLAMA_MAX_LOADED_MODELS=1
export OLLAMA_FLASH_ATTENTION=1
```
- 재시작  
[Ollama 서버 배포 가이드](https://github.com/cna-bootcamp/aistudy/blob/main/agentic-ai/reference/run-ollama-server.md)를 참고하여 서버 재시작   

**`concurrent_requests`와 `OLLAMA_NUM_PARALLEL`의 관계**

프레임워크의 동시 요청 수 설정(예: MS GraphRAG `settings.yaml`의 `concurrent_requests`)은   
Ollama의 `OLLAMA_NUM_PARALLEL`과 맞춰야 함.  
단, GPU 사용률이 90% 이상인 경우 병렬 수를 낮추면  
GPU 경합(contention)이 줄어 오히려 처리량이 증가함.

| GPU 사용률 | 권장 `concurrent_requests` | 이유 |
|-----------|--------------------------|------|
| ~70% | `OLLAMA_NUM_PARALLEL`과 동일 (3~4) | GPU 여유 있음, 병렬 처리 효율적 |
| 80~90% | 2~3 | GPU 부하 높음, 경합 발생 가능 |
| **90%+** | **2** | GPU 포화 상태, 병렬 증가 시 오히려 느려짐 |

> **실측 결과**: VRAM 16GB + qwen3:8b-q4_K_M 환경에서  
> `concurrent_requests: 4` → GPU 94% 포화, 처리 지연 발생  
> `concurrent_requests: 2` → GPU 사용률 감소, 처리 속도 향상
  
### 2) 모델 양자화 (Quantization)
FP16(16비트) 원본 모델 대신 4비트 양자화 모델(GGUF) 사용.  
- **효과**: 메모리 사용량 감소, 추론 속도 30~50% 향상
- **품질**: 4비트(Q4_K_M) 정도면 정보 추출 작업에서 품질 저하 미미.
- **예시**: `qwen2.5:14b` 대신 `qwen2.5:14b-q4_K_M` 사용

### 3) 프레임워크 설정 튜닝

프레임워크별 설정 파일 수정만으로 성능 향상 가능.
각 프레임워크마다 **필수 설정**(효과가 큰 상위 항목)을 우선 적용하고, 추가 최적화를 진행.

#### (a) MS GraphRAG

**설정 파일:** `settings.yaml`

**필수 설정 (우선 적용)**

| 설정 항목 | 설정값 | 효과 | 우선순위 |
|----------|--------|------|---------|
| 재추출(Gleaning) 비활성화 | `max_gleanings: 0` | 속도 약 2배 향상 | ⭐⭐⭐ |
| 청크 크기 확대 | `size: 2500` | LLM 호출 횟수 감소 | ⭐⭐ |
| Entity Types 제한 | `[organization, technology]` 등 2~4개 | LLM 집중도 향상 | ⭐⭐ |

**전체 설정 (효과 순)**

1. **재추출(Gleaning) 비활성화** ⭐⭐⭐
   - 기본값은 1(한 번 더 검사)이나, 0으로 설정 시 속도 약 2배 향상
   - 설정: `extract_graph: max_gleanings: 0`

2. **청크(Chunk) 크기 확대** ⭐⭐
   - LLM 컨텍스트 윈도우가 크다면(8K 이상), 청크 사이즈를 키워(예: 1200 → 2500) 전체 청크 수 감소
   - 설정: `chunking: size: 2500`
   - 청크 수 감소 시 LLM 호출 횟수 비례하여 감소

3. **Entity Types 최적화** ⭐⭐
   - 모든 엔티티 추출 대신 도메인 필수 타입만 정의
   - 설정: `extract_graph: entity_types: [organization, technology]` 등 2~4개로 제한

4. **동시 요청 수 조정** ⭐
   - 설정: `concurrent_requests: 3` (OLLAMA_NUM_PARALLEL과 맞춤)

5. **불필요한 출력 비활성화** ⭐
   - 시각화용 파일(graphml 등) 생성 비활성화
   - 설정: `snapshots: graphml: false`
   - 단, 임베딩은 검색에 필수이므로 반드시 활성화: `embeddings: true`

#### (b) LangChain + Neo4j

**설정 파일:** `config/settings.py`, `indexing/kg_builder.py`

**필수 설정 (우선 적용)**

| 설정 항목 | 설정값 | 효과 | 우선순위 |
|----------|--------|------|---------|
| 비동기 병렬 처리 | `aconvert_to_graph_documents()` | 5~10배 속도 향상 | ⭐⭐⭐ |
| strict_mode 활성화 | `strict_mode=True` | 불필요한 DB 쓰기 제거 | ⭐⭐ |
| baseEntityLabel 활성화 | `baseEntityLabel=True` | Neo4j 쓰기/조회 속도 향상 | ⭐⭐ |

**전체 설정 (효과 순)**

1. **비동기 병렬 처리** ⭐⭐⭐
   - 동기 `convert_to_graph_documents()` → 비동기 `aconvert_to_graph_documents()`로 전환
   - LLM 호출 대기 시간 최소화, 5~10배 속도 향상 기대
   - `asyncio.run()`으로 감싸서 기존 호출 인터페이스 유지

2. **strict_mode 활성화** ⭐⭐
   - 설정: `LLMGraphTransformer(strict_mode=True)`
   - `allowed_nodes`, `allowed_relationships`에 매칭되는 엔티티/관계만 저장
   - `False`(기본값)일 때는 허용 목록이 힌트일 뿐 모든 엔티티 저장
   - 불필요한 DB 쓰기 제거 + 그래프 품질 향상

3. **baseEntityLabel 활성화** ⭐⭐
   - 설정: `graph.add_graph_documents(baseEntityLabel=True)`
   - `__Entity__` 인덱스 라벨 자동 생성 → Neo4j 쓰기/조회 속도 향상
   - 기본값은 `False`이므로 명시적으로 활성화 필요

4. **청크(Chunk) 크기 축소** ⭐⭐
   - MS GraphRAG와 반대 전략: LLMGraphTransformer는 작은 청크에서 추출 정확도가 높음
   - 설정: `chunk_size: 800`, `chunk_overlap: 100` (기본 2000/200에서 축소)
   - 청크당 LLM 처리 시간 감소, 비동기 병렬과 조합 시 총 시간 단축

5. **allowed_nodes / allowed_relationships 제한** ⭐
   - 도메인에 맞는 엔티티 타입만 정의 (예: 개념, 기술, 라이브러리 등 3~7개)
   - LLM 프롬프트가 집중되어 파싱 실패 감소

#### (c) LightRAG

**설정 파일:** `config/settings.py`, `config/lightrag_init.py`

**필수 설정 (우선 적용)**

| 설정 항목 | 설정값 | 효과 | 우선순위 |
|----------|--------|------|---------|
| 재추출(Gleaning) 비활성화 | `entity_extract_max_gleaning=0` | 속도 약 2배 향상 | ⭐⭐⭐ |
| 배치 인덱싱 활용 | `rag.ainsert(list[str])` | 오버헤드 대폭 감소 | ⭐⭐⭐ |
| LLM 병렬 처리 조정 | `llm_model_max_async=2~3` | 병렬 처리 최적화 | ⭐⭐ |

**전체 설정 (효과 순)**

1. **재추출(Gleaning) 비활성화** ⭐⭐⭐
   - 엔티티 추출 후 누락 여부를 재검사하는 횟수
   - 기본값 1(한 번 재검사)을 0으로 설정 시 속도 약 2배 향상
   - 설정: `entity_extract_max_gleaning=0`
   - 품질이 중요한 경우 1 유지 권장

2. **배치 인덱싱 활용** ⭐⭐⭐
   - `rag.ainsert(list[str])`로 전체 문서를 한 번에 전달
   - 건별 호출 대비 파이프라인 오버헤드 대폭 감소
   - `max_parallel_insert=2` (기본값)로 동시 인덱싱 문서 수 제어

3. **LLM/임베딩 병렬 처리 조정** ⭐⭐
   - LLM 동시 요청: `llm_model_max_async=4` (기본값, Ollama 환경에선 2~3 권장)
   - 임베딩 동시 요청: `embedding_func_max_async=8` (기본값)
   - 임베딩 배치 크기: `embedding_batch_num=10` (기본값, 한 번에 10개 텍스트 임베딩)
   - Ollama 서버의 `OLLAMA_NUM_PARALLEL` 값과 맞춤 필요

4. **청크(Chunk) 크기 축소** ⭐⭐
   - LightRAG는 청크 단위로 LLM에 엔티티/관계 추출을 요청
   - 작은 청크일수록 추출 정확도 향상, 대신 LLM 호출 횟수 증가
   - 설정: `chunk_token_size=800`, `chunk_overlap_token_size=100` (기본 1200/100)
   - 배치 인덱싱과 조합 시 호출 횟수 증가 영향 최소화

5. **LLM 캐시 활성화** ⭐
   - 설정: `enable_llm_cache=True` (기본값)
   - 동일 청크 재인덱싱 시 LLM 호출 스킵
   - 엔티티 추출 캐시: `enable_llm_cache_for_entity_extract=True` (기본값)

6. **그래프 노드 수 제한** ⭐
   - 설정: `max_graph_nodes=1000` (기본값)
   - 대규모 데이터셋에서 그래프 크기가 커지면 검색 속도 저하
   - 도메인에 맞게 조정 (교육 콘텐츠는 500~1000 적정)

7. **코사인 유사도 임계값** ⭐
   - 설정: `cosine_threshold=0.2` (기본값)
   - 낮을수록 더 많은 결과 반환, 높일수록 정밀도 향상
   - 검색 품질과 응답 속도 간 트레이드오프
