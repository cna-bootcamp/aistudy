## 1. 개요

RAG(Retrieval-Augmented Generation) 시스템의 정확도는 **검색 품질**과 **생성 품질**  
두 가지 요소에 의해 결정됨. 검색 단계에서 관련 없는 문서가 반환되면  
아무리 뛰어난 LLM도 정확한 답변 생성 불가.

### 핵심 원칙

1. **한 번에 하나의 변수만 변경**: 테스트 간에 하나의 파라미터만 변경하여 정확한 원인 분석
2. **기준선 설정**: 최적화 전 현재 성능을 측정하여 비교 기준 마련
3. **반복적 개선**: 평가 → 분석 → 개선 사이클 반복

> **참고**: Google Cloud의 RAG 최적화 가이드에서  
> "Change only one variable at a time between test runs"를 핵심 원칙으로 강조함.
> - 출처: [Google Cloud - Optimizing RAG retrieval](https://cloud.google.com/blog/products/ai-machine-learning/optimizing-rag-retrieval)

## 2. 청킹 전략 (Chunking Strategies)

청킹은 RAG 파이프라인에서 가장 기초적이면서도 성능에 큰 영향을 미치는 요소임.

### 2.1 청킹의 필요성
관련 밀도가 높은 내용들만 찾아 LLM에 제공함으로써 결과의 품질을 높이기 위한 목적  
- **LLM 컨텍스트 윈도우 제한**: 대부분의 LLM은 컨텍스트 길이 제한이 있음
- **"바늘 찾기" 문제 방지**: 너무 큰 청크는 관련 정보가 희석됨
- **임베딩 모델 제한**: 대부분의 임베딩 모델은 8K 토큰 정도의 제한이 있음

### 2.2 주요 청킹 전략

#### 2.2.1 고정 크기 분할 (Fixed-Size Chunking)

```python
from langchain.text_splitter import CharacterTextSplitter

# 고정 크기 분할 (separator를 사용하지 않음)
splitter = CharacterTextSplitter(
    separator="",  # 구분자 없음 = 그냥 자름
    chunk_size=1000,
    chunk_overlap=200,
    length_function=len,
)

text = "여러분의 긴 문서 텍스트..."
chunks = splitter.split_text(text)
```

- **장점**: 구현 간단, 예측 가능한 청크 크기
- **단점**: 문장/문단 중간에서 잘릴 수 있음, 의미적 일관성 부족
- **권장 사용처**: 구조화되지 않은 일반 텍스트

#### 2.2.2 재귀적 문자 분할 (Recursive Character Text Splitter)

```python
from langchain.text_splitter import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=1000,
    chunk_overlap=200,
    separators=["\n\n", "\n", ".", " ", ""]  # 우선순위 순서
)
```

- **작동 방식**: 문단 → 문장 → 단어 순으로 계층적 분할 시도
- **장점**: 자연스러운 경계 유지, **범용 RAG의 기본 선택으로 권장**
- **단점**: 의미적 맥락을 고려하지 않음
- **권장 사용처**: 기사, 블로그 포스트, 일반 문서

> **권장**: Cohere와 Weaviate 문서에서  
> RecursiveCharacterTextSplitter를 **기본 전략**으로 추천함.
> - 출처: [Cohere - Chunking Strategies](https://docs.cohere.com/page/chunking-strategies)
> - 출처: [Weaviate - Chunking Strategies for RAG](https://weaviate.io/blog/chunking-strategies-for-rag)

#### 2.2.3 시맨틱 청킹 (Semantic Chunking)

```python
from langchain_experimental.text_splitter import SemanticChunker
from langchain_openai import OpenAIEmbeddings

# 임베딩 기반으로 의미적 경계 감지
embeddings = OpenAIEmbeddings()
semantic_chunker = SemanticChunker(
    embeddings,
    breakpoint_threshold_type="percentile",  # 분할 임계값 방식
    breakpoint_threshold_amount=95
)

chunks = semantic_chunker.split_documents(documents)
```

**동작 원리**:

**STEP 1: 인접 문장 간 유사도 계산**

```
문장1-2: 0.85
문장2-3: 0.90
문장3-4: 0.65  ← 유사도 급락
문장4-5: 0.88
문장5-6: 0.70  ← 유사도 급락
```

**STEP 2: 95 백분위수 계산**

유사도 값 정렬 및 P95 계산:
```
[0.65, 0.70, 0.85, 0.88, 0.90]
                          ↑
                     P95 ≈ 0.89
```

- 계산식: (95/100) × (n-1) = 0.95 × 4 = 3.8번째 인덱스
- 결과: 0.88과 0.90 사이 → 약 0.89

**STEP 3: 분할 기준 적용**

유사도가 P95(0.89)보다 **훨씬 낮은 지점**에서 분할:

```
[문장1, 문장2, 문장3] ─┐
                      0.65 (분할!)
[문장4, 문장5] ────────┐
                   0.70 (분할!)
[문장6] ──────────────┘

결과: 청크1=[문장1,2,3], 청크2=[문장4,5], 청크3=[문장6]
```

**breakpoint_threshold_type 옵션**:

| 옵션 | 설명 |
|------|------|
| `percentile` | 유사도 분포의 백분위수 기준 (기본값) |
| `standard_deviation` | 평균에서 표준편차 N배 이상 차이 |
| `interquartile` | 사분위 범위(IQR) 기준 |

- **장점**: 높은 의미적 일관성, 주제별 자연스러운 분할, chunk_size 수동 설정 불필요, 문맥 손실 최소화
- **단점**: 계산 비용 높음 (임베딩 API 필요), 청크 크기가 불균일할 수 있음, 처리 시간 증가
- **권장 사용처**: 학술 논문, 기술 문서, 복잡한 구조의 텍스트, 비구조 문서 (채팅, 블로그)

> **참고**: ACL 2025 논문에서 Recursive Semantic Chunking(RSC)이  
> 기존 방법보다 우수한 성능을 보임을 입증함.
> - 출처: [ACL 2025 - The Chunking Paradigm: Recursive Semantic for RAG](https://aclanthology.org/2025.icnlsp-1.15.pdf)

#### 2.2.4 문서 구조 기반 분할 (Document-Specific Splitting)

```python
# Markdown 헤더 기반 분할
from langchain.text_splitter import MarkdownHeaderTextSplitter

headers_to_split_on = [
    ("#", "Header 1"),
    ("##", "Header 2"),
    ("###", "Header 3"),
]
splitter = MarkdownHeaderTextSplitter(headers_to_split_on=headers_to_split_on)
```

- **장점**: 문서 구조를 활용한 자연스러운 분할, 메타데이터 보존
- **권장 사용처**: Markdown, HTML, 코드 파일


#### 2.2.5 계층적 청킹 (Hierarchical Chunking)

작은 청크로 검색 후, 필요시 **상위 청크로 자동 병합**하는 방식임

```
계층 구조:
Level 0 (2048자): [==========큰 청크==========]
Level 1 (1024자): [====청크1====][====청크2====]
Level 2 (512자):  [==A==][==B==][==C==][==D==]

검색 흐름:
1. Level 2에서 정밀 검색 → [B] 매칭
2. [B]의 형제 [A]도 관련 있으면 → Level 1 [청크1]로 병합하여 반환
```

**LlamaIndex 구현**:

```python
from llama_index.core.node_parser import HierarchicalNodeParser
from llama_index.core.retrievers import AutoMergingRetriever

# 계층적 청크 생성 (512 → 1024 → 2048)
node_parser = HierarchicalNodeParser.from_defaults(
    chunk_sizes=[512, 1024, 2048]
)

# 자동 병합 검색기
retriever = AutoMergingRetriever(
    vector_retriever=base_retriever,
    storage_context=storage_context,
    simple_ratio_thresh=0.5  # 병합 임계값: 0.5 = 60%
)
```

**병합 동작 예시** (`simple_ratio_thresh=0.5`):

```
부모 청크 [청크1]
  ├─ 자식 [A]  ← 검색됨
  └─ 자식 [B]  ← 검색됨

판단: 2개 중 2개 검색 = 100% (≥ 60%)
결과: [A], [B] 대신 부모 [청크1] 전체 반환

---

부모 청크 [청크2]
  ├─ 자식 [C]  ← 검색됨
  ├─ 자식 [D]
  ├─ 자식 [E]
  └─ 자식 [F]

판단: 4개 중 1개 검색 = 25% (< 60%)
결과: [C]만 반환 (병합 안 함)
```

**왜 병합하는가?**: 여러 자식이 검색되면 해당 영역 전체가 관련 있다는 의미이므로, 더 큰 부모 청크로 문맥 제공

| 장점 | 단점 |
|------|------|
| 검색 정밀도와 맥락 둘 다 확보 | 구현 복잡도 높음 |
| 동적으로 청크 크기 조절 | 저장 공간 증가 (여러 레벨) |


### 2.3 청크 크기 권장사항

| 모델/사용 사례 | 권장 청크 크기 | 오버랩 |
|---------------|--------------|-------|
| 일반적인 QA | 500-1000 토큰 | 10-20% |
| 정밀 검색 필요 | 200-500 토큰 | 10-15% |
| 요약/분석 | 1000-2000 토큰 | 5-10% |
| 코드 | 함수/클래스 단위 | 컨텍스트에 따라 |

**프로토타입 시작점**:

프로토타입 단계에서는 **chunk_size=500, overlap=100**으로 시작하는 것을 권장함

이 값은 대부분의 문서 타입에서 합리적인 출발점임:
- 너무 작지 않아 문맥 보존
- 너무 크지 않아 검색 정확도 유지
- LLM 컨텍스트에 적합한 크기

> **실무 권장**: 기본값으로 빠르게 시작한 후, 객관적 평가 지표(RAGAS 등)로 최적화

> **실험적 권장값**: Unstructured.io에서는
> **250 토큰(약 1000자)**을 실험 시작점으로 권장함.
> - 출처: [Unstructured - Chunking for RAG Best Practices](https://unstructured.io/blog/chunking-for-rag-best-practices)

### 2.4 오버랩 전략

청크 간 오버랩은 문맥 손실을 방지하는 중요한 기법임.

#### 오버랩 결정 Factor

| Factor | 설명 | 오버랩 영향 |
|--------|------|-----------|
| **청크 크기** | 청크가 작을수록 경계에서 정보 손실 위험 높음 | 작음 → ↑ / 큼 → ↓ |
| **문맥 의존도** | 문장 간 연결성이 강할수록 연속성 중요 | 높음 → ↑ / 낮음 → ↓ |

#### Factor 기반 오버랩 권장값

| 청크 크기 | 문맥 의존도 | 권장 오버랩 |
|----------|-----------|-----------|
| 작음 (200-400) | 높음 | **20%** |
| 중간 (500-800) | 중간 | **15%** |
| 큼 (1000+) | 낮음 | **10%** |

**오버랩 계산식**: `overlap = chunk_size × 권장_비율`

#### 실무 예시

| 문서 유형 | 특성 | 권장 오버랩 |
|----------|------|-----------|
| 법률 문서 | 작은 청크 + 문맥 의존 높음 | 20% |
| FAQ | 중간 청크 + 정보 독립적 | 10% |
| 기술 문서 | 중간 청크 + 중간 의존도 | 15% |

```python
# 오버랩 설정 예시

# 또는 문장 단위 오버랩
```

### 2.5 파라미터 최적화 (실무 권장)

**RAGAS + Grid Search**를 사용하여 여러 chunk_size를 실험하고 **객관적 평가 지표**로 최적값을 선택함

```python
from ragas import evaluate
from ragas.metrics import faithfulness, answer_relevancy, context_precision

# 테스트할 chunk_size 후보
chunk_sizes = [200, 500, 800, 1000, 1500]
results = {}

for size in chunk_sizes:
    # 1. 해당 크기로 인덱싱
    vectorstore = build_index(documents, chunk_size=size)

    # 2. 테스트 질문으로 RAG 실행
    responses = run_rag(vectorstore, test_questions)

    # 3. RAGAS 평가
    score = evaluate(
        dataset=responses,
        metrics=[faithfulness, answer_relevancy, context_precision]
    )
    results[size] = score

# 최적 chunk_size 선택
best_size = max(results, key=lambda x: results[x]['answer_relevancy'])
print(f"최적 chunk_size: {best_size}")
```

| 장점 | 단점 |
|------|------|
| 객관적 지표 기반 | 테스트셋 필요 |
| 도메인 맞춤 최적화 | 시간 소요 (여러 번 실험) |
| 재현 가능한 결과 | 평가 비용 (LLM 호출) |

### 2.6 방법 선택 가이드

| 상황 | 권장 방법 |
|------|----------|
| **빠른 프로토타이핑** | RecursiveCharacterTextSplitter + 수동 조정 |

#### 3.2.3 Mafin (Model Augmented Fine-tuning)

OpenAI 같은 API 기반 임베딩 모델은 직접 파인튜닝할 수 없는 블랙박스임.
Mafin은 이런 모델 위에 **작은 학습 가능한 변환 모델**을 추가하여 도메인에 맞게 보정하는 기법임.

```
[API 임베딩] → [작은 변환 모델] → [도메인 특화 임베딩]
   (고정)        (학습 가능)         (개선된 결과)
```

**장점**:
- API 임베딩 모델은 그대로 사용하면서 도메인 적응 가능
- 비용 효율적: 전체 모델 재학습 불필요

**구현 예시**:

```python
import numpy as np
from openai import OpenAI
import torch
import torch.nn as nn

# 1. API 기반 임베딩 (고정, 학습 불가)
client = OpenAI()
def get_api_embedding(text):
    response = client.embeddings.create(
        model="text-embedding-3-small",
        input=text
    )
    return np.array(response.data[0].embedding)

# 2. 작은 변환 모델 정의 (학습 가능)
class MafinAdapter(nn.Module):
    def __init__(self, input_dim=1536, hidden_dim=256, output_dim=1536):
        super().__init__()
        self.adapter = nn.Sequential(
            nn.Linear(input_dim, hidden_dim),
            nn.ReLU(),
            nn.Linear(hidden_dim, output_dim)
        )

    def forward(self, x):
        return self.adapter(x)

# 3. 사용 흐름
adapter = MafinAdapter()

# 원본 API 임베딩 생성
api_embedding = get_api_embedding("의료용 MRI 장비")
api_tensor = torch.FloatTensor(api_embedding)

# 도메인 특화 임베딩으로 변환
domain_embedding = adapter(api_tensor)

# 4. 도메인 데이터로 adapter만 학습
# (API 모델은 그대로, adapter만 파인튜닝)
optimizer = torch.optim.Adam(adapter.parameters())
for epoch in range(num_epochs):
    # 도메인 특화 쿼리-문서 쌍으로 학습
    loss = contrastive_loss(adapter, query_doc_pairs)
    optimizer.step()
```

## 4. 벡터 스토어 파라미터 튜닝

### 4.1 HNSW 기반 Vector DB
**1)개요**     
Chroma, Qdrant, Weaviate, Milvus, FAISS 

HNSW(Hierarchical Navigable Small World)는 대부분의 Vector DB에서 사용하는
근사 최근접 이웃(ANN) 검색 알고리즘임.

```
HNSW 구조:
Layer 2:  [A] ─────────────────── [B]     (상위: 넓은 탐색)
           │                       │
Layer 1:  [A] ─── [C] ─── [D] ─── [B]     (중간: 세부 탐색)
           │       │       │       │
Layer 0:  [A]-[E]-[C]-[F]-[D]-[G]-[B]     (하위: 정밀 탐색)
```

- **계층적 그래프 구조**: 상위 레이어에서 대략적 탐색 후 하위 레이어로 정밀화
- **Small World 특성**: 소수의 연결로 빠른 탐색 가능
- **장점**: 높은 재현율(Recall: 찾아야 할 문서 중 실제 찾은 문서의 비율)과 빠른 검색 속도 균형

**2)주요 튜닝 파라미터**   
 
| 파라미터 | 설명 | 기본값 | 영향 |
|----------|------|--------|------|
| **M** | 노드(청크)당 최대 연결 노드(청크)수 | 16 | ↑ 재현율, ↑ 메모리, ↓ 속도 |
| **ef_construction** | 인덱스 구축 시 얼마나 많은 후보(청크)를 탐색 | 100-200 | ↑ 인덱스 품질, ↑ 구축 시간 |
| **ef_search** | 검색 시 얼마나 많은 후보(청크)를 탐색 | 50-100 | ↑ 재현율, ↓ 검색 속도 |

> **ef (exploration factor)**: 탐색할 후보 개수를 의미하는 파라미터. 값이 클수록 더 많은 후보를 탐색하여 정확도는 높아지지만 속도는 느려짐

**파라미터 관계**:
```
ef_search ≥ top_k (검색할 문서 수)
ef_construction ≥ ef_search (권장)
```

**3)튜닝 권장사항**     

| 사용 사례 | M | ef_construction | ef_search | 특징 |
|----------|---|-----------------|-----------|------|
| 빠른 검색 우선 | 8-12 | 100 | 40-60 | 속도 ↑, 정확도 ↓ |
| 균형 (기본) | 16 | 200 | 100 | 일반적 RAG 용도 |
| 높은 정확도 | 32-64 | 400 | 200+ | 정밀 검색, 속도 ↓ |

> **권장**: RAG 시스템에서는 **M=16, ef_construction=200, ef_search=100**으로 시작 후  
> 재현율(Recall)과 응답 시간을 측정하며 조정

**데이터 규모에 따른 HNSW 효과**:

| 청크 개수 (벡터 수) | HNSW 효과 |
|---------------------|----------|
| ~10,000 | 미미함 |
| 10,000~100,000 | 효과 있음 |
| 100,000+ | 필수 |

### 4.2 IVF 기반 Vector DB
**1)개요**  
FAISS, Milvus, Pinecone, Weaviate

IVF(Inverted File Index)는 벡터 공간을 여러 클러스터로 분할하여
검색 범위를 줄이는 근사 최근접 이웃(ANN: Approximate Nearest Neighbors) 검색 알고리즘임.

```
IVF 구조:
전체 벡터 공간:
┌──────────┬──────────┬──────────┬──────────┐
│Cluster 0 │Cluster 1 │Cluster 2 │Cluster 3 │
│  ● ●     │    ● ●   │  ●       │  ● ● ●   │
│    ●     │  ●       │    ● ●   │    ●     │
│  ●       │    ● ●   │  ●   ●   │  ● ●     │
│    ★     │    ★     │    ★     │    ★     │
│(centroid)│(centroid)│(centroid)│(centroid)│
└──────────┴──────────┴──────────┴──────────┘

검색 시 (nprobe=2):
Query → 가장 가까운 centroid 2개의 클러스터만 탐색
```

- **클러스터 기반 분할**: K-Means로 벡터를 클러스터로 분류 후 centroid(중심점)와 비교하여 탐색 범위 축소
- **Inverted Index 구조**: 각 클러스터에 속한 벡터 목록을 역인덱스로 관리
- **장점**: 대규모 데이터에서 빠른 검색 속도, 메모리 효율적

**2)주요 튜닝 파라미터**  

| 파라미터 | 설명 | 기본값 | 영향 |
|----------|------|--------|------|
| **nlist** | 전체 벡터를 나눌 클러스터 수 | 100-1000 | ↑ 검색 속도, ↓ 재현율 (너무 크면) |
| **nprobe** | 검색 시 탐색할 클러스터 수 | 1-10 | ↑ 재현율, ↓ 검색 속도 |

> **nlist와 nprobe의 관계**: nprobe가 nlist와 같으면 전수 검색(brute-force)과 동일.  
> nprobe를 늘릴수록 정확도는 높아지지만 속도는 느려짐

**파라미터 관계**:
```
nprobe ≤ nlist (nprobe는 nlist를 초과할 수 없음)
nlist ≈ sqrt(총 벡터 수) (권장 공식)
```

**3)튜닝 권장사항**  

| 사용 사례 | nlist | nprobe | 특징 |
|----------|-------|--------|------|
| 빠른 검색 우선 | 1000 | 1-5 | 속도 ↑, 정확도 ↓ |
| 균형 (기본) | 100-256 | 10-20 | 일반적 RAG 용도 |
| 높은 정확도 | 50-100 | 30-50 | 정밀 검색, 속도 ↓ |

> **권장**: RAG 시스템에서는 **nlist=sqrt(N), nprobe=nlist의 5~10%**로 시작 후  
> 재현율(Recall)과 응답 시간을 측정하며 조정

**데이터 규모에 따른 IVF 효과**:

| 청크 개수 (벡터 수) | nlist 권장값 | IVF 효과 |
|---------------------|-------------|----------|
| ~10,000 | 100 | 미미함 |
| 10,000~100,000 | 100-316 | 효과 있음 |
| 100,000~1,000,000 | 316-1000 | 필수 |
| 1,000,000+ | 1000+ | 필수 (PQ 병용 권장) |

## 5. 쿼리 최적화 (Query Optimization)

### 쿼리 최적화 기법 비교

| 기법 | 사용 시기 | 활용 사례 | 특징 |
|------|----------|-----------|------|
| **Query Rewriting** | 사용자 질문을 검색에 적합하게 변형해야 할때 | • 구어체 질문 → 검색 키워드<br>• 긴 질문문장 → 핵심 개념 추출<br>• "~을 알려줘" 같은 지시사항 제거 | 가장 기본적인 전처리<br>모든 쿼리에 적용 가능 |
| **Multi-Query** | 단일 쿼리로 충분한 문서를 찾기 어려울 때 | • 다양한 표현으로 검색 필요<br>• 질문의 여러 측면 커버<br>• 검색 재현율(Recall) 향상 | 여러 변형 쿼리 자동 생성<br>검색 커버리지 확대 |
| **HyDE** | 쿼리가 짧고 모호하거나 전문 용어 검색 시 | • 짧은 질문: "RAG란?"<br>• 전문 용어 검색<br>• 쿼리-문서 간 어휘 불일치 해소 | 가상 답변 생성으로 검색<br>의미적 정렬 개선 |
| **Step-back** | 구체적 질문에 개념적 배경 필요할 때 | • 특정 API 파라미터 질문<br>• 구현 디테일 + 원리 설명 필요<br>• 컨텍스트가 풍부한 답변 요구 | 추상적 질문 생성<br>개념/원리 문서 검색 |

### 조합 전략

실무에서는 여러 기법을 조합하여 사용하는 것이 효과적임:

```python
# 1단계: Query Rewriting (기본 정제)
rewritten = rewrite_chain.run(query=user_question)

# 2단계: Multi-Query (변형 쿼리 생성)
multi_retriever = MultiQueryRetriever.from_llm(base_retriever, llm)
docs = multi_retriever.get_relevant_documents(rewritten)

# 또는 HyDE + Step-back 조합
hyde_docs = hyde_retriever.get_relevant_documents(rewritten)
stepback_query = stepback_chain.run(query=rewritten)
stepback_docs = retriever.get_relevant_documents(stepback_query)
```

### 5.1 Query Rewriting (쿼리 재작성)

사용자 질문을 검색에 최적화된 형태로 재작성함.
지시사항이나 불필요한 단어를 제거하고 핵심 개념과 키워드만 추출함.

```python
from langchain.chains import LLMChain
from langchain.prompts import PromptTemplate

# 쿼리 재작성 프롬프트
template = """다음 사용자 질문을 벡터 검색에 최적화된 검색 쿼리로 변환하세요.
지시사항이나 불필요한 단어를 제거하고 핵심 개념과 키워드만 추출하세요.

사용자 질문: {query}
검색 쿼리:"""

prompt = PromptTemplate(template=template, input_variables=["query"])
rewrite_chain = LLMChain(llm=llm, prompt=prompt)

# 사용 예시
original = "Python으로 머신러닝을 하려면 어떤 라이브러리를 사용해야 하나요?"
rewritten = rewrite_chain.run(query=original)
# → "Python 머신러닝 라이브러리"
```

**활용 시나리오**:
- 구어체 질문 → 검색 키워드 변환
- 긴 질문 → 핵심 개념 추출
- 애매한 표현 → 명확한 용어 변환

### 5.2 Multi-Query

원본 쿼리에서 여러 변형 쿼리를 생성하거나 관련 키워드를 추가하여 검색 커버리지를 높임.

#### 5.2.1 MultiQueryRetriever (LangChain)

LangChain의 `MultiQueryRetriever`는 LLM을 사용하여 자동으로 여러 변형 쿼리를 생성함:

```python
from langchain.retrievers.multi_query import MultiQueryRetriever

retriever = MultiQueryRetriever.from_llm(
    retriever=base_retriever,
    llm=llm
)

# 내부적으로 다음과 같이 작동:
# 1. LLM이 원본 쿼리에서 3-5개의 변형 쿼리 생성
# 2. 각 쿼리로 검색 수행
# 3. 결과를 중복 제거 후 병합

# 사용 예시
docs = retriever.get_relevant_documents("Python의 역사와 활용")
# → "Python의 역사", "Python 활용 분야", "Python 개발 배경" 등 여러 쿼리로 검색
```

#### 5.2.2 키워드 확장 방식 (선택사항)

LLM을 직접 사용하여 쿼리에 관련 키워드를 추가하는 방식:

```python
from langchain.chains import LLMChain
from langchain.prompts import PromptTemplate

# 키워드 확장 프롬프트
template = """다음 쿼리에 대해 검색을 개선하기 위한 관련 키워드를 추가하세요.
원본 쿼리: {query}

확장된 쿼리 (관련 키워드 포함):"""

prompt = PromptTemplate(template=template, input_variables=["query"])
expansion_chain = LLMChain(llm=llm, prompt=prompt)

# 사용
expanded_query = expansion_chain.run(query="Python 머신러닝")
# → "Python 머신러닝 scikit-learn tensorflow numpy pandas 데이터분석"
```

### 5.3 HyDE (Hypothetical Document Embeddings)

HyDE는 쿼리 대신 **가상의 답변 문서**를 생성하여 검색하는 기법임.

```
[사용자 쿼리] → [LLM: 가상 답변 생성] → [가상 답변 임베딩] → [검색]
```

#### 5.3.1 HyDE 구현

```python
from langchain.chains import HypotheticalDocumentEmbedder
from langchain_openai import OpenAI, OpenAIEmbeddings

# HyDE 체인 생성
hyde = HypotheticalDocumentEmbedder.from_llm(
    llm=OpenAI(),
    base_embeddings=OpenAIEmbeddings(),
    prompt_key="web_search"  # 또는 custom prompt
)

# 검색 수행
hyde_embedding = hyde.embed_query("What is the capital of France?")
```

#### 5.3.2 HyDE 장단점

**장점**:
- 짧고 모호한 쿼리의 의미적 정렬 개선
- 제로샷 검색 성능 향상
- 쿼리-문서 간 어휘 불일치 해소

**단점**:
- LLM 호출 추가로 지연 시간 증가
- LLM이 부정확한 가상 답변 생성 시 오류 전파
- 비용 증가

> **실험 결과**: KorQuAD 1.0에서 HyDE-reranked 방식이 72% ACC@1을 달성 (Query-only: 46%)
> - 출처: [GitHub - HyDE-RAG Experiment](https://github.com/millet04/HyDE-RAG)

### 5.4 Step-back Prompting

구체적인 질문을 더 추상적이고 일반적인 질문으로 변환하여 검색 품질을 향상시키는 기법.
세부 사항에 집중된 질문을 높은 수준의 개념 질문으로 "한 걸음 물러나서(step back)" 재구성함.

```python
from langchain.chains import LLMChain
from langchain.prompts import PromptTemplate

# Step-back 프롬프트
template = """다음 질문에 대해 더 일반적이고 추상적인 질문을 생성하세요.
구체적인 세부사항 대신 근본적인 개념이나 원리에 초점을 맞추세요.

원본 질문: {query}
Step-back 질문:"""

prompt = PromptTemplate(template=template, input_variables=["query"])
stepback_chain = LLMChain(llm=llm, prompt=prompt)

# 사용 예시
original = "Python 3.11에서 asyncio.gather()의 return_exceptions 파라미터는 어떻게 동작하나요?"
stepback = stepback_chain.run(query=original)
# → "Python에서 비동기 프로그래밍의 예외 처리 원리는 무엇인가요?"

# 두 질문으로 모두 검색하여 결합
original_docs = retriever.get_relevant_documents(original)
stepback_docs = retriever.get_relevant_documents(stepback)
combined_docs = original_docs + stepback_docs
```

**장점**:
- 구체적 질문만으로는 찾기 어려운 개념적 설명 문서 검색 가능
- 원리/배경 지식과 구체적 구현 정보를 함께 제공
- 컨텍스트가 더 풍부한 답변 생성

**예시**:

| 원본 질문 (구체적) | Step-back 질문 (추상적) |
|-------------------|------------------------|
| "Kubernetes에서 livenessProbe의 timeoutSeconds 기본값은?" | "Kubernetes에서 컨테이너 헬스체크는 어떻게 동작하나요?" |
| "React 18의 useTransition hook은 언제 사용하나요?" | "React에서 UI 렌더링 우선순위는 어떻게 관리되나요?" |
| "PostgreSQL의 JSONB 인덱싱은 GIN과 GiST 중 무엇이 빠른가요?" | "PostgreSQL에서 JSON 데이터 검색 최적화 방법은?" |

## 6. 하이브리드 검색 전략

### 6.1 하이브리드 검색의 필요성

순수 벡터 검색의 한계:
- **전문 용어/희소 표현 검색 한계**: 도메인 특화 전문 용어, 신조어, 희소 표현 등
- **정확한 키워드 매칭 실패**: 제품 코드, ID, 약어 등

### 6.2 하이브리드 검색 구성

```
하이브리드 검색 = Dense (벡터) 검색 + Sparse (키워드) 검색
```

#### 6.2.1 Dense 검색 (벡터 검색)

- 의미적 유사도 기반
- 동의어, 유사 표현 처리 가능
- 오타에 강건함

#### 6.2.2 Sparse 검색 (BM25)

```python
from langchain.retrievers import BM25Retriever

bm25_retriever = BM25Retriever.from_documents(documents)
bm25_retriever.k = 5
```

- 키워드 정확 매칭에 강함
- 약어, 코드, 고유명사에 효과적
- 계산 비용이 낮음

### 6.3 결과 융합 전략

Dense와 Sparse 검색 결과를 결합하는 두 가지 주요 방법

#### 6.3.1 가중 조합 (Weighted Combination)

각 검색 방식의 점수를 가중치로 결합하는 방식

**공식**:
```
H = (1 - α) × K + α × V

여기서:
- H: 최종 하이브리드 점수
- K: 키워드 검색 점수 (정규화 필요)
- V: 벡터 검색 점수 (정규화 필요)
- α: 가중치 (0-1, 보통 0.5-0.7)
```

**특징**:
- 각 검색 방식의 점수를 직접 결합
- 점수 정규화 필요 (각 검색 엔진마다 점수 범위가 다름)
- 가중치 α 조정으로 검색 방식 간 균형 제어

**LangChain 구현**:

```python
from langchain.retrievers import EnsembleRetriever

# 앙상블 리트리버 생성
ensemble_retriever = EnsembleRetriever(
    retrievers=[bm25_retriever, vector_retriever],
    weights=[0.4, 0.6]  # BM25 40%, Vector 60%
)

# 검색 수행
results = ensemble_retriever.invoke("쿼리")
```

#### 6.3.2 RRF (Reciprocal Rank Fusion)

검색 결과의 **순위**를 기반으로 융합하는 방식

**개념**:
- 점수 대신 순위(rank)를 사용하여 결과 융합
- 점수 정규화 불필요 (순위만 사용)
- 각 검색 방식에서 상위 랭크된 문서에 높은 점수 부여

**공식**:
```
score(d) = Σ 1 / (k + rank(d))

여기서:
- d: 문서
- rank(d): 해당 검색에서 문서 d의 순위 (0부터 시작)
- k: 상수 (기본값 60, 순위 차이 완화용)
```

**장점**:
- 점수 정규화 불필요
- 여러 검색 방식 결합에 효과적
- 구현 간단, 안정적 성능

**구현 예시**:

```python
def reciprocal_rank_fusion(results_list, k=60):
    """
    여러 검색 결과를 RRF로 융합

    Args:
        results_list: [[doc1, doc2, ...], [doc3, doc1, ...], ...]
        k: 상수 (기본값 60)
    """
    fused_scores = {}
    for results in results_list:
        for rank, doc in enumerate(results):
            if doc not in fused_scores:
                fused_scores[doc] = 0
            fused_scores[doc] += 1 / (k + rank + 1)

    return sorted(fused_scores.items(), key=lambda x: x[1], reverse=True)

# 사용 예시
bm25_results = ["doc1", "doc3", "doc2"]  # BM25 검색 결과
vector_results = ["doc2", "doc1", "doc4"]  # 벡터 검색 결과

final_results = reciprocal_rank_fusion([bm25_results, vector_results])
# 결과: [('doc1', 0.0325), ('doc2', 0.0323), ('doc3', 0.0161), ('doc4', 0.0159)]
```

**핵심**: 두 검색 방식에서 모두 나타난 문서(doc1, doc2)가 한 곳에서만 나타난 문서(doc3, doc4)보다 높은 점수를 받음

> **권장**: RRF는 점수 정규화 없이 다양한 검색 결과를 효과적으로 융합함.
> - 출처: [Qdrant - Hybrid Search](https://qdrant.tech/articles/hybrid-search)

## 7. 리랭킹 (Reranking)

### 7.1 리랭킹의 역할

리랭킹은 초기 검색 결과를 더 정교한 모델로 재정렬하여  
최종 상위 K개 문서의 관련성을 높임.

```
[쿼리] → [1단계: 후보 검색 (Top-100)] → [2단계: 리랭킹 (Top-10)] → [LLM]
```

### 7.2 전용 리랭킹 모델 (로컬)

로컬 환경에서 직접 실행하는 전용 리랭킹 모델

#### 7.2.1 Cross-Encoder

Cross-Encoder는 쿼리와 문서를 함께 인코딩하여 관련성 점수를 직접 계산함.

```python
from sentence_transformers import CrossEncoder

# 리랭커 모델 로드
reranker = CrossEncoder('cross-encoder/ms-marco-MiniLM-L-6-v2')

# 리랭킹 수행
pairs = [(query, doc.page_content) for doc in initial_results]
scores = reranker.predict(pairs)

# 점수 기준 정렬
reranked = sorted(zip(initial_results, scores), key=lambda x: x[1], reverse=True)
```

**주요 Cross-Encoder 모델**:

| 모델 | 성능 | 속도 | 사용 사례 |
|-----|-----|-----|---------|
| ms-marco-MiniLM-L-6-v2 | 중간 | 빠름 | 실시간 검색 |
| BAAI/bge-reranker-v2-m3 | 높음 | 중간 | 정밀 검색 |
| dragonkue/bge-reranker-v2-m3-ko | 높음 | 중간 | bge-reranker-v2-m3의 한국어 모델 |
| cross-encoder/ms-marco-TinyBERT-L-2-v2 | 낮음 | 매우 빠름 | 대용량 처리 |

> 출처: [SBERT - Pre-trained Cross-Encoders](https://www.sbert.net/docs/pretrained_cross-encoders.html)

#### 7.2.2 ColBERT

ColBERT은 토큰 수준의 상호작용을 통해 더 정밀한 매칭을 수행함:

```python

# ColBERT 모델 초기화

    "JavaScript는 웹 개발을 위한 스크립팅 언어입니다.",
    "Python은 데이터 과학과 AI 분야에서 널리 사용됩니다."
]

# ColBERT 리랭킹: 토큰(보통 단어)별 유사도 계산 → MaxSim 연산

    query=query,
    documents=initial_results,
    k=3  # 상위 3개 반환
)

# 결과: [{'content': ..., 'score': ..., 'rank': ...}, ...]
for result in reranked:
```

### 7.4 범용 LLM 활용

#### 7.4.1 LLM 기반 Re-ranking

로컬 LLM 또는 API 기반 LLM을 활용하여 검색 결과를 재정렬하는 방식임.

**작동 원리**:

```
1. 벡터 검색으로 후보 문서 추출 (Top-N)
2. LLM에 쿼리와 각 문서를 제시하여 관련성 점수 산출
3. LLM 점수와 벡터 점수를 가중 결합
4. 최종 점수로 재정렬
```

- **벡터 점수(vector_score)**: 1단계 벡터 검색에서 반환된 코사인 유사도 점수.  
  쿼리 임베딩과 문서 임베딩 간의 유사도를 나타내며, 일반적으로 0~1 범위임.
- **LLM 점수(llm_score)**: LLM이 쿼리-문서 쌍의 관련성을 평가한 점수.  
  프롬프트 기반으로 0~100 범위의 점수를 산출함.
- **가중 결합**: 두 점수를 가중치로 결합하여 최종 점수 산출.
  예: `final_score = llm_score * 0.7 + vector_score * 100 * 0.3`

**구현 예시**:

```python
def rerank_with_llm(query: str, results: list, llm_client) -> list:
    """LLM 기반 리랭킹 수행"""
    scored_results = []
    
    for result in results:
        content = result.get("content", "")
        
        # 짧은 청크 필터링 (노이즈 제거)
        if len(content) < 150:
            continue
            
        prompt = f"""
        질문과 문서의 관련성을 0-100 점수로 평가하세요.
        
        질문: {query}
        문서: {content[:500]}
        
        점수만 숫자로 응답:
        """
        
        response = llm_client.generate(prompt)
        llm_score = parse_score(response)
        
        # 가중 결합: LLM 70% + Vector 30%
        vector_score = result.get("score", 0)
        final_score = llm_score * 0.7 + vector_score * 100 * 0.3
        
        scored_results.append({
            **result,
            "llm_score": llm_score,
            "final_score": final_score
        })
    
    return sorted(scored_results, key=lambda x: x["final_score"], reverse=True)
```

**짧은 청크 필터링**:

| 파라미터 | 권장값 | 설명 |
|---------|-------|------|
| min_content_length | 100-200자 | 최소 청크 길이 |
| 필터링 시점 | 리랭킹 전 | 노이즈 사전 제거 |

짧은 청크의 문제점:
- 문맥 정보 부족으로 LLM 평가 정확도 저하
- 헤더, 목록 마커 등 비본질적 콘텐츠 포함 가능성
- 벡터 유사도는 높으나 실제 관련성 낮은 경우 다수

**장단점**:

**장점**:
- Cross-Encoder 대비 유연한 평가 기준 적용 가능
- 도메인 특화 프롬프트로 정밀도 향상
- 로컬 LLM 사용 시 비용 절감

**단점**:
- API 호출 비용 및 지연 시간
- 프롬프트 엔지니어링 필요
- 일관성 있는 점수 산출을 위한 튜닝 필요

## 8. 평가 및 메트릭

### 8.1 RAGAS 프레임워크

RAGAS(Retrieval-Augmented Generation Assessment)는 RAG 파이프라인의 자동 평가를 위한 오픈소스 프레임워크임.
검색(Retrieval)과 생성(Generation) 두 단계의 품질을 다양한 메트릭으로 측정.

#### 8.1.1 동작 원리


#### 8.1.2 주요 메트릭
검색 메트릭스 **Precision**과 **Recall**, 생성 메트릭스 **Faithfulness**와 **Relevancy**가 가장 중요한 지표임

| 지표 | 측정 대상 | 설명 |
|------|----------|------|
| **Context Precision** | 검색 정밀도 | 검색 결과에서 질문 연관 청크가 얼마나 상위에 있나?
 |
| **Context Recall** | 검색 재현율 | 검색 결과의 청크에 정답이 얼마나 많이 존재하는가? |
| Entity Recall | 검색 | 정답의 핵심 엔티티가 검색되었는지 |
| **Faithfulness** | 근거성 | 생성된 답변이 검색된 컨텍스트에 기반하고 있는가 |
| **Answer Relevance** | 답변 적절성 | 답변이 사용자의 질문에
얼마나 관련 되는가? |
| Factual Correctness | 생성 | 답변의 사실적 정확성 |
| Noise Sensitivity | 검색 | 노이즈에 대한 민감도 |

**암기팁:위-정-출-관**    
**위**에 깔리고 **정**답 많이 있고, **출**처와 **관**련도가 높은가?   
  
#### 8.1.3 점수 해석 가이드

| 점수 범위 | 해석 | 조치 |
|-----------|------|------|
| 0.9 ~ 1.0 | 매우 우수 | 현 상태 유지 |
| 0.7 ~ 0.9 | 양호 | 세부 튜닝 고려 |
| 0.5 ~ 0.7 | 개선 필요 | 파이프라인 점검 필요 |
| 0.0 ~ 0.5 | 심각한 문제 | 근본적 재설계 필요 |

```
    ]

    generation_metrics = [
        Faithfulness(),          # 답변이 컨텍스트에 근거하는지
        ResponseRelevancy(),     # 답변이 질문과 관련 있는지
        FactualCorrectness(),    # 사실적 정확성
    ]

    metrics = retrieval_metrics + generation_metrics
    
    # 평가 실행
    result = evaluate(
        dataset=eval_dataset,   # 테스트 데이터셋트(질문,정답,예상출처)
        metrics=metrics,        # 평가지표 
        llm=llm_wrapper,
        embeddings=embeddings_wrapper,
    )

    return result
```

**종합 점수 계산 방식**:
- 검색 점수 = (Context Precision + Context Recall + Entity Recall) / 3
- 생성 점수 = (Faithfulness + Answer Relevancy + Factual Correctness) / 3
- 종합 점수 = 검색 점수 × 0.4 + 생성 점수 × 0.6
  (생성 품질을 더 중요하게 평가하는 가중치)

### 8.2 검색 메트릭

#### 8.2.1 MRR (Mean Reciprocal Rank)

첫 번째 관련 결과의 순위에 초점:

```
MRR = (1/|Q|) × Σ (1/rank_i)

- 첫 번째 관련 문서를 빨리 찾는 것이 중요할 때 사용
- 이진 관련성 (관련/비관련)
```

#### 8.2.2 NDCG (Normalized Discounted Cumulative Gain)

순위와 관련성 등급을 모두 고려:

```
DCG@k = Σ (2^rel_i - 1) / log2(i + 1)
NDCG@k = DCG@k / IDCG@k

- 관련성에 등급이 있을 때 사용 (예: 0, 1, 2, 3)
- 상위 순위에 더 높은 가중치 부여
```

#### 8.2.3 Recall@K

상위 K개 결과에서 관련 문서 비율:

```
Recall@K = (K개 중 관련 문서 수) / (전체 관련 문서 수)
```

> - 출처: [Stackademic - NDCG vs MRR](https://blog.stackademic.com/ndcg-vs-mrr-ranking-metrics-for-information-retrieval-in-rags-2061b04298a6)

### 8.3 LLM 기반 검색 품질 평가

RAGAS 외에 LLM을 직접 활용하여 검색 품질을 평가하는 방식임.

#### 8.3.1 평가 방법

```python
def evaluate_search_quality(query: str, result: dict, llm_client) -> int:
    """LLM으로 검색 결과 관련성 평가 (0-100점)"""
    
    prompt = f"""
    다음 질문에 대한 검색 결과의 관련성을 평가하세요.
    
    질문: {query}
    검색 결과: {result['content'][:1000]}
    
    평가 기준:
    - 90-100: 질문에 대한 정확한 답변 포함
    - 70-89: 관련 정보 포함, 부분적 답변 가능
    - 50-69: 간접적으로 관련된 정보
    - 30-49: 약간 관련 있으나 답변에 불충분
    - 0-29: 관련 없음
    
    점수만 숫자로 응답:
    """
    
    response = llm_client.generate(prompt)
    return parse_score(response)
```

#### 8.3.2 배치 평가 스크립트 구성

```python
# 평가 실행
test_queries = [
    {"query": "RAG에서 청킹이란?", "expected_keywords": ["분할", "토큰", "문서"]},
    {"query": "BM25 알고리즘 설명", "expected_keywords": ["키워드", "TF-IDF", "희소"]},
]

results = []
for item in test_queries:
    search_results = retriever.search(item["query"], top_k=10)
    
    for result in search_results:
        score = evaluate_search_quality(item["query"], result, llm)
        results.append({
            "query": item["query"],
            "content_preview": result["content"][:100],
            "llm_score": score
        })

# 평균 점수 계산
avg_score = sum(r["llm_score"] for r in results) / len(results)
```

### 8.4 테스트 쿼리 설계 원칙

검색 품질 평가의 정확도는 테스트 쿼리 품질에 의존함.

#### 8.4.1 핵심 원칙

1. **데이터 소스 기반 설계**: 실제 인덱싱된 문서에 존재하는 내용으로 쿼리 작성
2. **다양한 난이도 포함**: 명시적 질문 ~ 추론 필요 질문까지 분포
3. **도메인 용어 활용**: 문서에 사용된 실제 용어로 쿼리 구성

#### 8.4.2 좋은 테스트 쿼리 vs 나쁜 테스트 쿼리

| 구분 | 예시 | 이유 |
|-----|------|-----|
| **좋음** | "Sparse Retrieval과 Dense Retrieval 차이" | 문서에 해당 섹션 존재 |
| **나쁨** | "Hybrid Search란?" | 문서에 정의 없이 사용만 됨 |
| **좋음** | "SAS 패턴의 구성 요소" | 구체적 내용 문서에 포함 |
| **나쁨** | "SAS 패턴이란?" | 문서에 정의 부재 |

#### 8.4.3 테스트 쿼리 검증 체크리스트

```
□ 해당 쿼리의 답이 인덱싱된 문서에 실제로 존재하는가?
□ 쿼리에 사용된 용어가 문서의 용어와 일치하는가?
□ 기대하는 답변의 위치(청크)를 알고 있는가?
□ 동의어/유의어 변형도 테스트에 포함되어 있는가?
```

### 8.5 테스트 데이터셋 구성

#### 8.5.1 테스트 데이터셋 크기 권장사항

### 9.2 AutoRAG-HP

AutoRAG-HP는 Multi-Armed Bandit(MAB) 알고리즘을 사용한
**자동 하이퍼파라미터 튜닝 방법**임.

```
- Hierarchical MAB (Hier-MAB)로 대규모 검색 공간 효율적 탐색
- Grid Search 대비 약 20%의 LLM API 호출로 유사한 성능 달성
- 튜닝 대상: top-k, 프롬프트 압축 비율, 임베딩 방법 등
```

선행 조건: 11.1에서 `test_dataset.py` 작성 + 인덱싱 대상 PDF(`hands-on/10.rag/data/특허법.pdf`) 존재

**요청 프롬프트:**
```
[목표]
청킹 사이즈(인덱싱 파라미터)를 변화시키며 naive RAG의 검색/생성 품질을 RAGAS로 평가·비교하여
최적 청킹 사이즈를 도출하는 예제 개발
[역할]
당신은 RAG 기반 AI앱 평가 전문가임
[입력]

  - 변화 변수: chunk_size 후보 3개 (예: [400, 800, 1200])
  - 고정 규칙: chunk_overlap = int(chunk_size × 0.2)  (청킹 사이즈의 20%, 각 후보마다 자동 계산)
  - 그 외 조건(임베딩 모델, LAW_SEPARATORS, top_k, 생성 LLM)은 전부 동일하게 고정
- 각 chunk_size 후보별 반복 처리:
  - indexing.py의 전처리·분할(LAW_SEPARATORS)·노이즈 필터 로직을 재사용하되,
    chunk_size·chunk_overlap을 파라미터로 받는 분할기로 PDF를 재청킹·임베딩
    (※ indexing.py의 split_documents()는 모듈 상수 CHUNK_SIZE/CHUNK_OVERLAP을 읽으므로 직접 호출 불가
       → chunk_size·chunk_overlap을 인자로 받는 분할기를 별도 구현)
  - test_dataset.py 테스트 케이스로 RAG 파이프라인(검색 → 생성) 실행 후 RAGAS 평가
- (중요) 공용 벡터 DB 보호:
  - 각 후보는 임시 persist_directory + 고유 collection_name(예: patent_law_cs400)으로 인덱싱하고 평가 후 정리
  - 공용 벡터 DB(hands-on/10.rag/vectordb)를 절대 덮어쓰거나 삭제하지 말 것

  - chunk_size는 검색 품질에 직접 영향 → Context Precision/Recall을 주 선정 기준으로 사용
```
